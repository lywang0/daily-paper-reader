## 摘要
本文旨在实现局域网（LAN）内跨设备的计算与通信高效GPU共享，促进异构个人设备上的普适AI推理。我们通过CUDA API远程调用实现分布式任务卸载。然而，除了原始计算之外，网络约束成为主要瓶颈：有限的带宽、高频API调用以及跨任务竞争显著阻碍了性能。为解决这些挑战，我们提出了Gleam，一种新颖且网络高效的框架，用于跨本地CUDA设备的任务通用GPU共享，具有三个关键贡献。首先，我们通过自动模型权重缓存减少了CUDA API远程调用中的带宽开销，并通过异步执行缓解了频繁API调用带来的累积延迟。其次，我们设计了一个运行时任务调度器，动态确定LAN客户端与服务器之间的API远程调用配对，明确考虑并行工作负载下的网络条件和GPU资源争用。最后，我们引入了专用机制以确保分布式执行中CUDA上下文的一致性。在异构NVIDIA GPU和多样化AI工作负载上的大量实验表明，Gleam始终优于最先进的基线，在API远程调用效率上实现了1.4至24.2倍的提升，系统吞吐量最高提升1.79倍。

## Abstract
This paper aims to enable computation- and communication-efficient GPU sharing across devices within local area networks (LANs), facilitating ubiquitous AI inference on heterogeneous personal devices. We achieve distributed task offloading via CUDA API remoting. However, beyond raw computation, network constraints emerge as the primary bottleneck: limited bandwidth, high-frequency API invocations, and cross-task contention significantly hinder performance. To address these challenges, we propose Gleam, a novel and network-efficient framework for task-generic GPU sharing across local-area CUDA devices, with three key contributions. First, we reduce bandwidth overhead in CUDA API remoting through automatic model weight caching, and mitigate accumulated latency from frequent API calls by asynchronous execution. Second, we design a runtime task scheduler that dynamically determines API remoting pairs between LAN clients and servers, explicitly accounting for both network conditions and GPU resource contention under parallel workloads. Finally, we introduce dedicated mechanisms to ensure CUDA context consistency across distributed executions. Extensive experiments on heterogeneous NVIDIA GPUs and diverse AI workloads show Gleam consistently outperforms state-of-the-art baselines, achieving 1.4-24.2 times improvements in API remoting efficiency and up to 1.79 times higher system throughput.

- 客户端拦截CUDA GPU API调用，通过局域网转发至远程服务器GPU执行。
- 相比整体程序卸载，API远程调用无需修改应用代码、无需安装复杂依赖环境，具有**非侵入性**、**任务通用性**和**细粒度控制**的优势。

## 2. 方法论：Gleam框架

### 总体架构
Gleam由三大核心模块组成：**CUDA API远程调用优化**、**竞争感知任务调度**和**CUDA上下文一致性守护**。客户端指定任务类型给调度器，服务器通过心跳上报运行状态，调度器预测延迟并分配目标服务器，客户端随后以优化后的API远程调用方式执行。

### 模块一：CUDA API远程调用优化（§4）

#### 4.1 模型权重管理器（Model Weight Manager）
- **权重块识别**：通过`cudaMalloc`分配的内存块，若其中所有`cudaMemcpy HtoD`数据块在块生命周期内保持不变，则识别为模型权重（一致性检查在`cudaFree`时执行）。
- **哈希索引检索**：客户端对每个HtoD块计算MD5哈希（取前1024位）；若哈希命中服务器的缓存表，只发送哈希和大小等轻量级元数据（<1KB），否则传输完整数据。
- **权重块共享与虚拟内存层**：构建虚拟地址映射（1TB虚拟地址空间，红黑树管理），将客户端地址映射到服务器的共享内存池；采用LRU策略进行容量回收。
- **效果**：消除3GB冗余传输，单次加载从152s降至9s；对7种任务识别出93%以上的权重块。

#### 4.2 API远程调用路径管理器（API Remoting Path Manager）
- **基本异步（Basic Async）**：对仅返回错误码的API（如`cudaLaunchKernel`），客户端乐观地立即返回成功，错误异步上报。
- **本地模拟（Local Simulation）**：对维护简单状态的API（如`cudaGetDevice`、`cudaPopCallConfiguration`），在客户端本地模拟状态更新，直接产生正确返回值。
- **批量预取（Batched Prefetch）**：对返回资源句柄的API（如`cublasLtMatmulDescCreate`），服务器批量预创建资源，客户端从本地句柄缓存中取出复用。
- **效果**：通过异步化消除客户端-服务器之间的同步往返依赖，显著提升高频API的吞吐。

### 模块二：竞争感知任务调度（§5）

#### 问题形式化
给定M个任务和N个服务器，最小化归一化总延迟：
$$\min_{X} \frac{1}{M}\sum_{i=1}^{M}\left(\frac{L_i^{infer}(\Psi,X)}{\bar{L}_i^{infer}} + \frac{L_i^{load}(\Psi,X)}{\bar{L}_i^{load}}\right)$$
约束条件：服务器GPU内存容量限制 + 每任务仅分配给一个服务器。

#### 资源竞争模型（§5.1.1）
- **资源占用率（$u_i$）**：通信维度=带宽占用率（模型加载期68%~80%，推理期约8%）；计算维度=GPU利用率（加载期<3%可忽略，推理期13%~90%）。
- **延迟增加因子**：$\alpha = \max(1, \gamma\sum_{i=1}^{n}u_i)$，其中$\gamma \geq 1$为惩罚因子。

#### 在线延迟预测器（§5.1.2）
- 接收任务按剩余时间降序排序，分段累加预测：
$$Latency = \sum_{i=1}^{|\Phi|}\alpha(\sum_{j=1}^{i}u_j)\times(r_i - r_{i-1}), \quad r_0 = 0$$
- 加载阶段剩余时间按已传字节/总字节比例估计；推理阶段按`cudaStreamSynchronize`调用次数比例估计（该类调用具有周期性规律）。

#### 两阶段调度算法（§5.2，Algorithm 1）
- **Phase 1（缓存任务优先）**：对服务器上有缓存、可直接进入推理阶段的任务，按GPU内存需求降序处理；按计算占用率约束（式6）对同类型任务分组以复用权重；分配给预测延迟最小的服务器。
- **Phase 2（无缓存任务）**：在带宽占用率允许的条件下，将无缓存任务分配给预测计算延迟最小且有内存余量的服务器；否则挂起等待。
- **复杂度**：O(MN)，可在运行时周期调用。

### 模块三：CUDA上下文一致性守护（§6）
- **网络故障恢复**：发送方保留未确认消息缓冲区，双向ACK机制；连接恢复后重新发送未确认消息；有界状态预留控制内存开销。
- **跨流保护**：全局门控机制，在CUDA图捕获（graph capture）期间阻止其他流上的上下文级API调用（如`cudaMalloc`、`cudaFree`），防止上下文崩溃。

| 开销量化（§7.6） | 调度开销（4配置）、恢复开销（4配置） | 8组 |

### 充分性评估
- **优点**：实验配置从1台到4台GPU递进（3→15并发客户端），覆盖从简单到复杂的扩展性验证；对比基线兼顾了API远程调用专用方案（GVirtuS、cricket+SR、DGSF）和调度方案（FGD、Mudi）；消融实验验证各模块必要性。
- **不足**：实验服务器最多4台GPU，大规模扩展性未验证；客户端为模拟而非真实多台物理设备；Wi-Fi 6单一路由器拓扑，未覆盖复杂LAN拓扑；未与vLLM/SGLang等任务特定推理框架对比（作者在附录A.4.2中以适用场景不同为由回避）。

## 6. 主要结论与发现

1. **API远程调用效率显著提升**：Gleam在Wi-Fi和以太网下均稳定超越SOTA基线，实现1.4×~24.2×加速；对sd3-medium-t5-ggml，较GVirtuS提速约54×，较cricket+SR约8.4×，较DGSF约3.9×。
2. **端到端吞吐量最高提升1.79×**，平均延迟降低最多1.56×，排队延迟降低2.88×，Makespan缩短1.76×。
3. **通信优化逐步叠加效果显著**：从朴素版起逐步添加异步、批处理、模拟、权重缓存，延迟呈一致下降趋势。
4. **任务调度开销可忽略**：单次调度仅74~84微秒；恢复机制开销受控（max_pending_batch=8时开销≤4.16%）。
5. **Wi-Fi劣势可被缓解**：启用全部优化后，Wi-Fi额外开销从约81×降至约53%（以太网从约31×降至19%）。

## 7. 优点

- **任务通用性**：API级设计不依赖特定任务/框架，对ggml和PyTorch任务均可优化，已支持1000+ CUDA API。
- **系统性优化覆盖两大阶段**：针对模型加载（权重缓存消除冗余传输）和推理（异步化消除往返延迟）分别定制优化，而非仅单一策略。
- **调度算法轻量高效**：O(MN)贪心两阶段调度替代O(N^M)暴力搜索，可在运行时周期调用；离线profiling + 在线预测相结合，适应动态环境。
- **竞争模型简洁且有效**：基于资源占用率和延迟增加因子的拥塞预测模型，经过验证（并发加载预测59.76s vs 实测58.32s）。
- **鲁棒性设计**：网络故障恢复和跨CUDA流保护使系统支持长期多任务共享，而非仅一次性短期执行。
- **非侵入式部署**：采用gRPC + protobuf + LD_PRELOAD拦截，无需修改应用源码。

## 8. 不足与局限

### 实验覆盖方面
- **规模有限**：最多4台GPU、15个并发客户端，大规模集群下的可扩展性（如数十上百GPU）未验证。
- **网络拓扑单一**：仅Wi-Fi 6 + 千兆以太网交换机的简单两级拓扑，未评估多跳网络、RDMA、跨交换机等复杂场景。
- **客户端模拟**：使用单台CPU机器模拟多客户端，未在真实分布式物理设备上部署，未考虑真实客户端CPU处理能力差异。
- **缺乏真实训练场景**：仅覆盖推理任务，未评估训练或微调场景下的API远程调用行为。

### 偏差风险
- **哈希碰撞**：权重块哈希（MD5前1024位）碰撞概率在理论上非零，虽实验中未观察到，但缺乏形式化安全性证明；小于1024字节的块不做缓存。
- **权重识别保守性**：若块中有任何片段被修改则整个块不缓存——对部分更新的权重块效率降低（如compvis仅识别66.91%）。
- **离线profiling依赖**：任务配置（资源占用率、延迟成本、缓存块分布）依赖于离线单任务测量，环境变化时可能需要重新配置。
- **与任务特定框架的对比缺失**：直接回避了与vLLM、SGLang的高效推理框架对比，虽以场景不同为由，但缺乏量化比较。

### 应用限制
- **仅限NVIDIA CUDA生态**：不适用于AMD/Intel等非NVIDIA GPU。
- **数据安全未解决**：未来工作才计划解决边缘GPU共享的数据安全问题，当前版本缺乏隐私保护（明文传输权重数据）。
- **API覆盖不完备**：如CUDA Driver API覆盖率为57%，部分PyTorch调用的API无法通用优化，需完整RTT，导致PyTorch任务仍有3×以上延迟退化。

## 总结
Gleam是一项系统性工程，在CUDA API远程调用这一既有方向上，针对局域网特有的带宽和延迟瓶颈提出了"权重缓存 + 异步路径优化 + 竞争感知调度 + 上下文守护"的完整解决方案。实验数据扎实，消融清晰，结果显著优于现有方案。但其验证规模限于小型LAN原型系统，距离实际超大规模部署仍有距离，且安全与隐私问题尚待解决。
