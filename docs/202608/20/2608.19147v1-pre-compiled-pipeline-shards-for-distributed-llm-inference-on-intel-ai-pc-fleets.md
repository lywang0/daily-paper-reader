## 摘要
现代英特尔AI PC搭载了性能不俗的集成GPU和NPU，配备16GB以上统一内存，但大部分时间处于空闲状态。然而，这些内存仍不足以容纳诸如700亿参数大语言模型这样的大型模型。我们证明，通过普通网络协作的少量AIPC即可提供超越任何单台设备能力的模型服务。我们采用流水线并行策略：将模型按层分割为各阶段分片，每个分片预编译为OpenVINO图，使每台机器运行一个分片并将激活传递至下一分片。三项技术使其速度得以实用。首先，我们恢复了未分割模型的性能：朴素的逐阶段导出运行速度远低于整体推理，因为它错过了OpenVINO GPU优化；向每个分片注入beam_idx Gather可触发该优化（IndirectKVCache融合），使分片性能与整体推理持平。其次，我们利用有状态OpenVINO模型上的推测解码。第三，该流水线通过跨阶段交错处理多个用户的请求（每个请求携带自身缓存，即微批处理）同时服务多个用户。综上，双节点Llama 3.1 8B INT4流水线在相同硬件上同时服务两个并发用户，其吞吐量是未分割模型单用户吞吐量的1.79倍，且在模拟广域网延迟下差距进一步扩大。同一设计可扩展至单个成员无法容纳的70B模型：英特尔Tiber Cloud上四节点Lunar Lake AI PC部署为单个用户提供交互式速度，输出与无推测解码的同一四节点流水线逐token完全一致。代码、原始基准日志和复现脚本以自包含包形式提供，位于https://github.com/labscommunity/pipeline-sharded-inference-paper（顶层reproduction/目录）。

## Abstract
Modern Intel AI PCs ship capable integrated GPUs and NPUs with 16+ GB of unified memory, and they spend considerable time idle. That is not enough memory to fit a large model such as a 70B-parameter LLM. We show that a handful of AIPCs, working together over an ordinary network, can serve models beyond the capability of any single one. We use pipeline parallelism: a model is split by layer into per-stage shards, each pre-compiled into an OpenVINO graph, so that every machine runs one shard and passes activations to the next. Three techniques make this fast enough to be useful. First, we recover the speed of the unsplit model: a naive per-stage export runs well below monolithic inference because it misses an OpenVINO GPU optimization, and injecting a beam_idx Gather into each shard triggers that optimization (the IndirectKVCache fusion) and brings the shards to parity. Second, we leverage speculative decoding on stateful OpenVINO models. Third, the pipeline serves several users at once by interleaving their requests across the stages, each request carrying its own cache (micro-batching). Together, a two-node Llama 3.1 8B INT4 pipeline serves two concurrent users at 1.79x the single-user throughput of the unsplit model on the same hardware, and the gap widens under simulated wide-area latency. The same design scales to a 70B model that no single fleet member can hold: a four-node deployment of Lunar Lake AI PCs on Intel Tiber Cloud serves a single user at interactive speed, with output token-for-token identical to the same four-node pipeline decoding without speculation. Code, raw benchmark logs, and reproduction scripts ship as a self-contained package at https://github.com/labscommunity/pipeline-sharded-inference-paper (in the top-level reproduction/ directory).

## 2. 方法论

### 核心思想

- **流水线并行**：将模型按层切分为 N 个连续的分片（shard），每个分片预编译为独立的 OpenVINO INT4 图，部署在一台机器上；每台机器只运行一个分片，分片之间通过 TCP 连接传递隐藏状态（激活）。
- **三大关键技术**叠加，使分布式推理从“可用但慢”提升到“超过单体性能”：

### 关键技术之一：beam_idx Gather注入（达到单机性能持平）

- **问题**：朴素的分片导出（每阶段独立导出）比整体模型（monolithic）慢 13–23%，原因是 OpenVINO GPU 插件内的 `IndirectKVCache` 优化被门控在特定图模式上——每个 KV `ReadValue` 的输出必须经过由 `beam_idx` 参数索引的 `Gather` 操作才会触发该融合。初始导出缺少该模式，GPU 回退到性能较差的通用 `KVCacheFusion` 路径。
- **解法**：在导出后的图上做图手术——添加 `beam_idx: [-1] i32` 参数，并在每个 KV `ReadValue` 与其下游消费者之间插入 `Gather(ReadValue, beam_idx, axis=0)`。这使得分片达到与整体推理的 0.4% 以内性能差距（v5_beam 分片）。
- **澄清**：这只是一个编译期模式，运行时 `beam_idx = [0]` 是恒等重排，论文中所有解码均为贪心解码，不涉及实际 beam search。

### 关键技术之二：基于掩码的 KV 缓存回退（使推测解码在有状态 OpenVINO 上有收益）

- **问题**：推测解码需要拒绝草稿模型的错误 token 并从 KV 缓存中移除其贡献。标准做法（物理修剪：`query_state()`/`set_state()`）耗时约 48ms/次（Arc B390 iGPU 上，72-token 缓存），足以使推测解码在常见接受率下净亏损。
- **解法**：利用 OpenVINO 状态模型已有的 `attention_mask` 输入——将拒绝的草稿 token 位置对应的 mask 设为 0，而不是物理移除它们。这样注意力结果与物理修剪**位级完全相同**（验证最大绝对差异为 0.0000，FP32 精度），而成本仅为 CPU 端重建 mask，小于每步耗时的 1%。
- **要点**：`position_ids` 跟踪逻辑序列长度（回退前长度）而非物理缓存长度，保证 RoPE 旋转一致。缓存膨胀比在 2048-token 生成时仅 1.02×，无需在线压缩。

### 关键技术之三：微批处理（多用户并发）

- **原理**：每个 OpenVINO `InferRequest` 携带独立的 KV 缓存状态。为每个分片创建两个（或多个）`InferRequest`，即可在阶段 1 处理请求 A 时，阶段 0 同时处理请求 B，从而填充流水线气泡。
- **实现**：每个用户流使用独立的 `compile_model()` 调用，拥有完全独立的编译图和 KV 状态，实现流间隔离。
- **效果**：2 节点管道上，2 流并发比单流分布式提升 1.80×。

### 系统架构与推理流程

- **协调者（Coordinator）** 由节点 0 承担：托管 tokenizer、生成循环、第 0 阶段分片，以及（启用推测解码时）草稿模型。
- **每步解码流程**：协调者运行 stage 0 → 隐藏状态经 TCP 传给 stage 1 → 中间阶段逐级转发 → 最终阶段应用 LM Head 返回 token（或 top-1 logits）→ 逐跳返回协调者。
- **TCP 激活中继**：静态持久连接，TCP_NODELAY 已设置，16KB/跳的 FP32 激活（约 6.5ms 一跳的 WiFi 延迟）。
- **导出流水线**：选择性层加载 → 手动注意力重写（替换 DynamicCache/RoPE）→ `torch.jit.trace` + `ov.convert_model` + `make_stateful_transformation` → NNCF INT4 压缩（组大小 128）。

## 6. 总体评价与意义

该论文提出了一套完整、可落地的分布式 LLM 推理方案，核心价值在于将“闲置的 AI PC 算力”组织起来，以零额外硬件成本、全数据本地化的方式运行远超单机容量的大模型。三大关键优化均针对实际工程痛点提出，且实验结果充分支持其主张：分布式流水线不仅能跑通 70B 模型，还能在吞吐量上超过单机单体推理，并在 WAN 延迟下保持可用性。尽管在硬件普适性、极端网络条件和系统可靠性方面存在局限，但论文严谨的实验设计与详尽的消融分析，使其成为边缘 AI 推理领域一项具有重要参考价值的工作。
