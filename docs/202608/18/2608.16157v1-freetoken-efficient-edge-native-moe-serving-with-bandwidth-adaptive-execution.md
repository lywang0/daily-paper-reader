## 摘要
前沿开放权重模型日益普及，但其服务仍然主要假设在数据中心基础设施上运行。我们提出了FreeToken，一个边缘原生的MoE服务系统，它将个人机器不仅视为小型GPU，而是作为一个统一的弹性推理平台。FreeToken围绕本地AI的两个现实情况，协同设计整个服务堆栈，包括模型布局与加载、专家驻留、CPU-GPU执行、智能体状态复用和运行时内存管理：智能体工作负载持续改变其执行模式，边缘硬件展现出异构资源，其平衡因机器而异。FreeToken不采用固定的卸载策略，而是持续将计算和模型状态映射到实际可用的资源上。FreeToken支持超过20种MoE模型，以及从8GB笔记本电脑GPU到单一工作站GPU等硬件上的真实编码和工具使用智能体。更重要的是，它改变了这些机器实际能服务的范围：从笔记本电脑上的35B模型，到游戏台式机上的284B模型，再到单一工作站GPU上的753B GLM-5.2。FreeToken将开放权重转化为可部署的本地软件，使用户已有的机器成为面向前沿规模的智能的实际平台。我们在flashml.ai上发布该系统。

## Abstract
Frontier open-weight models are increasingly available, but serving them still largely assumes datacenter infrastructure. We present FreeToken, an edge-native MoE serving system that treats a personal machine not as a small GPU, but as a unified, elastic inference platform. FreeToken co-designs the full serving stack, including model layout and loading, expert residency, CPU--GPU execution, agentic state reuse, and runtime memory management, around two realities of local AI: agent workloads continuously change their execution pattern, and edge hardware exposes heterogeneous resources whose balance differs from machine to machine. Rather than committing to a fixed offloading strategy, FreeToken continuously maps computation and model state onto the resources actually available. FreeToken supports more than 20 MoE models and real coding and tool-using agents across hardware ranging from an 8GB laptop GPU to a single workstation GPU. More importantly, it changes what these machines can practically serve, from a 35B model on a laptop to a 284B model on a gaming desktop and the 753B GLM-5.2 on a single workstation GPU. FreeToken turns open weights into deployable local software, making the machines users already own a practical platform for frontier-scale intelligence. We release the system at flashml.ai.

## 1. 论文的核心问题与整体含义

- **背景与动机**：前沿开放权重模型（如 Kimi-K3、GLM-5.2、DeepSeek-V4-Flash）的能力正快速逼近专有系统，但“发布参数”与“能跑起来”是两回事。传统推理依赖昂贵的云数据中心 GPU 集群，而代理（Agent）应用（编码、工具调用等）带来的推理需求激增，使得个人用户和小团队难以承受持续 API 成本。
- **核心观察**：全球已有超过一亿台消费级 GPU 设备（游戏本、工作站、笔记本），这些算力被大量闲置；MoE 架构使单 token 激活的参数占比很小（如 DeepSeek-V4-Flash 激活 13B/284B），理论上可在边缘设备运行，但完整专家池仍远超显存，需要高效的 CPU–GPU 协同卸载。
- **论文主张**：现有边缘服务系统（llama.cpp、KTransformers、Ollama、MoE-Infinity）只解决碎片化问题，在预填充（Prefill）、解码（Decode）和资源弹性三方面均存在明显短板。FreeToken 将个人机器视为“统一的弹性推理平台”，通过带宽自适应执行、语义感知缓存和弹性内存管理，把开放权重变成用户已有的、可实际部署的本地软件。

## 2. 论文提出的方法论

- **总览**：FreeToken 构建两级专家内存层次：CPU 内存中驻留完整专家池，作为“源数据”；GPU 显存中维护一个**弹性专家缓存**（按 `(layer, expert)` 逻辑标识组织），非专家权重常驻 GPU。核心是两条执行原则 + 一个弹性资源管理策略：
  - **带宽自适应执行**：将有限 PCIe/主机带宽作为运行时调度信号，动态决定专家从何处执行。
  - **语义感知缓存**：在预填充和解码阶段分别利用“智能体上下文编辑结构”和“token 间路由局部性”来最大化复用。
  - **弹性边缘资源管理**：让 GPU 显存预算可运行时调整，无需重启引擎。

- **预填充阶段（Prefill）**：
  - **全层双缓冲（Full-Layer Double Buffering）**：为每个 MoE 层分配两个完整层缓冲区。GPU 计算第 `l` 层时，专用传输流同时将第 `l+1` 层全部专家载入另一缓冲区；通过静态图捕获保证流水线连续，预填充达到 PCIe 带宽上限（约 6.7k tok/s），关闭重叠后吞吐下降 19%–26%。
  - **语义感知状态缓存（Semantic-Aware State Cache）**：针对混合注意力架构（全注意力 + 滑动窗口/循环层），在特殊 token（`<think>`、`</tool_call>`、`</tool_output>` 等）标记的语义边界保存循环状态检查点。智能体框架编辑上下文（如删除思考块、替换工具输出）时，可从最近的有效检查点恢复，只重新计算新增后缀，避免整段重预填充。

- **解码阶段（Decode）**：
  - **语义感知专家缓存**：利用路由时间局部性（相邻 token 倾向于路由到相同/相近专家），用跨层共享的 **LRU 专家缓存**取代静态专家放置。命中率显著更高（在 5090 上 DSV4 的 miss 率 39% vs KTransformers 59% vs llama.cpp 89%）。
  - **q\* 策略**：对未命中专家集合 `M`，划分成 `F`（通过 PCIe 搬入缓存并 GPU 执行）和 `C`（直接在 CPU 执行），融合两部分的部分和得到精确输出。公式如下：
    - 令 `S` 为单个专家大小，`B_P` 为 PCIe 传输带宽，`B_H` 为主机侧专家处理带宽。
    - PCIe 饱和后留给 CPU 的残差带宽 `B_R = max(B_H - B_P, 0)`。
    - 两分支耗时近似：`T_fill(q) ≈ qS/B_P`，`T_cpu(m-q) ≈ (m-q)S/(B_H - B_P)`。
    - 平衡后得到最优填充数：`q⋆ ≈ m · B_P / B_H`。
    - 该策略同时覆盖极端情况（当 `B_H ≈ B_P` 时退化为纯 on-demand 填充），并保留至少一个填充项以维持缓存自热。

- **弹性内存管理**：
  - **运行时缓存重建**：在调度安全点，FreeToken 可根据变化的 VRAM 预算重建 GPU 专家缓存，无需重启或重载宿主池。
  - **快速启动**：将专家权重直接从磁盘读入最终宿主布局后再 pin 内存，避免先 pin 空页再写入带来的开销；冷启动首请求通过普通解码路径处理，无需预热。

## 7. 论文的局限与未解决的问题

- **模型覆盖有限**：虽然包含 35B/284B/753B 三个量级，但所有模型均为 MoE 架构；对于稠密（Dense）模型或不同量化方案（如 INT8/INT4 非原生格式）的适用性未被验证。FreeToken 的优化几乎全部针对“专家可卸载”这一 MoE 特性设计，对稠密模型的预填充/解码加速手段缺乏讨论。
- **评估场景偏窄**：四个工作负载均为“单用户代理”类，未涉及多租户并发、批量推理或长会话服务；缓存与调度策略在多用户混合负载下的表现（如缓存污染、公平性）仍是开放问题。
- **语义边界依赖标记鲁棒性**：语义感知状态缓存依赖模型输出中稳定存在的特殊 token（`<think>`、`</tool_call>` 等）。若模型未产生这些标记，或代理框架以非结构化方式编辑上下文，检查点策略将退化为保守的全量重算，收益不确定。
- **q\* 策略的静态假设**：调度模型假设专家大小均匀、带宽恒定、主机计算资源独占。实际中 MoE 各层专家大小可能不一致，NVMe 换页、后台进程、CPU 频率波动都会使最优填充数发生漂移；论文未说明是否引入了运行时自适应步长调节。
- **冷启动与长尾内存仍待细化**：快速启动优化的是“加载到宿主池”的初始化；首次请求仍走普通解码路径。对于 753B 级别模型，主机内存驻留完整专家池本身就需要约 1.5TB 内存（NVFP4），普通 PC 难以满足，FreeToken 的适用边界实际比标题暗示的更窄。
- **缺乏质量评测**：论文只报告吞吐和延迟，未验证与官方实现相比的生成质量是否一致（尽管权重逐位一致，但 CPU 分支与 GPU 分支的数值精度差异、融合方式可能引入轻微偏差）。
- **开源发布情况不明**：文中未提及代码、配置或模型转换工具的公开计划，这对可复现性是一个显著限制。

## 8. 个人总体评价（优点与不足）

**优点**：
- **问题意识强**：准确捕捉了“大模型能力增强 vs. 个人设备算力闲置”之间的剪刀差，将 MoE 推理从“能不能跑”推进到“跑得好不好、快不快”的层次。
- **技术组合有启发性**：带宽自适应执行、语义感知缓存、弹性显存管理三者形成了完整闭环，尤其是将“宿主带宽”而非“GPU 算力”作为调度核心信号，是值得借鉴的系统设计视角。
- **实验设计扎实**：硬件覆盖从 8GB 笔记本到 96GB 工作站，权重格式严格对齐，带宽实测而非规格，对比结果可信度高；消融实验针对三项核心机制分别给出量化支撑。

**不足**：
- **概念包装略大于实质创新**：语义感知缓存本质上是“前缀缓存 + 检查点”的工程化变体，q\* 策略的数学推导较为朴素，核心贡献更多在于工程整合（静态图捕获、双缓冲、运行时重建）而非范式创新。
- **评估标准单一**：全部指标围绕 Token 吞吐和 TTFT，缺少端到端任务成功率（如 SWE-bench 的 Patch 通过率）、能效（Joule/token）或成本（$/token）的对比，导致“更好”只体现在速度层面，而非智能体完成任务的综合效能层面。
- **与基线对比的公平性有隐性倾斜**：基线的静态缓存策略原本不针对代理工作负载的频率感知与上下文编辑设计，FreeToken 以自身有利场景（代理编辑 + 路由局部性）证明自身优势，属于“主场作战”；若换到随机上下文切换的多用户场景，优势幅度可能收窄。
- **表达与可读性略显晦涩**：一些核心名词（如“智能体上下文编辑结构”“带宽饱和自适应”）定义不够直观，图表编号与正文的对应关系不够紧密，增加了复现难度。

**适用场景**：FreeToken 最适合“单人开发者/研究者在自有 GPU 上运行开放权重 MoE 模型做代理任务”的部署形态。对云数据中心场景、多租户服务或严格离线批次处理，其收益有限。它代表了一个重要方向：把推理系统从“数据中心导向”转向“边缘设备导向”，让超大开放模型的本地部署不再只是演示，而是一种可日常依赖的基础设施。

## 9. 最终总结（一句话）

FreeToken 通过带宽自适应调度、语义感知缓存与弹性显存管理，将消费级 GPU 上的 MoE 代理推理速度提升至最强基线 1.3–2.3 倍，证明了“一亿台闲置显卡足以构成分布式大模型推理底座”的可行性；但其评估场景的单一性、对代理语义标记的依赖以及开源缺失，使其在成为通用工业标准之前仍需更多验证与打磨。
