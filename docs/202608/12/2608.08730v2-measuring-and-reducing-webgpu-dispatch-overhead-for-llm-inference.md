## 摘要
大语言模型被部署到多种类型的环境中，从互联网浏览器到边缘设备，而WebGPU作为一种现代跨平台标准。基于浏览器的LLM推理引擎已经 proliferated，但WebGPU每操作调度的开销仍然缺乏详细描述。在这项工作中，我们引入了一种顺序调度测量方法，并表明朴素的单操作测量通过将调度与同步混为一谈而高估了每调度成本。使用我们的方法，我们测量了每调度成本，并表明它与使用的数据类型无关。我们表明，在批次大小为1时，调度开销（而非内核质量）是瓶颈，并将调度计数隔离为原因。因此，我们得出结论，在批次大小为1时，WebGPU中LLM推理优化的有效方法是减少调度计数。我们的发现指向调度摊销，在推理引擎和WebGPU规范中，作为实用浏览器推理的路径。

## Abstract
Large Language Models are deployed to multiple types of environments, from internet browsers to edge devices, and WebGPU serves as a modern cross-platform standard. The engines for browser-based LLM inference have proliferated, yet the overhead of WebGPU per-operation dispatch remains poorly characterized. In this work, we introduce a sequential-dispatch measurement method and show that naive single-operation measurements overestimate per-dispatch cost by conflating dispatch with synchronization. Using our method, we measure the per-dispatch cost and show that it is independent of data type used. We show that the dispatch overhead, not kernel quality, is the bottleneck at batch size 1, and isolate the dispatch count as the cause. Therefore, we conclude that at batch size 1, the effective approach to LLM inference optimization in WebGPU is reducing dispatch count. Our findings point to dispatch amortization, in the inference engines and in the WebGPU specification, as a path to practical browser-based inference.

## 方法论

- **核心思想**：将“调度（dispatch）”与“同步（GPU-CPU synchronization）”两种成本明确分离。朴素单操作测量（naive single-operation timing）把一次完整操作从编码到同步的整个往返时间都归因于调度，从而大幅高估了每次调度的实际边际成本；真实的自回归解码每个 token 只需同步一次，而不是每个操作同步一次。
- **顺序调度测量方法（sequential-dispatch measurement）**：
  - 连续提交 N 个完全相同的调度操作，仅在最后做一次 GPU-CPU 同步。
  - 将总耗时除以 N，得到单个调度的摊销边际成本（amortized marginal cost）。
  - 这样一次性同步成本被摊销掉，剩余即为纯调度开销。
- **关键技术细节**：
  - 测量基于作者自研的 **torch-webgpu** 后端（PyTorch 的 PrivateUse1 扩展），将模型编译为 WGSL 着色器，并通过 Dawn 执行。
  - 覆盖多种 WebGPU 实现（Dawn、wgpu-native）和底层 API（Vulkan、Metal），以及多个 GPU 厂商设备。
- **可控融合实验**：
  - 保持底层计算不变（WGSL 着色器未重新 tile 或优化），仅通过融合操作减少调度次数（876 → 564）。
  - 由于融合仅减少约 1.8 MB 的中间内存流量（小于 1 μs 的传输时间），因此可排除内存带宽因素。
  - 通过控制变量，将吞吐量提升归因于调度次数的减少，从而隔离出“调度计数”作为独立变量。
- **实验性质**：该方法测量的是“同质调度流”下的摊销成本，是一个下界；真实推理中的异构操作、数据依赖和浏览器调度会增加开销，因此顺序测量值可作为真实开销的下界参考，朴素单操作测量值作为上界。

## 主要结论与发现

- **朴素测量高估调度成本**：单操作端到端测量将一次 GPU-CPU 同步（约 450 μs）折叠进调度成本，导致高估约 20 倍（Dawn上），在 Chrome 和 Safari 上高估更严重（最高约 63 倍）。
- **真实调度成本**：顺序测量得到的每调度成本为 **Vulkan 24–36 μs、Metal 32–71 μs**，且 **与数据类型无关**（float32 与 float16 相同）。
- **调度开销是 batch size = 1 时的瓶颈**：在保持内核质量不变、内存流量节省极微小的条件下，仅将调度次数从 876 降到 564，吞吐量提升 **53%**（从 13.5 到 20.6 tok/s），TTFT 从 71.4 ms 降至 41.6 ms。
- **调度次数而非内核质量决定性能**：由于融合未改变计算方式和效率，唯一的显著变量是调度次数，因此证明了调度数量才是主要限制因素。
- **命令缓冲提交是主要开销来源**：Submit 占单个调度 CPU 时间的约 40%（12.9 μs），其次是 encoder 创建和结束（合计约 12.5 μs），流水线设置、绑定组和派发调用相对较小。
- **减少调度次数是 WebGPU LLM 推理的关键优化路径**：建议在推理引擎和 WebGPU 规范层面引入调度摊销机制（类似 CUDA Graphs 的命令图捕获和重放），但同时需要考虑浏览器安全模型对逐操作校验的要求。
