## 摘要
大型语言模型（LLM）被集成到软件系统和AI服务中，使得高效的LLM服务成为软件工程关注的问题。LLM服务具有挑战性，因为推理需要计算、内存、GPU资源和执行，同时还要保持延迟和吞吐量。尽管先前的研究已经提出了LLM推理、优化和服务技术及框架，但关于它们在实践中如何被采用知之甚少。在本研究中，我们调查了开源软件系统中LLM服务框架和服务方法的使用情况。我们识别并分析了五个特定于LLM的框架：vLLM、SGLang、TensorRT-LLM、LMDeploy和FlashInfer。我们检查了这些框架和技术如何单独和组合采用，采用如何在不同类别的LLM之间变化，以及仓库在意图、关注点、用例和架构设计上的差异。我们的结果表明，vLLM在流行度和采用率方面是最可见的框架，而并行计算、内存管理和网络剪枝是最常用的服务方法类别。多框架使用有限，表明开发者依赖单一服务框架；然而，组合框架连接了服务栈中的互补能力。框架采用在不同模型家族、模态、模型大小、领域专业化和部署设置中有所不同。仓库级别的分析表明，LLM服务框架支持应用和架构，包括基于强化学习（RL）的推理、多模态生成和理解、微服务以及云基础设施。总体而言，本研究提供了实践中LLM服务框架采用的大规模经验特征，并为研究LLM系统的研究人员、框架维护者和实践者提供了见解。

## Abstract
Large Language Models (LLMs) are integrated into software systems and AI services, making efficient LLM serving a concern for software engineering. Serving LLMs is challenging because inference requires computation, memory, GPU resources, and execution while maintaining latency and throughput. Although prior research has proposed LLM inference, optimization, and serving techniques and frameworks, little is known about how they are adopted in practice. In this study, we investigate the use of LLM serving frameworks and serving methods in open-source software systems. We identify and analyze five LLM-specific frameworks: vLLM, SGLang, TensorRT-LLM, LMDeploy, and FlashInfer. We examine how these frameworks and techniques are adopted individually and in combination, how adoption varies across categories of LLMs, and how repositories differ in intent, focus, use case, and architectural design. Our results show that vLLM is the most visible framework in popularity and adoption, while parallel computation, memory management, and network pruning are the most frequently used serving-method categories. Multi-framework usage is limited, suggesting that developers rely on a single serving framework; however, combined frameworks connect complementary capabilities across the serving stack. Framework adoption varies across model families, modalities, model sizes, domain specializations, and deployment settings. Repository-level analysis shows that LLM serving frameworks support applications and architectures, including Reinforcement Learning (RL)-based reasoning, multimodal generation and understanding, microservices, and cloud infrastructure. Overall, this study provides a large-scale empirical characterization of LLM serving framework adoption in practice and offers insights for researchers, framework maintainers, and practitioners working on LLM systems.

### 6. 论文的主要结论与发现

- **RQ1 — 流行度与采用率**：
  - **vLLM 在 GitHub 流行度（56.3K stars）和仓库采用率（1,821 个过滤后仓库）上均居首位**；FlashInfer 的采用排名（第 3）高于其流行度排名（第 5）；TensorRT-LLM 流行度第 3 但采用率最低，可能受 NVIDIA 专用硬件限制。
  - 最常用的服务方法类别是：**额外并行计算方法（1,010 仓库）、内存管理方法（451 仓库）、网络剪枝（203 仓库）**；框架内部模式差异显著，如 FlashInfer 仓库高度集中于内核融合（88%）。
  - 早期退出、投机解码、注意力简化等架构级方法采用率极低；非自回归解码、配置缩减、循环单元、激活共享等方法甚至未在现有框架中实现。
- **RQ2 — 方法与框架组合**：
  - 开发者常在**同一框架内组合多种服务方法**（如 vLLM 中内存管理 + 并行计算；FlashInfer 中定制注意力 + 内存管理 + 内核融合），以协同解决不同瓶颈。
  - **多框架使用率总体有限**：vLLM 绝对共现数最大（28 个仓库）但比率最低（1.54%）；FlashInfer 共现比率最高（44.23%），常作为低层注意力/内核优化组件嵌入其他框架。
  - 三大反复出现的框架组合（FlashInfer+vLLM、SGLang+vLLM、FlashInfer+SGLang）均体现**服务栈分层互补**的特征——上层调度/内存/并行（vLLM、SGLang）与低层注意力/内核优化（FlashInfer）的结合。
  - 框架采用因模型类型而异：**vLLM 和 LMDeploy 覆盖的模型家族范围更广**；仅 LMDeploy 涉及边缘/资源受限场景和嵌入式检索/数学推理/专用 grounding 等专业化模型；大模型（10B+、70B+、MoE）仅见于 vLLM 和 LMDeploy。
- **RQ3 — 仓库级系统类型**：
  - 采用服务框架的仓库覆盖多样化的意图（高性能 GPU 服务、RL 框架、数学推理 RL、RAG、多模态、聊天智能体等）；
  - 技术焦点涵盖模型训练与优化、CUDA 并行与内核优化、容器化 API 部署、Kubernetes 部署、语音/OCR/多媒体流水线、Hugging Face 与 RL 集成等；
  - 用例涵盖高效 LLM 服务、云部署、长上下文 QA、数学推理、RL 工作流、Agent 系统、检索推荐、GPU 优化部署等；
  - 系统设计涵盖可扩展服务后端、容器化 GPU 部署、微服务和云基础设施、Kubernetes 架构等；
  - **各框架采用模式不均匀**：vLLM 在四个维度全面领先；SGLang 跨度较广但集中在主流指令/聊天工作负载及中小模型；TensorRT-LLM 集中在 GPU 导向和部署密集型上下文；FlashInfer 主要聚焦 GPU 服务、内核优化和服务后端基础设施。

- **分析粒度丰富**：从框架 → 方法 → 方法组合 → 框架组合 → LLM 类型 → 仓库系统特征逐层递进，视 角全面。
- **分类体系灵活**：在遇到已有分类无法覆盖的新方法时，主动新增子类别而非强行归入错误类别，保证了分类的科学性。
- **聚类流程标准化**：使用 GPT-4o mini 生成多源信息融合的结构化仓库摘要，再通过 SentenceTransformer + UMAP + HDBSCAN + BERTopic 的标准主题建模流水线，并对多种预处理策略进行对比选择，提升了聚类可靠性。
- **可复现性**：提供了完整的复制包（replication package），包含数据、脚本和分析结果。
- **结论行动导向**：对框架维护者（改进文档、API、集成示例）、应用开发者（框架选型参考）、MLOps 工程师（部署规划）、研究人员（未来方向）均提供了明确可操作的建议。

### 8. 不足与局限

- **样本偏差**：
  - 仅分析 Python 仓库（虽遵循 Python 主导的现状，但仍忽略其他语言生态）；
  - 仅关注 GitHub 开源仓库，不包括商业/闭源部署场景；
  - 过滤条件（10 stars/forks、100 commits、一年内活跃、≥1 贡献者）可能排除了一些新生的但具有代表性的项目；
  - 框架 API 搜索依赖 GitHub Search API，虽然分区策略缓解了 1,000 条限制，但仍可能因 GitHub 搜索索引覆盖不完整而有遗漏。
- **TensorRT-LLM 样本量过小**：过滤后仅 15 个仓库，其采用率对比、方法组合分析（图 3c）和模型类型分析受统计效力限制，结论的外推性存疑。
- **方法检测的不完整性**：
  - 方法→API 映射依赖框架官方文档，可能存在文档未覆盖的 API 或被检测脚本的遗漏；
  - 许多方法（如并行计算）通过参数传递使用而非 import 语句，仅靠正则和 AST 可能漏检或误判；
  - LoRA 服务等"零使用"结论需谨慎，可能只是检测方式未能捕获。
- **小样本多框架组合分析**：FlashInfer+vLLM（18 个）、SGLang+vLLM（5 个）、FlashInfer+SGLang（4 个）的仓库级表格逐行分析具有描述性价值，但难以统计推断；"多框架使用有限"的原因（集成复杂度、兼容性约束、文档缺乏等）未能验证，仅作为推测。
- **LLM 类型归类的可靠性**：模型家族、大小、专业化等分类来自人工归纳，某些归类判断可能受模型文档和常见认知影响，存在主观性风险。
- **聚类主观性风险**：依赖 LLM 生成的摘要进行聚类，GPT-4o mini 可能产生幻觉或对仓库描述的曲解，虽然综合了 README + about + topics 三个来源，但仍无法完全避免生成摘要的偏差。
- **时效性问题**：LLM 服务领域快速演进，数据采集截至某时间点（GitHub 数据统计到 2025 年 11 月），随着新框架（如 AIBrix）和框架新功能的发布，结论可能很快过时；论文本身发布时间标注为 2026 年，也可能存在出版延迟带来的时效性偏差。
