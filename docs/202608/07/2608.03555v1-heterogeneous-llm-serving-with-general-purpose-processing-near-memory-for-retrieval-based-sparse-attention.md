## 摘要
本文提出了一种异构解码阶段服务系统，将KV缓存从GPU内存中移出，其动机是近期前沿LLM采用基于检索的稀疏注意力来服务百万级token上下文。它按操作类型划分解码步骤：GPU节点持有模型权重并执行投影和MoE层，而近内存处理（PNM）节点持有KV缓存和索引键，并执行所有读取它们的操作。我们首先表明，先前PIM和PNM设计背后的假设对这些操作不再成立，并推导出此类节点的四个设计要求。基于这些要求，我们提出了KARAT（用于基于检索的注意力的KV缓存驻留加速器），这是一种通用PNM设计，是满足所有四个要求的设计点。KARAT设备将大容量LPDDR容量与为检索索引器定制的通用计算相结合，提供了超出为低强度GEMV构建的PIM/PNM设计所针对的操作强度，同时适应了固定功能单元无法支持的多样化稀疏注意力算法，因为这些算法在不断发展。为减少两种设备类型在微批次之间交替时的流水线气泡，我们进一步提出了机会主义的细粒度微批次调度（OFMS），将专家全对全通信隐藏在其他微批次的GEMM后面，以及上下文长度感知的微批次再平衡（CMR），尽管上下文长度存在差异，仍能均衡其token数量。在三个最先进的模型和真实代理轨迹上，我们提出的系统在服务水平目标下将每TDP吞吐量提高了2.09-6.13倍（相对于仅GPU基线），并以1.36-3.21倍的改进运行免训练的稀疏注意力方法。

## Abstract
This paper presents a heterogeneous decode-phase serving system that relocates the KV cache out of GPU memory, motivated by the retrieval-based sparse attention that recent frontier LLMs adopt to serve million-token contexts. It partitions a decode step by operation type: GPU nodes hold the model weights and execute the projections and MoE layers, while processing-near-memory (PNM) nodes hold the KV cache and index keys and execute every operation that reads them. We first show that the assumptions behind prior PIM and PNM designs no longer hold for these operations, and derive four design requirements for such a node. From these requirements, we propose KARAT (KV-cache-resident Accelerator for Retrieval-based ATtention), a general-purpose PNM design that is the design point meeting all four. A KARAT device combines large LPDDR capacity with general-purpose compute sized for the retrieval indexer, serving an operational intensity beyond what PIM/PNM designs built for low-intensity GEMV target while accommodating diverse sparse attention algorithms that fixed-function units cannot support as they evolve. To reduce pipeline bubbles as the two device types alternate between micro-batches, we further propose opportunistic, fine-grained micro-batch scheduling (OFMS), which hides expert all-to-all behind the other micro-batch's GEMMs, and context-length-aware micro-batch rebalancing (CMR), which equalizes their token counts despite the variance in context length. Across three state-of-the-art models and real agentic traces, our proposed system improves throughput per TDP under a service-level objective by 2.09-6.13x over a GPU-only baseline and runs training-free sparse attention methods with 1.36-3.21x improvements.

## 1. 论文核心问题与整体含义（研究动机和背景）

- **背景**：前沿 LLM（如 GLM-5.2、MiniMax-M3、DeepSeek-V3.2）开始采用**检索式稀疏注意力**来服务百万级 token 的长上下文。该方法在每步解码时，通过索引器（indexer）对整个上下文的索引键打分、选出 top-k  token，再仅对该子集做注意力计算，从而将注意力的内存读取量从 O(L) 降为 O(k)。
- **核心瓶颈**：尽管稀疏注意力降低了**激活**的数据量（每步读取量），但完整 KV 缓存与索引键仍然必须**驻留**在内存中。实测显示：单个百万 token 请求的 KV 缓存与索引键即占 78–137 GB，而一张 8-GPU 节点仅有 1.1–1.4 TB HBM，还需容纳数百亿参数的 MoE 权重，导致可并发服务的请求数极少，吞吐量受限于内存容量而非算力。
- **现有方案的不足**：
  - 将 KV 缓存卸载到主机/ CXL 内存（如 HiSparse、Mooncake）虽然扩容，但 O(L) 的索引扫描和 gather 仍需跨带宽受限的链路访问，瓶颈未消除。
  - 现有 PIM/PNM 设计（如 Duplex、AttAcc、SPNM）虽将计算移到内存旁，但均假设低操作强度（OI）和固定的密集注意力形式（MHA/GQA）；检索式稀疏注意力的 OI 更高（4–128 FLOPs/byte），且算法形式多样、快速演进，专用单元无法覆盖。
- **论文提出的整体思路**：按操作类型进行异构分区——GPU 持有权重、执行投影和 MoE；提出 **KARAT** 通用 PNM 节点，持有 KV 缓存与索引键，并执行所有读取它们的操作（索引扫描、gather、attention），从而在高容量、高带宽/瓦的同时，保证通用可编程性以支持算法演进。

## 2. 论文提出的方法论

### 2.1 核心设计思想
- **操作类型分区**：解码步骤被划分为 GPU 端（QKV 投影、输出投影、MoE 层）与 KARAT 端（INDEX-BUILD、SCORE、SELECT、GATHER、ATTEND）两类，二者通过微批次流水线交替执行。
- **KARAT 设备**：采用 LPDDR5X 内存（512 GB、1.2 TB/s、175 W TDP），配合 18 个 GPNM 通用核心（约 250 TFLOPS FP8 / 125 TFLOPS BF16），其 ridge point（208 FLOPs/byte）高于检索索引器的 OI 范围（4–128），避免计算成为瓶颈。
- **四个设计要求**：
  - R1（容量）：容量/瓦比 HBM 高一个数量级；
  - R2（带宽）：带宽/瓦与 HBM 相当，且与索引键共置；
  - R3（计算）：ridge point 高于索引器扫描的 OI；
  - R4（通用性）：核心可编程，覆盖多样化的稀疏注意力算法。
- **KV 放置**：每个请求的上下文固定在单一 KARAT 设备上（请求级数据并行），使 SCORE 到 ATTEND 全部在本地完成，避免跨设备 gather 流量。

### 2.2 关键技术细节
- **执行流程**：GPU 先构建索引器 Q/K 并发送给 KARAT → KARAT 执行 SCORE→SELECT→GATHER→ATTEND → 返回注意力输出 → GPU 执行输出投影和 MoE（含专家 all-to-all）。
- **OFMS（机会主义细粒度微批次调度）**：在 GPU 处于 MoE 通信等待时，若另一微批次的注意力输出已就绪，则提前启动其输出投影、dispatch 等操作，将专家 all-to-all 隐藏在其他微批次的 GEMM 后面；仅在依赖允许时重排，否则回退到静态顺序，不劣于基线。
- **CMR（上下文长度感知微批次再平衡）**：每当请求完成或新请求到达时，按上下文长度降序将各 KARAT 设备上的请求重新分配到两个微批次，使二者在各设备上的聚合上下文长度（token 数）尽量均衡；算法复杂度低（每设备一次排序），且不移动 KV 数据。

### 2.3 系统级方法
- 采用 prefill–decode 分离架构，prefill 在独立 GPU 池完成，仅新 prefill token 的 KV 需传输到 KARAT 节点。
- 通过工作量感知的系统配置搜索（§III-G），在等功率约束下，遍历 GPU/KARAT 节点配比、MoE 专家并行度和注意力张量并行度的组合，最大化满足 SLO 的吞吐量。

## 6. 论文的主要结论与发现

- **模型原生稀疏注意力**：KARAT 在所有模型与轨迹上取得最高吞吐/TDP，较 GPU-only 提升 **2.09–6.13×**（几何均值 2.23×）；增益来源是释放 GPU HBM 后并发会话数大幅增加（如 KVCT 上从约 253–339 提升到 4,017–5,055）。
- **训练免费稀疏注意力**：KARAT 无需硬件改动即可支持全部三种 SELECT 变体，提升 **1.36–3.21×**；MagicPIG 场景增益最大（2.09–3.21×），因为 SPNM 完全无法执行 LSH 选择。
- **与现有方案对比**：KARAT 优于 HiSparse（1.14–2.18×）、Duplex（1.61–4.83×）、AttAcc（2.46–9.03×，仅 MiniMax-M3）。SPNM 虽具同等 LPDDR 容量，但因计算能力不足（8 TFLOPS）在 OI 64/128 的索引器上严重受限，甚至低于 GPU-only，证明仅有容量不够，还需匹配的计算强度。
- **调度优化的贡献**：禁用 OFMS 平均降低吞吐 16%（DeepSeek-V3.2 + KVCT 达 33%）；禁用 CMR 平均降 5%（最差 21%）；二者共同提升 GPU/KARAT 利用率。
- **系统设计空间**：引入 KARAT 后，最优 EP 度从 64 降至 16–32（减少 all-to-all 开销）；随着上下文长度增加，最优 GPU/KARAT 配比向更多 KARAT 设备偏移。
- **鲁棒性**：链路带宽减半损失 ≤4%，带宽降低至 1/4 损失 8–32%；延迟增加 100× 损失 ≤6%；核心数从 18 减至 10 损失 27%，增至 26 仅增益 3.8%，证明 18 核配置接近最优。

## 7. 优点

- **问题定位准确**：基于真实 agentic 负载（99 百分位上下文达 198K–791K、94–97% 前缀复用）和三个前沿模型的具体架构特征（表 II），从容量、带宽、计算、通用性四个维度系统性地推导设计需求，逻辑严密。
- **修正了 PIM/PNM 领域的关键假设**：明确指出检索式稀疏注意力的 OI（4–128）显著高于传统 dense GEMV（<10），且算法形式快速演化，因此固定功能单元不再适用；KARAT 的通用 GPNM 设计是解决该问题的正确设计点。
- **软硬件协同完整**：不只提出硬件，还配套了 OFMS 和 CMR 两个调度/再平衡机制，解决了异构流水线气泡问题；且调度是去中心化、可回退的，部署成本低。
- **评估严谨**：等功率对比、SLO 约束统一口径、对基线采取有利假设、包含消融与敏感性分析、提供设计空间搜索，体现了较高的工程严谨性。
- **可演进性**：由于计算是通用可编程的，KARAT 可支持未来新出现的稀疏注意力算法，不随算法代际更替而失效。

## 8. 不足与局限

- **缺乏真实硬件原型**：KARAT 设备本身是设计提案，评估完全依赖模拟器（虽用 H200 MIG 建模），未经过硅验证或 FPGA 原型验证；实际面积（286 mm²）和功耗（175 W）估算存在不确定性。
- **模拟器依赖假设**：MoE 路由默认采用均匀采样，仅在一组偏斜实验中使用真实分布；GPU/KARAT 间通信延迟和带宽假设来自公开文献（CXL 600 ns 往返），与实际部署环境可能偏差。
- **对比基线范围有限**：未与更新的 CXL 池化方案（如 POND、Beluga、Tract 等）直接对比，也未与 Megascale-Infer 等层分发式系统对比；仅对比了 2024–2025 年的代表性 PIM/PNM 方案。
- **评估规模有限**：所有实验在 8 节点（44.8 kW）规模进行，未验证万卡级超大规模集群的可扩展性。
- **动态性处理简化**：KV 缓存每请求固定在单一 KARAT 设备上，若个别设备被“热点”请求占满，文中说明“在我们的评估中不会发生”，但未给出极端不均衡请求分布下的鲁棒性验证。
- **SLO 定义单一**：仅采用 P99 TBT ≤ 100 ms，未覆盖更严格或更多样的 QoS 目标（如 tail token 延迟、首 token 延迟、多优先级混合负载）。
- **训练免费方法评估不完整**：仅测试了 Quest、STARC、MagicPIG 三种，且 MagicPIG 使用了 GPU 版本而非其原生的 CPU 实现（作者说明 GPU 在该规模下更快，但仍可能影响对比公平性）。
- **数据与可复现性**：部分真实 agentic 轨迹（如 SWE-chat、KVCT）来自非正式来源（GitHub 仓库、预印本），且论文未公开完整模拟器与配置，第三方复现存在门槛。
