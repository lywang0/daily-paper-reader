## 摘要
我们推出PTXBench，一个用于评估和适配大语言模型使用架构特定PTX进行GPU内核优化的基准测试。PTXBench衡量功能正确性、所选目标指令是否在运行时执行，以及在H100和B200 GPU上针对GEMM和注意力工作负载相较于前沿库的加速效果。我们的评估表明，架构特定PTX能力仍不均衡：在复杂的注意力反向传播工作负载上，成功率大幅下降，且执行目标指令并不必然带来具有竞争力的性能。在整套测试中，没有评估模型能持续匹配前沿库。我们进一步使用监督微调适配了Qwen3.6-27B。基于修复条件的训练改善了几项任务，但泛化能力仍不均衡；除数据集规模外，数据覆盖、平衡以及推理教师模型的质量同样重要。PTXBench为衡量和提升大语言模型利用不断演进的GPU架构的能力，提供了一个可审计的测试平台。

## Abstract
We introduce PTXBench, a benchmark for evaluating and adapting large language models (LLMs) to use architecture-specific PTX for GPU kernel optimization. PTXBench measures functional correctness, whether selected target instructions execute at runtime, and speedup over frontier libraries across GEMM and attention workloads on H100 and B200 GPUs. Our evaluation shows that architecture-specific PTX capability remains uneven: success rates fall substantially on complex attention backward workloads, and executing the target instructions does not necessarily translate into competitive performance. No evaluated model consistently matches frontier libraries across the suite. We further adapt Qwen3.6-27B using supervised fine-tuning. Repair-conditioned training improves several tasks, but generalization remains uneven; data coverage, balance, and the quality of the reasoning teacher matter in addition to dataset size. PTXBench provides an auditable testbed for measuring and improving LLMs' ability to exploit evolving GPU architectures.

## 1. 核心问题与整体含义（研究动机和背景）

- **背景**：GPU 内核优化高度依赖 PTX（Parallel Thread Execution），尤其是 NVIDIA 新一代架构（如 Hopper、Blackwell）引入了大量架构特定的 PTX 指令（如张量核、异步内存、同步机制等）。通用 CUDA 代码虽然功能正确，但往往无法充分利用新硬件特性。
- **问题**：大语言模型（LLM）能否直接编写使用架构特定 PTX 的 CUDA 内核？能否通过后训练（post-training）提升这种能力？现有 GPU 内核基准（如 KernelBench）主要衡量端到端正确性和加速比，但没有区分性能是否来自架构特定指令、通用 CUDA 或现有厂商库，因此无法隔离模型对底层架构机制的编程能力。
- **本文含义**：提出 PTXBench，一个受控的、可审计的基准测试与适配环境，用于独立衡量 LLM 在功能正确性、目标指令实际执行情况、以及相对前沿库的加速性能三个维度上的表现，并基于该环境研究针对架构特定 PTX 的后训练方法。

## 2. 方法论

- **核心思想**：将“架构特定能力的探测”与“问题收集”分离。每个基准实例由参考算子（cuBLAS、cuDNN、FlashInfer 等）+ 固定工作负载 + 目标 GPU 架构 + 指定 PTX 指令族组成，要求模型从零生成带内联 PTX 的 CUDA 内核（CUDA–PTX），并禁止调用现有厂商库。
- **受控上下文（Architecture-specific Knowledge Pack）**：为避免模型仅靠文档检索，每个任务提供统一的知识包，包括架构参数、PTX 指令的 C++ 包装、布局/同步/内存一致性契约，以及经验证的调度原则（如 FlashAttention 修正后的伪代码）。知识包约 20k–30k token。
- **多轮评估协议（MiniPTXAgent）**：
  - 每轮轨迹最多 8 次模型调用，保留之前的生成历史和执行反馈。
  - 候选内核先用 nvcc 编译，编译成功的送入隔离的 profiling 服务进行内存安全检查、错误信息、功能评估和延迟测量。
  - 功能正确性：验证输出形状、类型，并用 `torch.allclose`（atol=rtol=1e-2）比较。
  - 性能：用 CUPTI 测量，每次试验取 10 次 warmup + 50 次计时迭代的中位数，加速比 = 参考库延迟 / 候选延迟。
- **目标指令执行验证**：
  - Hopper 选择 GMMA 计算或 UTMA 载荷移动；Blackwell 选择 TCGEN05 张量路径（TMA 不算，因为 Blackwell 继承自 Hopper）。
  - 首先通过 `cuobjdump --dump-sass` 静态检查 SASS 中是否存在匹配指令族；如果存在，再用 NVIDIA Nsight Compute (NCU) 动态检查谓词启用的线程计数是否为正，以排除死代码或未启动代码。
  - 目标指令正确性 = 功能正确 + 在运行时实际执行了目标指令。
- **适应性训练方法 Fixit**：
  - 从待适配模型 π₀ 出发，采样失败内核 k⁻，收集编译/执行反馈 e。
  - 用修复教师 π_R（更强模型）生成修复后的内核 k⁺，仅保留通过正确性检查的修复。
  - 用推理教师 π_T 生成从失败到修复的推理过程 r。
  - 学生模型以 `(x, k⁻, e)` 为输入，以 `(r, k⁺)` 为监督进行微调（SFT）。

## 3. 实验设计

- **评估模型**：
  - 闭源/开源共 4 个：Gemini 3.1 Pro、Claude Opus 4.8、GLM-5.2、Qwen3.6-27B。
- **硬件与工作负载**：
  - GPU：NVIDIA H100 80GB（Hopper）和 B200（Blackwell）。
  - 工作负载：BF16 的 GEMM（C = ABᵀ）和四种注意力变体：MHA 前向（非因果/因果）、MHA 反向（非因果/因果）。主要工作负载：batch=4，48 头，序列长度 4096，头维度 128。另有泛化测试：d64、d96、GQA（ragged/paged）等。
  - 性能基线：GEMM 用 cuBLAS，非 GQA 注意力用 cuDNN，GQA 用 FlashInfer。
- **对比方法**：
  - 主要对比四个模型在 H100/B200 上的四项指标：正确率、目标指令正确率、最好加速比、以及 Fast_p / Fast Inst._p 分布。
  - 额外对比：同一模型生成 Triton 内核与 CUDA–PTX 内核的性能差异；知识包消融（仅架构参数、加入模板函数、再加入架构契约）。
  - 微调实验：基于 Qwen3.6-27B，用 Gemini 3.1 Pro 作为修复教师，GLM-5.2 或 Qwen 自身作为推理教师，构造 7 种数据配方（s0–s6），包括 KernelGen 直接解和监督，以及 Fixit 修复条件监督，并比较数据覆盖、平衡、推理教师等影响。
  - 进一步测试：s1 模型在 held-out 形状（d64、d96、GEMM）和 GQA 上的迁移；跨语言迁移（CUDA-PTX → Triton）；以及 SFT 与提示词级监督（专家指导、检索修复经验）的对比。

## 6. 主要结论与发现

- **架构特定 PTX 能力不均衡**：模型在前向注意力上成功率相对较高，但在注意力反向传播上显著下滑；即使执行了目标指令，也不一定达到有竞争力的性能。没有模型能在整个测试套件上持续匹配前沿库。
  - 例如 Claude Opus 4.8 在 Blackwell GEMM 上达到 1.012×cuBLAS，但在 Blackwell 注意力反向传播上最佳仅 0.149×。
- **前沿模型差距依然明显**：Gemini 3.1 Pro 虽知识截止与 Blackwell PTX 同期，但 GEMM 性能仍低于 cuBLAS；Claude 表现更好，但两者对 Blackwell 注意力的优化均不如 Hopper。
- **知识包的作用**：没有显式 PTX 知识时，模型几乎不使用目标指令；加入模板函数后目标指令出现，再加入架构契约后正确率显著提升（达到 38.5% 目标指令正确率），但峰值速度与正确率顺序不同。
- **修复条件监督（Fixit）效果混合**：与直接监督（KernelGen）相比，Fixit 在部分任务上提升正确率，但并非全面占优；在 MHA-Fwd 和 MHA-Bwd-Causal 上反而落后。数据覆盖和平衡比单纯扩大数据量更重要，推理教师质量也至关重要（GLM-5.2 作为教师明显优于用 Qwen 自身）。
- **泛化有限**：s1 模型能迁移到 GEMM 和部分 d64/d96 前向任务，但 d96 反向注意力几乎失败，GQA 完全不行；跨语言迁移到 Triton 时，正确率普遍下降，但峰值速度在因果注意力上大幅提升。
- **SFT 优于提示词级监督**：即使有专家编辑的指导，基础模型仍然不能生成正确的 MHA 内核；而 SFT 后的 s1 模型在无专家指导下就能做到。检索修复经验若只给笔记无效，必须同时提供修复后的内核。
- **高层语言在新架构上仍有价值**：在 Blackwell 上，Triton 生成的注意力和反向传播内核明显优于直接生成的 CUDA-PTX，但在 Hopper 上两者差距较小。

## 7. 优点

- **受控能力探测**：PTXBench 将目标指令执行与端到端性能分开测量，能准确判断模型是否真正使用了指定的架构机制，避免“调用现成库”或“只用通用 CUDA”的混淆。
- **动态执行验证**：用 NCU 检测真实运行时的指令执行计数，排除静态存在但实际未运行的指令，保证指标可信。
- **多轮 agent 评估**：模拟实际内核开发流程，保留编译/运行反馈和修复过程，评估更贴近真实使用。
- **可审计性**：保留原始 SASS、NCU 计数、源代码和 cubin 哈希，支持事后核查；对未定义行为（如 use-after-free）的情况采用保守处理。
- **数据与训练方案分离**：基于 FlashInfer-Trace 统一 schema，容易扩展到其他任务集合（如 SOL-ExecBench）。
- **受控消融设计**：训练配方对问题覆盖、数据平衡、推理教师分别做隔离对比，为后续研究提供清晰参考。
- **实践意义明确**：展示了“修复条件训练”在特定架构 PTX 编程中的潜力和局限，并指出数据质量比数量更重要。

## 8. 不足与局限

- **训练规模有限**：仅使用 Qwen3.6-27B 一个基座模型、LoRA 适配（rank 32）、小规模数据集，结论是否能推广到更大模型或工业级全参数训练未知。
- **工作负载覆盖面窄**：只涉及 BF16 GEMM 和注意力（H100/B200），未涵盖融合算子、非矩阵乘算子、量化、稀疏性等更广泛的 GPU 工作类型。
- **实验数组不够充分**：每条轨迹只取 32 个 turn（N=32），对于慢速 workload 可能方差较大；微调实验没有报告多次种子或重复运行的结果。
- **目标指令定义范围有限**：Blackwell 的 UTC* 匹配涵盖控制指令，作者也承认不能精确表达“第五代 MMA 做了有用工作”；Hopper 排除了 TMA 缓存控制指令。
- **依赖前沿库作为参考**：cuBLAS/cuDNN 等库可能并未针对特定 workload 完全调优，加速比上下界可能有偏差。
- **评测成本高**：需要真实 GPU 执行、NCU 动态分析、多轮调用，评估速度慢，难以大规模扩展。
- **提示词知识包较长**（20k–30k token），对上下文窗口较小或推理成本敏感的模型不友好；且知识包的构造需要大量人工验证（如修正 FlashAttention-3 伪代码）。
- **未明确报告计算资源**，不利于复现和评估训练成本。
