## 摘要
LLM服务系统按峰值负载进行配置以满足严格的延迟目标，当流量低于峰值时，大量GPU计算资源处于空闲状态。我们提出了DeltaServe，一种与主机无关的协同服务设计，它将这种空闲的推理能力转化为LoRA微调吞吐量，同时保持推理服务级别目标（SLO）。DeltaServe通过一个紧凑的钩子接口与现有推理引擎集成，该接口仅需要支持多LoRA批处理。它利用了推理预填充和LoRA微调前向传播的共享执行结构，并使用一个感知SLO的调度器，仅在推理余量充足时才准入和执行微调任务。该调度器由一个感知CUDA图的延迟模型驱动，该模型离线校准并在线优化。我们将DeltaServe与vLLM、SGLang和S-LoRA集成。在来自X公司的生产流量追踪上，vLLM上的DeltaServe比LLMStation提供了2.9倍更高的微调吞吐量，同时实现了100%的推理SLO合规率，而LLMStation为85%。此外，与运行vLLM+torchtune的基线相比，它实现了39%更高的微调吞吐量，且无需额外硬件并保持完全SLO合规。

## Abstract
LLM serving systems are provisioned for peak load to meet strict latency targets, leaving substantial GPU compute idle whenever traffic falls below peak. We present DeltaServe, a host-agnostic co-serving design that converts this idle inference capacity into LoRA fine-tuning throughput while preserving inference service-level objectives (SLOs). DeltaServe integrates with existing inference engines through a compact hook interface that requires only multi-LoRA batching support. It exploits the shared execution structure of inference prefill and LoRA fine-tuning forward passes, and uses an SLO-aware scheduler to admit and execute fine-tuning only when sufficient inference headroom is available. The scheduler is driven by a CUDA-graph-aware latency model calibrated offline and refined online. We integrate DeltaServe with vLLM, SGLang, and S-LoRA. On a production trace from Company X, DeltaServe on vLLM delivers 2.9x higher fine-tuning throughput than LLMStation at 100% inference SLO compliance, versus 85% for LLMStation. It also achieves 39% higher fine-tuning throughput than a baseline running vLLM+torchtune, using no additional hardware and maintaining full SLO compliance.

# DeltaServe 论文详细总结

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：生产环境中的 LLM 推理系统按峰值负载配置 GPU 资源，当流量低于峰值时，大量 GPU 算力处于闲置状态。例如，论文中 Nutanix 的生产负载追踪显示，平均约 40% 的 GPU 能力未被利用。
- **希望利用闲置算力的场景**：持续模型适配（continual model adaptation）、新数据注入、适配器变体评估、多租户/多产品定制等需要独立 GPU 的 LoRA 微调任务。
- **现有方案不足**：
  - 传统推理优化（如 Splitwise 的 prefill/decode 分离、Orca 的连续批处理）无法恢复请求流低于峰值时闲置的 GPU 周期。
  - 时间切片和空间分区（MIG/MPS）粒度过粗，无法跟踪亚秒级推理负载波动。
  - 独立分配 GPU 给微调会造成训练与推理之间的资源竞争权衡。
- **论文主张**：将 LoRA 微调前向计算与推理 prefill 的结构一致性作为基础，将空闲推理能力转化为有价值的高吞吐微调资源，在不违反推理 SLO 的前提下实现协同服务。

## 2. 论文提出的方法论：核心思想、关键技术细节、公式或算法流程

### 2.1 核心思想
- **结构同源性**：LoRA 微调的前向传播与推理 prefill 结构相同，只是微调需保存激活。因此可将微调样本作为"单步、仅 prefill"请求注入推理批处理，共享基座模型权重、内核和内存。
- **宿主无关设计**：DeltaServe 将协同服务机制封装在紧凑的钩子接口后，仅要求宿主引擎支持多 LoRA 批处理（multi-LoRA batching）。核心逻辑（SLO 延迟模型、准入策略、解耦后向执行器）与具体推理引擎无关。

### 2.2 四大核心组件
1. **微调管理器（Fine-tuning Manager）**：加载/分词微调语料、排序候选样本、跟踪 epoch 进度，位于宿主引擎客户端请求路径之外。
2. **DeltaServe 调度器（DeltaServe Scheduler）**：拦截宿主调度循环，在宿主形成新批处理前检查批组成、用延迟模型估算执行代价，在 SLO 允许范围内准入尽可能多的微调样本。
3. **推理引擎钩子（Inference-Engine Hooks）**：轻量插入宿主前向路径和引擎循环；模型级激活钩子将微调反向传播所需激活保存到共享 GPU 内存中，并记录每步执行时间用于在线精化延迟模型。
4. **后向子进程（Backward Subprocess）**：在独立 GPU 子进程（CUDA MPS 控制下）中执行梯度计算和适配器权重更新，与宿主前向引擎分离以减少启动路径竞争。

### 2.3 关键技术细节

#### 延迟模型——分阶段拟合公式
- **公式（I）——混合批处理（prefill + decode + 微调）**：
  $$T \approx \alpha \sum_i (n_i + B_d)^2 + \beta (T_{in} + B_d) + \gamma T_{ft} + \varepsilon K + c$$
  - $\alpha$ 定价自注意力计算（二次项，随 prefill 序列长度与 decode 查询数量变化）
  - $\beta$ 定价前馈网络计算
  - $\gamma$ 捕获保存微调激活的代价
  - $\varepsilon$ 定价 decode 请求的 KV 缓存内存访问
  - $c$ 为每步固定开销
- **公式（II）——纯 decode 步骤**：
  $$T \approx \beta' B_d + \varepsilon' K + c'$$
  - 仅含 decode 时，prefill 和微调项消失。
- **执行模式感知**：同一批处理在 CUDA graph 回放模式下与 eager 模式下延迟可相差近一个数量级。DeltaServe 为公式（I）中图执行和 eager 执行各拟合一组系数，预测时根据宿主自身的图/eager 选择使用对应系数。微调激活钩子无法在图回放中使用，因此混合批处理强制走 eager 模式。

#### 准入调度算法（Algorithm 1）流程
- 前置条件检查：后向子进程运行中、激活缓冲区满、微调池为空、或宿主不支持混合批处理且当前仅 decode 时，拒绝准入。
- 计算可用延迟预算 $\Delta$：取 TTFT 余量与 TPOT 余量的较紧者。TTFT 余量按 $\Delta_{budget} = T_{SLO} - (t_{now} - t_{arrival})$ 计算；TPOT 余量等于 TPOT 目标减去本步延迟的 decode 成本。
- 先验证纯推理批处理是否已超预算；若否，则按 token 长度升序贪心准入微调样本，直到触发延迟预算或激活缓冲区容量上限。
- 准入后保留缓冲区空间并从微调池中移除样本，防止重复选择。

#### 后向执行与抢占
- 后向子进程在每层 transformer 边界检查共享 GPU 授权标志；prefill 到达时清标志，后向在最多一层内让步；decode 过程中可继续执行后向。
- 微调前向中断：当推理请求在纯微调步骤期间到达时，激活钩子检测到每层边界的中断信号，丢弃部分激活、将中断样本退回微调池，并立即调度推理。

## 6. 论文的主要结论与发现

1. **端到端效果（4×A100 + Nutanix 生产追踪）**：

2. **Burst-light**：DeltaServe-vLLM 微调吞吐 1797 tok/s，是 LLMStation 的 3.5 倍，比 split-pool 高 77%；平均延迟仅比基线高 22%（LLMStation 高 68%）。
3. **Burst-dense**：LLMStation 仅 83.3% SLO 合规，而 DeltaServe-vLLM 保持 100%；微调吞吐为 LLMStation 的 2.6 倍。
4. **跨引擎可移植性**：SGLang 上微调吞吐 972 tok/s（100% SLO 合规），S-LoRA 上 484 tok/s（100% SLO 合规），证明核心设计不依赖特定引擎架构。
5. **消融结果**：
   - 前向批共置使微调吞吐从 507 提升至 934 tok/s（+84%）。
   - 层边界中断机制将 5% 尾部延迟增幅从 27.8% 降至 8.1%，仅损失 2% 微调吞吐。

## 7. 优点

- **宿主无关的通用设计**：将协同服务逻辑（延迟模型、准入策略、后向执行器）与具体引擎解耦，仅需多 LoRA 批处理能力，降低了在真实生产引擎中落地的门槛。
- **CUDA 图感知延迟模型**：显式区分图回放和 eager 执行模式，避免了现有系统（如 LLMStation 延迟缓存）忽略该区别导致的预测偏差。
- **全阶段协同**：可在预填充和 decode 阶段灵活准入微调，而非像 LLMStation 仅限 decode 阶段，能更充分地利用推理余量。
- **细粒度抢占机制**：后向在层边界让步、前向在中断信号处中止，以一层计算为粒度权衡延迟敏感性与训练吞吐，设计精巧。对推理尾延迟保护明显。
- **多引擎验证**：在 vLLM、SGLang、S-LoRA 三种架构差异显著的引擎上验证了可移植性，增强了结论的普适性。

## 8. 不足与局限

- **模型规模覆盖单一**：仅评估 Llama 3-8B 一个模型；未覆盖更大模型（如 70B 及以上），其预填充/解码资源特征可能不同。
