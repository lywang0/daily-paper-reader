## 摘要
大语言模型（LLM）工作负载促使多分区GPU成为扩展计算和内存容量的途径，但其非均匀内存访问特性和分区间的通信可能加剧竞争并损害局部性，导致内核延迟次优。为解决此问题，我们分析了覆盖最先进服务引擎的权重投影、混合专家和注意力变体的性能关键型LLM内核实现，以呈现多分区GPU中数据访问模式的特征。首先，我们引入内存迹线分析方法来推导工作组级的数据访问和共享行为，然后使用周期级模拟器评估延迟的局部性影响。利用这些工具，我们将LLM内核操作数归类为三种工作组间共享模式（全局、部分或私有），并表明所需的优化策略因类别而异，从简单的工作组固定到子组感知的协同调度。我们的发现强调了在多分区GPU中需要位置感知的内核编程以及更智能的工作和数据局部性架构支持。

## Abstract
Large language model (LLM) workloads motivate multi-partition GPUs as a path to scaling compute and memory capacity, but their non-uniform memory access characteristics and inter-partition communication can amplify contention and degrade locality, leading to suboptimal kernel latency. To address this, we analyze performance-critical LLM kernel implementations spanning weight projection, mixture-of-experts, and attention variants of state-of-the-art serving engines to present a characterization of data access patterns in multi-partition GPUs. First, we introduce memory trace analysis methodology to derive workgroup-level data access and sharing behavior, then evaluate the locality implications on latency using a cycle-level simulator. Using these tools, we categorize LLM kernel operands into three inter-workgroup sharing patterns (global, partial, or private) and show that the required optimization strategies differ across categories, from simple per-workgroup pinning to subgroup-aware co-scheduling. Our findings highlight the need for placement-aware kernel programming and smarter architectural support for work and data locality in multi-partition GPUs.

- **背景**：LLM 模型规模（如 DeepSeek、Gemma、Qwen）已扩展到数千亿参数，长上下文推理使 KV 缓存远超单内存栈可高效服务的范围。GPU 厂商（如 AMD MI300X、NVIDIA B200）转向**多分区（multi-partition）**架构，将多个计算与内存域封装在同一 package 内，以同时扩展算力和容量。
- **核心问题**：多分区 GPU 具有**非均匀内存访问（NUMA）**特性——工作组（workgroup）访问远程分区内存时需穿越片上互连，产生更高延迟与带宽竞争。然而 GPU MMU 只暴露统一虚拟地址空间，导致内核开发者和运行时无法显式控制数据物理放置位置，于是原本在单芯片 GPU 上良性的访问模式（共享权重、激活、KV 缓存等）在分区场景下会静默变成跨分区流量，造成性能退化。
- **研究目标**：系统刻画 LLM 服务内核（权重投影、注意力变体、MoE）在多分区 NUMA GPU 上的内存访问模式，量化跨分区访问的延迟代价，并探讨内核编程实践与架构支持如何缩小这一性能差距。

# 论文提出的方法论

## 核心思想

- 以**工作组（workgroup，即 threadblock）粒度**分析内存访问与数据共享行为，因为工作组是 GPU 调度和放置的基本单元。
- 通过**内存迹线（memory trace）分析**从真实内核执行中提取工作组级访存模式，再结合**周期级模拟器**量化 NUMA 效应带来的延迟开销。

## 关键技术细节

1. **内存迹线生成**：使用 AMD Omniprobe 在应用层收集虚拟地址空间的内核内存访问迹线（含内核名、dispatch ID、工作组坐标、波前号、操作类型、逐 lane 地址列表）。
2. **地址过滤与内核/工作组选择**：过滤非全局内存地址，枚举目标 dispatch 的所有工作组，支持单工作组分析。
3. **步长（stride）检测与分段**：
   - 先检测每个 lane 的主步长；
   - 对每个迹线条目内的连续地址，按步长一致性分割成多个 stride-consistent 子序列；
   - 零地址差表示广播访问，单独计数。
4. **Chunk 形成与合并**：将每个 stride 一致的段转换为字节区间 [s, e)，并将连续或间隙小于容差 δ 的区间合并，得到紧凑的“内存 chunk”集合。
5. **工作组间共享分析**：对所有工作组的 chunk 集合两两计算字节级重叠，定义 read/write reuse 量，用于判断数据共享程度和潜在的跨分区竞争。

## 工作组间共享模式分类

论文将 LLM 内核操作数分为三类：

- **WG-Private（私有）**：每个工作组访问互不重叠的数据区域，零共享，最利于放置优化（可 100% 局部化）。
- **Global Shared（全局共享）**：所有工作组访问整个数据结构，如激活向量，需 N 路复制才能达到高局部性。
- **Partial Sharing（部分共享）**：工作组形成子组，子组内共享同一数据切片，子组间不共享。如 GQA 中一组 query 头共享同一 KV 头，MoE 中多个专家工作组共享路由激活。

## Partition Locality 度量

定义了 **Partition Locality**：
\[
\text{Partition Locality}(O, \pi, \sigma) = \frac{\#local\_accesses}{\#local\_accesses + \#remote\_accesses}
\]
由三个因素决定：
- 内核访问足迹（固定）；
- 页放置策略 π（如 4KB 轮转交织）；
- 工作组调度策略 σ（如按 WG id 取模分发到分区）。

默认策略下（页级轮转 + WG 轮转），任何大足迹操作数的局部性均近似收敛到 \(1/N\)（对 4 分区即约 0.25）。不同类别的可达性上限不同：私有类可达 1.0（无复制）；全局共享需 N 倍内存复制；部分共享需将共享子组协同调度到同一分区。

# 主要结论与发现

1. **NUMA 代价差异巨大**：理想放置相对默认放置的加速比从 1.05×（MoE 共享路由）到 1.79×（GQA decode）不等；计算密集型 FA prefill 只有 1.09×，访存密集型 decode 类内核收益明显。
2. **共享模式决定优化策略**：
   - **WG-private**（权重投影、MHA decode）：只需简单的 per-WG 页固定（pinning）即可达到近乎 100% 局部性。
   - **部分共享**（GQA、MLA、MoE）：需要子组感知协同调度（如将共享同一 KV 头的 G 个 WG 放在同分区），并对子组共享数据做放置。MoE 还需动态、逐 batch 的激活放置。
   - **全局共享**（激活向量）：跨度小或可复制时代价低（如 128 KB），但若巨大则需 N 路复制。
3. **跨内核数据复用被忽视**：MLA 的 Stage1/Stage2 存在 producer–consumer 跨内核依赖，分区感知调度可利用 L2 复用，说明调度不仅要考虑内内核共享，还要考虑跨内核关系。
4. **架构需求**：
   - 需要更细粒度的数据交织（如 CLAP 可避免粗粒度大页错放）；
   - 需要显式的工作组调度粒度控制（如 MGvm/LADM 协同放置）；
   - 编程模型层面需要暴露放置机制（如 AMD CPX/NPS4 模式），但代价是失去统一地址空间。
5. **统一结论**：当前运行时无法充分利用多分区 GPU 的容量优势，必须发展**放置感知的内核编程**与**架构级局部性支持**。

# 不足与局限

- **模拟而非真实系统评估**：理想配置假定零互连延迟，未实现真实运行时优化，因此得到的“可达到速度提升”是理论上界。
- **硬件平台单一**：仅基于 AMD MI300X（及其衍生模拟配置），缺少对 NVIDIA B200 等同类产品的验证；不同厂商的互连拓扑、页表机制和调度策略可能改变结论。
- **缺少多分区场景下的旧基线对比**：未与单分区/单芯片 GPU 的绝对性能做对比，未能直接体现分区架构相对于单体的收益与损失。
- **虚拟地址分析局限**：论文承认迹线基于虚拟地址，而真实物理页放置可能受到内存管理优化干扰；虽然声称共享模式不变量，但实际局部性数值仍可能偏差。
- **MoE 路由场景过于简化**：只测试了共享/不相交两种极端，未体现真实动态路由的统计分布，可能低估实际优化难度。
- **未涉及大规模系统效应**：未讨论多 GPU 扩展、多租户调度、页迁移开销等生产环境因素，实际落地时 NUMA 优化可能与这些因素耦合。
- **计算资源披露不足**：没有给出迹线收集耗时、模拟器运行成本等，可复现性信息不完整。
