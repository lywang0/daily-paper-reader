## 摘要
大语言模型（LLM）服务通常通过增加批次大小来提高吞吐量，但性能最终会达到一个依赖部署环境的平台期，超过该平台期后，更大的批次只能带来边际收益，同时增加延迟和GPU内存消耗。以往研究将此行为归因于HBM/DRAM带宽限制，但其根本原因主要通过概念性论证或高层性能观察得到支持。作为我们的第一项贡献，我们利用硬件剖析技术进行了详细的GPU特征分析，证明吞吐量饱和源于解码阶段的注意力核。具体而言，我们表明，随着活动上下文长度增加，其算术强度几乎恒定——而不仅仅是更大的批次大小——驱动了DRAM带宽饱和，同时实际达到的计算吞吐量远低于硬件上限。基于此分析，我们提出了批处理配置顾问（BCA），它选择满足目标延迟约束的最高吞吐量批处理配置，并识别出对于所评估的OPT模型，可以避免高达55 GB的GPU内存分配，且吞吐量损失最小。为实现这些建议，我们引入了SLIM（饱和感知轻量级性能模型），这是一种半解析模型，通过Transformer计算和内存流量的解析公式来预测LLM推理的吞吐量和延迟。在所评估的场景中，SLIM优于具有代表性的性能建模基线，同时成功泛化到以前未见过的运行条件。

## Abstract
Large language model (LLM) serving commonly increases batch size to improve throughput, but performance eventually reaches a deployment-dependent plateau beyond which larger batches provide marginal gains while increasing latency and GPU memory consumption. Previous studies have attributed this behavior to HBM/DRAM bandwidth limitations, but the underlying causes have primarily been supported by conceptual arguments or high-level performance observations. As our first contribution, we present a detailed GPU characterization using hardware profiling techniques, demonstrating that throughput saturation originates in the attention kernels during the decode phase. Specifically, we show that their nearly constant arithmetic intensity as active-context lengths increases -not merely larger batch sizes- drives DRAM-bandwidth saturation, while the achieved compute throughput remains far below the hardware limit. Building on this analysis, we present the Batching Configuration Advisor (BCA), which selects the highest-throughput batching configuration satisfying a target latency constraint and identifies up to 55 GB of GPU memory allocation that can be avoided for the evaluated OPT models with minimal throughput loss. To enable these recommendations, we introduce SLIM (Saturation-Aware Lightweight Performance Model), a semi-analytical model that predicts LLM inference throughput and latency from analytical formulations of Transformer computation and memory traffic. Across the evaluated scenarios, SLIM outperforms representative performance-modeling baselines while successfully generalizing to previously unseen operating conditions.

### 1. 论文的核心问题与整体含义（研究动机和背景）

- **背景**：大语言模型（LLM）已广泛部署于云端推理服务。服务提供商通常通过增大批处理大小（batch size）来提高吞吐量，但性能最终会进入一个**吞吐平台期（throughput plateau）**：继续增加批次带来的吞吐收益微乎其微，却显著增加延迟和 GPU 内存消耗（主要是 KV cache 开销）。这一现象已被广泛观察，但此前研究仅将其概念性地归因于 HBM/DRAM 带宽限制，缺乏基于硬件级内核剖析的详细验证。
- **核心问题**：本文要回答两个问题：
  1. 吞吐平台期的**根本原因**是什么？是单纯由批次大小驱动，还是由更深层的硬件执行特性决定？
  2. 如何建立**轻量级、可泛化的性能模型**，以预测吞吐量和延迟，从而避免过度配置、提高 GPU 资源利用效率？
- **整体含义**：一旦 DRAM 带宽饱和，继续增大批次已无实际收益，只会浪费内存和增加延迟。若能准确预测这一“拐点”，服务提供商可释放大量 GPU 内存用于其他模型实例或服务层级，在满足延迟约束的同时提升整体系统效率。

### 2. 论文提出的方法论

论文的方法论分为**三大部分**：

#### 2.1 低层 GPU 性能分析（定位瓶颈）

- 使用 **Nsight Systems 和 Nsight Compute** 对 vLLM（版本 0.15.1）在离线/在线模式下的执行进行详细剖析。
- 定义了**活动上下文（active context）** 概念：
  \[
  A_t = \sum_{r \in B_t} (IL_r + y_{r,t})
  \]
  即在处理步骤 t 时，批次中所有请求的输入长度与已生成输出长度之和。
- 分析了预填充（prefill）与解码（decode）阶段的时间分解、Tensor Core 利用率、SM Issue 率、DRAM 读取带宽、注意力核的 **roofline 模型**、L1/TEX 与 L2 缓存命中率、长记分板停顿（Long Scoreboard Stalls）与占用率（Occupancy）。

**关键发现**：解码阶段注意力核的算术强度（FLOP/byte）几乎不随批次大小、输入长度或输出长度变化（约为 3.8–4.0），导致其始终处于内存受限（memory-bound）状态，而计算吞吐量远低于硬件上限。这正是吞吐平台期的根本原因。

#### 2.2 SLIM 性能模型（半解析模型）

SLIM 通过解析公式估计端到端延迟和吞吐量。核心公式如下：

- **端到端延迟**：
  \[
  E2E(IL, OL, B) = T_{\text{pre}} + T_{\text{dec}} + t_{\text{fixed}}
  \]
  其中 \(t_{\text{fixed}}\) 为校准的系统开销常数。

- **吞吐量**：
  \[
  T(IL, OL, B) = \frac{B(IL + OL)}{E2E(IL, OL, B)}
  \]

- **预填充时间**（计算受限）：
  \[
  T_{\text{pre}} = \frac{F_{\text{pre}}}{\eta_c F_{\text{max}}}
  \]
  其中 \(F_{\text{pre}}\) 由 Transformer 各层的注意力与 FFN 的 FLOPs 解析累加得出，\(\eta_c\) 为校准的计算效率因子。

- **解码时间**（内存受限主导）：
  \[
  T_{\text{dec}} = \frac{B + B_0}{\eta_m} \left( T_d + \frac{M_{\text{dec}}}{BW_{\text{max}}} \right)
  \]
  - \(T_d\)：密集计算时间，用校准系数 α、γ 与模型维度 D、层数 L 建模。
  - \(M_{\text{dec}}\)：KV cache 内存传输量：
    \[
    M_{\text{dec}} = 2 L D_{kv} b_{kv} C(IL, OL)
    \]
    其中 \(C(IL, OL) = OL(IL+1) + \frac{OL(OL-1)}{2}\)，捕捉 KV cache 随生成长度二次增长的特性。

- 模型仅需少量校准参数（ηc，ηm，α，γ，B0，tfixed），通过非线性最小二乘法在少数剖析点上拟合。

#### 2.3 BCA 批处理配置顾问（应用框架）

- 基于 SLIM 的预测，在满足**延迟 SLO** 和**最小批处理效率阈值 ε** 的约束下，选择最高吞吐量的批次大小上限 \(B_{cap}\)：
  \[
  B_{cap}(IL, OL) = \arg\max_B T(IL, OL, B)
  \]
  约束条件：
  - \(E2E(IL, OL, B) \le SLO\)
  - \(\frac{T(IL, OL, B)}{B \cdot T(IL, OL, 1)} > \epsilon\)（避免进入平台区）

### 6. 论文的主要结论与发现

- **根本原因确认**：吞吐平台期由**解码阶段注意力核的 DRAM 带宽饱和**引起。注意力核的算术强度几乎恒定（约 4 FLOP/byte），活动上下文增大时内存流量与计算量同步增长，最终在内存带宽上达到瓶颈，而计算资源（Tensor Core <30%、SM Issue <10%）远未充分利用。
- **SLIM 模型有效性**：
  - 输入长度泛化：吞吐 MAPE **0.7%**；输出长度泛化：**5.6%**；模型泛化：**24.3%**；模型+输出长度联合泛化：**17.6%**。

- **BCA 实用价值**：在满足延迟约束与效率阈值的前提下，可避免高达 **55 GB** 的 GPU 显存分配（OPT-350M 节省 55.4 GB、OPT-1.3B 节省 49.1 GB、OPT-2.7B 节省 47.5 GB），且吞吐量损失很小。
- **架构泛化**：SLIM 通过 \(D_{kv}\) 参数适配 GQA 架构，能较好地预测 Mistral-7B 的性能曲线。

### 7. 优点

- **硬件级归因扎实**：通过 roofline 模型、缓存命中率、硬件计数器等多角度证明瓶颈来源，而非停留在概念层面。
- **模型可解释性与轻量性**：SLIM 解析建模 Transformer 计算和显存流量，仅需少量校准常数，剖析开销小，且能外推到未见过的模型/长度组合。
- **实用导向强**：BCA 可输出可操作的批次容量建议，显存释放效果显著，对云端 LLM 服务的资源配置有直接价值。
- **消融设计清晰**：验证了 KV 缓存扫描项与密集解码项分别对输出长度泛化和模型泛化的贡献，增强结论的可信度。

### 8. 不足与局限

- **模型泛化精度仍有待提升**：跨模型泛化的吞吐 MAPE 为 24.3%，虽然优于基线，但对精确容量规划而言仍有较大误差。跨模型性能差异涉及内核行为差异、框架开销等难以解析建模的部分。
- **未建模张量并行通信开销**：Qwen-72B 的预测偏差体现了该局限——模型将 Qwen-72B 视为统一更大的模型，未显式建模分片后的每 GPU 工作负载和通信开销。
- **评估范围有限**：
  - 低层剖析仅限单一 GPU 型号（H100）和两种模型。
  - 未将最新优化（量化 KV cache、前缀缓存、投机解码、Sarathi-style 分块预填充）纳入模型（论文讨论中提到这些会影响已有项，但未做实证扩展）。

- **假设过于简化**：模型假设批次内所有请求同时完成、输入/输出长度固定，与真实动态负载存在差异。
- **未报告算力消耗**：缺乏对训练/剖析时长、能耗等资源的量化描述，影响对其“轻量性”的整体评估。
