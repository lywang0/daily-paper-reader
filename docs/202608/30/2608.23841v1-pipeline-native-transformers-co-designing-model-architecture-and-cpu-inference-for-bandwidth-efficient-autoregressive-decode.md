## 摘要
在CPU上进行单令牌自回归解码受限于内存带宽而非计算能力：现代CPU大约可维持1 TFLOP/s的计算速度，但从主内存读取数据仅约50 GB/s，并且每个生成的令牌必须将所有活跃权重流式读取一次。本报告认为，最有效的应对方式是协同设计模型架构与推理运行时。它提出了cflow，一个CPU优先的流式引擎，以及一系列面向管道的原生Transformer架构，这些架构的层间依赖图被构建为允许垂直的、以阶段为主的执行调度。cflow将权重按计算消耗顺序存储为L2大小的分块，只读取每个混合专家层的前k个专家，融合投影，并根据每个模型的依赖参数执行延迟感知调度。在TinyStories上训练的五种架构中，其中一种（arch2_4_combined）在关键路径权重带宽上实现了2.00倍的减少（从9.00降至4.50 MB/令牌），与最佳候选的困惑度差异在0.24以内，并且分块布局相比行主序基线减少了7.29倍的L1数据读取未命中。在一个309亿参数的面向管道的原生MoE模型上，cflow在32 vCPU Ice Lake服务器上实现了5.94令牌/秒（tok/s）的解码速度，超过了在相当规模的稠密模型上的llama.cpp（4.75）和vLLM CPU后端（1.65）。将专家延迟窗口实现为磁盘驻留专家层上的异步I/O重叠，进一步带来了高达1.68倍的净收益，与重叠模型的差异在1%以内。测量结果反驳了八项设计声明中的一项，并使得第二项尚无定论；这两项均被完整报告，并附带了它们成立的条件。

## Abstract
Single-token autoregressive decode on CPUs is bound by memory bandwidth, not arithmetic: a modern CPU sustains roughly 1 TFLOP/s of compute but only about 50 GB/s from main memory, and each generated token must stream every active weight once. This report argues that the most effective response is to co-design the model architecture and the inference runtime together. It presents cflow, a CPU-first streaming engine, alongside a family of pipeline-native transformer architectures whose inter-layer dependency graphs are constructed to permit a vertical, stage-major execution schedule.   cflow stores weights as L2-sized tiles in compute-consumption order, reads only the top-k experts of each mixture-of-experts layer, fuses projections, and executes a delay-aware schedule from per-model dependency parameters. Across five architectures trained on TinyStories, one (arch2_4_combined) achieves a 2.00x reduction in critical-path weight bandwidth (9.00 to 4.50 MB/token) within 0.24 perplexity of the best candidate, and the tile layout incurs 7.29x fewer L1-data read misses than a row-major baseline. On a 30.9-billion-parameter pipeline-native MoE, cflow decodes at 5.94 tokens/s (tok/s) on a 32-vCPU Ice Lake server, ahead of llama.cpp (4.75) and the vLLM CPU backend (1.65) on comparably sized dense models. Realizing the expert-delay window as asynchronous I/O overlap on a disk-resident expert tier yields a further net win of up to 1.68x, matching the overlap model within 1%. Measurement refutes one of the eight design claims and leaves a second inconclusive; both are reported in full, with the conditions under which they would hold.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：在 CPU 上进行单 token 自回归解码时，系统的瓶颈是**内存带宽**而非算术计算能力。现代 CPU 的峰值计算约为 1 TFLOP/s，但从主存读取数据仅约 50 GB/s，机差（machine balance）约为 20 FLOP/byte。单 token 解码的算术强度仅约 4 FLOP/byte（Q4 量化时），远超带宽约束。
- **体制特征**：每个生成的 token 必须将模型的所有活跃权重从内存流式读取一遍。因此，**减少每一 token 读取的字节数，就能以接近 1:1 的比例降低解码延迟**。
- **既有方案缺陷**：主流 CPU 推理运行时（如 llama.cpp、ExLlama2）多源自 GPU 推理代码的移植，继承了 GPU 优化的假设（行主序权重布局、逐层顺序执行、全量加载 MoE 专家等），在 CPU 单 token 解码场景下系统性低效。
- **核心论点**：传统上将模型架构与推理运行时视为相互独立的做法在 CPU 推理中不再有效。**只有将两者协同设计，以 CPU 内存层级为共同优化目标**，才能实现任何单独设计都无法达到的带宽优化效果。

## 2. 论文提出的方法论：核心思想、关键技术细节

### 2.1 核心思想：Co-Design（协同设计）

- 修改 Transformer 层间依赖图，使一种新的执行调度——**垂直阶段主序（vertical stage-major）流水线**——在数学上有效。
- 建立配套运行时（cflow），其存储格式与执行计划均围绕该调度设计。

### 2.2 cflow 流式引擎的关键技术

- **Tile 原生的权重格式**：权重矩阵被划分为 128 × 256 的 L2 大小分块（Q4 量化下约 18 KB/块），按计算消耗顺序存储。相比行主序布局，减少了 7.29 倍的 L1-d 读取未命中（经 PMU 硬件计数器验证）。
- **计算顺序的存储布局**：磁盘上字节顺序与推理时的读取顺序一致，使 mmap 顺序读取可充分利用系统预读机制。
- **条件式专家加载**：MoE 层只读取 router 选中的 top-k 专家的权重块，而非加载全部 E 个专家。在如 Gemma 4（E=128, k=8）规模下，可减少 16× 的专家权重读取量。
- **融合投影内核**：QKV 三个投影和 gate+up 两个投影分别交错存储与计算，使激活向量只需加载一次即可服务多个投影。
- **延迟感知调度器**：读取模型头部的 dense_delay 与 expert_delay 参数，通过环形缓冲残差历史，在正确的层偏移注入延迟的输出。
- **Q4 内积流水线**：实现标量、AVX2+FMA、AVX-512 三档内核，运行时检测指令集自动分派。

### 2.3 五种架构与 DAG 重写

论文定义了两个依赖重写操作：

- **dense_delay（δd）**：FFN 读取 δd 层之前的残差而非当前层的，打破注意力→FFN 的层内依赖，使下一层注意力可提前开始。
- **expert_delay（δe）**：MoE 在层 ℓ 路由，但在层 ℓ+δe 才注入专家输出，从而在 δe 层窗口内异步加载专家权重。

## 6. 论文的主要结论与发现

- **协同设计有效**：将 CPU 内存层级作为共同优化目标，模型架构与推理运行时协同设计，可实现任何单独设计无法实现的关键路径带宽优化。
- **带宽减半**：arch2_4_combined 的关键路径带宽从 9.00 MB/token 降至 4.50 MB/token（2.00×），且困惑度仅比最佳候选差 0.24。
- **端到端吞吐领先**：cflow 在 30.9B MoE 模型上达到 5.94 tok/s，超过 llama.cpp（4.75 tok/s，32B 稠密 Q4）和 vLLM CPU（1.65 tok/s），且在磁盘驻留专家层实现异步 I/O 重叠，最高获得 1.68× 净加速。
- **架构设计洞察**：dense_delay 是带宽调节旋钮（显著减少关键路径），expert_delay 是质量调节旋钮（延迟路由前的激活信号更干净可提升困惑度）。
- **负面结果透明公开**：PREFETCHT0 在 I/O 受限时无正面效果且有害；阶段主序磁盘布局的优势需要异步流水线（异步 I/O 重叠）配合才能显现。

- **协同设计视角新颖**：将模型的依赖图重写与运行时的执行调度作为一个整体来优化，而非各自的独立局部优化，提供了一个新的优化维度。

- **多尺度验证链完整**：从 114M 规模的概念验证、到 8.34B 中规模验证（PMU 测量）、再到 30.9B 规模化端到端验证，证据链层层递进。

## 8. 不足与局限

- **端到端对比非模型匹配**：cflow 运行自研 30.9B MoE 模型，基线运行 Qwen2.5-32B 稠密模型。虽然参数总量接近，但架构、训练数据和质量都不可比，无法将 5.94 tok/s 的领先归因纯粹的运行时优势。论文也承认这一点，并列为未来的关键工作。
- **小规模训练的推广局限**：5 种架构仅在 d=512, L=6 的小规模下训练验证，较大规模的验证仅在单一架构（arch2_4_8k_4l）上进行，未做不同规模下的全架构比较。
- **单 token 解码的覆盖面局限**：结果仅针对单 token 自回归解码，不适用于批量推理场景。批量推理的算术强度更高，带宽优化的受益相对有限。
- **x86-64 指令集局限**：性能关键路径依赖 AVX2+FMA/AVX-512，ARM NEON 和 Apple Silicon 尚未实现，限制了普遍适用性。
- **实验硬件不一致**：不同硬件平台（Ryzen 5 2600 Windows、Xeon E5-2650 KVM、AWS r6i）的测量结果之间存在指令集差异（AVX2 vs AVX1、是否支持 VNNI），跨平台结论需谨慎归纳。
- **训练数据集与生产数据差异**：TinyStories 是合成儿童故事集，能提供相对清晰的比较信号，但与生产级语言数据分布有显著差异，延迟梯度路径在大规模真实数据下的稳定性尚待验证。
