## 摘要
LLM服务日益受到内存容量的限制，因为模型权重、KV缓存以及所服务的模型变体数量持续增长。本报告探讨了高带宽闪存（HBF）作为基于HBM的服务系统的一种面向容量的扩展。我们首先讨论了如何在不削弱计算芯片所期望的带宽的前提下，将HBF集成到GPU内存层次结构中。然后，我们将新增容量的系统级价值建模为对以读取为主的模型状态对象的扩展驻留。在这种视角下，HBF可以通过支持更多专家副本和改进多模型服务来改善MoE服务，同时减少模型加载并支持热门模型复制。我们的模拟结果表明，这些益处依赖于保留HBM驻留的执行路径，同时使用HBF扩展模型权重的驻留集合。

## Abstract
LLM serving is increasingly constrained by memory capacity as model weights, KV caches, and the number of served model variants continue to grow. This report examines High-Bandwidth Flash (HBF) as a capacity-oriented extension to HBM-based serving systems. We first discuss how HBF can be integrated into the GPU memory hierarchy without undermining the bandwidth expected by the compute die. We then model the system-level value of added capacity as expanded residency for read-mostly model-state objects. Under this view, HBF can improve MoE serving by enabling more expert replicas and can improve multi-model serving by reducing model loading and supporting hot-model replication. Our simulation results show that these benefits depend on preserving the HBM-resident execution path while using HBF to expand the resident set of model weights.

## 1. 核心问题与整体含义

**研究动机：**
- LLM在线服务（聊天、代码助手、智能体等）对内存容量和带宽的需求持续增长，主要压力来自三个维度：①单模型参数量增大；②上下文长度增加导致KV缓存膨胀；③服务商部署的模型变体（通用、代码、视觉、推理等）数量增多。
- 现代GPU依赖HBM提供高带宽和高容量，但HBM的容量扩展面临**堆叠层级的物理限制**（TSV、键合、热管理、良率）和**封装层级的路由与功耗限制**（interposer面积、布线资源）。带宽持续提升而容量增长受限——例如Micron的12层HBM4维持与HBM3E相同的36GB容量，但带宽翻倍至2.8TB/s。
- 现有的系统级方案（MoE专家并行、多模型动态加载/卸载、GPU内存池化等）只能缓解而非解决容量瓶颈，并引入额外的通信开销和调度复杂度。
- 为此，SanDisk提出了**高带宽闪存（HBF）**——基于3D NAND、类HBM堆叠结构、高容量密度且读取带宽接近HBM的新型存储技术。本文核心研究问题：**HBF如何在架构层面被集成到GPU存储层次中，以及如何将额外容量转化为系统级的LLM服务性能收益。**

## 2. 论文提出的方法论

### 2.1 架构层面：HBF集成方案与带宽权衡

论文提出一个带宽可用性公式来刻画存储子系统可暴露给计算芯片的有效带宽：

**Bw_avail = Bw_phy × U_intra × U_inter**

其中：
- **Bw_phy**：介质与封装I/O提供的物理峰值带宽；
- **U_intra**：信道内利用率，取决于请求是否匹配信道的优选访问粒度、是否有足够的内部并行度、是否足够多的在途请求以隐藏延迟；
- **U_inter**：信道间利用率，取决于请求能否在具有相似访问特征的信道间均匀分布。

基于此分析，论文比较了四种HBF集成方案：

| 方案 | 特征 | 主要挑战 |
|------|------|----------|
| (a) 全HBF堆栈 | 用HBF完全替代HBM作为主存 | 闪存更粗的访问粒度和更高延迟难以支撑计算芯片现有的细粒度存储语义，U_intra低 |
| (b) 并排HBM/HBF堆栈 | 部分HBM被HBF替代，同一内存层内异构共存 | 异构存储难以在同一负载下同时饱和，U_inter成为瓶颈 |
| (c) 菊花链HBF扩展 | 复用HBM逻辑芯片的I/O路径外挂HBF | HBF与HBM共享I/O资源，需仲裁以避免干扰关键HBM流量；封装面积增加 |
| (d) 集成式HBM/HBF堆栈 | 每个堆栈内同时集成HBM与HBF，共享TSV垂直互连和接口 | 需要管理堆栈内部I/O共享与调度；若HBF不阻塞关键HBM路径，各堆栈可维持高U_intra |

**结论**：对于带宽敏感的LLM推理，**集成式HBM/HBF堆栈**(d)最优——既保留HBM侧的计算端可用带宽，又在不显著增加interposer面积的情况下引入HBF容量。HBM继续服务细粒度、延迟敏感的访问（KV缓存、运行时缓冲区），HBF服务粗粒度、只读的模型权重数据。

### 2.2 系统层面：容量-驻留模型

论文将HBF的系统级收益形式化为**数据驻留约束下的调度问题**：

- 设硬件单元集合U（设备/节点），每个单元u有容量C_u，驻留对象集R_u ⊆ O（O为只读模型状态对象集合，如MoE专家权重或模型权重），满足容量约束：Σsize(o) ≤ C_u。
- 定义对象o的**可用硬件集** A_o = {u ∈ U | o ∈ R_u}，A_o越大表示驻留覆盖越广。
- 任务q所需的对象集D_q = {o₁, o₂, ...}，调度空间由各对象的A_o联合决定。

**容量收益的数学刻画（近似线性关系）：**

**P_remote(o) ≈ 1 − ρ_o，其中ρ_o ∝ r_o ∝ C_u；Load_per_replica(o) ∝ 1/r_o ∝ 1/C_u**

即：容量线性增长 → 副本数近似线性增加 → 跨节点访问概率近似线性下降、每副本负载近似反比下降。

**两类场景的具体应用：**
- **MoE推理**：对象为专家权重，加大容量使更多专家副本能驻留在本地通信域内，路由到远程专家的概率下降，同时热专家有更多副本可供负载均衡；
- **多模型服务**：对象为模型权重，加大容量让更多模型权重保持驻留，减少动态加载/换出，且热门模型可在多设备复制；调度器可以从更大候选集中选择低负载设备。

## 3. 实验设计

论文使用自研的**LLM服务模拟器**进行两组独立实验，每个场景单独评估以隔离容量收益。

### 3.1 MoE服务实验

- **模型**：Qwen3-235B-A22B，94层，128个路由专家，每token路由top-8专家
- **集群**：4个H100级节点（2个prefill节点 + 2个decode节点），每节点8 GPU，共计32 GPU
- **存储配置**：每GPU 80GB HBM + 512GB HBF用于驻留专家副本
- **互联**：节点内900GB/s scale-up，节点间400GB/s scale-out
- **并行策略**：DP用于attention/projection，EP用于MoE FFN，无tensor parallelism
- **放置与调度**：EPLB风格的分层专家复制 + 专家负载感知运行时调度
- **工作负载**：Poisson到达，log-normal分布输入/输出长度（均值1024/64 tokens）；专家访问遵循Hot-set Zipf分布（16个热专家覆盖90%需求）
- **对比维度**：以每设备驻留专家数（8/12/16/20/24/32）作为容量扫描变量，对应28.4GB~113.5GB容量（占80GB HBM的35.5%~141.9%）——无HBF时24/32专家点已超出HBM容量

### 3.2 多模型服务实验

- **硬件**：4 GPU的PD分离配置（2 prefIll + 2 decode），H100参数（80GB HBM）
- **HBF容量**：最高512GB per placement-group的模型权重驻留（6.4×HBM基线）
- **调度策略**：Prism风格 + KVPR动态模型放置；热模型复制策略用于吞吐率提升实验
- **数据集**：

- **对比维度**：容量从1×→6.4×扫描（80GB→512GB per placement-group）；是否启用模型复制；请求到达率变化（0.5~5.0 req/s）

### 3.3 关键度量指标

MoE实验：平均TPOT、p95 TPOT、跨节点流量（归一化）、scale-out延迟拆解；多模型实验：平均TTFT、模型激活次数、prefill负载均衡比（最大/最小设备运行时间比）。

## 6. 主要结论与发现

**MoE场景：**
1. **HBF容量提升MoE解码延迟**：驻留专家从8→32/设备时，平均TPOT从10.20ms降至9.13ms（↓10.5%），p95 TPOT从10.74ms降至9.73ms（↓9.4%）
2. **专家复制减少跨节点流量**：容量从8→32专家/设备时，跨节点流量降至基线的16.1%；但scale-out延迟未必同步下降（因为取决于最慢传输路径）
3. **容量收益依赖请求速率**：在8~40 req/s范围内，收益增幅先升后微降（8 req/s时↓11.1%→32 req/s时↓15.4%→40 req/s时↓14.8%），最佳区间是解码批大小足以暴露瓶颈设备不平衡、但未完全被平均化摊平的区间
4. **专家热度调节收益**：热专家比例0.6~0.7时收益最大（↓14.8%~15.4%），热比例0.95时降至7.9%；访问越集中，基线放置已能较好预测热专家，额外复制的收益递减

**多模型场景：**
1. **容量消除模型加载开销**：容量从1×→4×(80GB→320GB/placement-group)时，平均TTFT从196.1ms降至6.8ms（28.7×）；模型激活事件从212降至0——4×容量（2×4×80GB=640GB）恰好容纳全部27个模型的620GB权重（all-fit边界）
2. **超出all-fit的容量可用于热模型复制负载均衡**：prefill负载均衡比从7.87×降至约1.0；复制策略使平均TTFT从6.83ms进一步降至6.05ms（↓11%）
3. **活跃模型集波动越大，容量收益越大**：请求速率从0.5→5.0 req/s时，1×→4×容量带来的TTFT加速比从4.1×增至19.4×

**总体结论：** HBF作为HBM的**面向容量的补充扩展**，其价值在于将高容量读取带宽的硬件支持与将额外驻留空间转化为局部性、负载均衡和减少数据移动的服务策略相结合。HBM继续承载带宽关键的动态执行状态，HBF扩展只读模型状态对象的驻留集合。

## 7. 优点

- **问题定位清晰**：准确识别了HBM容量缩放瓶颈与LLM服务系统内存压力之间的结构性矛盾，动机数据翔实（HBM代际对比、MoE模型增长趋势、真实服务负载的活跃模型波动分析）
- **架构与系统双层分析框架**：先解决硬件集成问题（Bw_avail公式 + 四种集成方案比较），再解决系统利用问题（容量-驻留模型），逻辑层次分明
- **理论模型简洁有力**：用容量-驻留-调度的形式化模型（Eq.2~5）刻画了容量→副本数→局部性/负载均衡的定量关系，为结果解释提供理论基础
- **实验设计隔离良好**：MoE与多模型场景分开评估，避免混淆不同容量收益机制；容量扫描、请求速率扫描、热度扫描、复制策略消融等维度设置合理
- **结论有实际指导价值**：区分了MoE场景（容量→通信局部性）与多模型场景（容量→加载消除+负载均衡）的差异性收益机制，并指出"容量收益在请求速率与热度分布的中高区间更显著"这一较为精细的边界条件
- **诚实陈述局限性**：明确声明实验前提——HBF访问不干扰HBM关键路径、KV缓存不放在HBF中、实际收益依赖带宽保持假设

## 8. 不足与局限

- **实验均为模拟而非实测**：模拟器对HBF行为做了较多简化（假设HBF独立带宽、页面粒度布局、预取命令可有效隐藏延迟等），缺乏真实硬件验证；带宽保持假设如果被违反，所有量化结果需打折扣
- **硬件层面分析较粗**：未对集成式HBM/HBF堆栈的I/O仲裁、堆栈内噪声干扰、NAND磨损与写放大对模型权重动态度（如热更新）的影响进行建模
- **模型覆盖有限**：MoE实验仅Qwen3-235B-A22B一个模型；多模型场景的模型最大仅40B参数，未覆盖更大规模的dense模型（如405B/480B）在单设备内的驻留场景
- **工作负载规模偏小**：生产trace仅1,500请求/600秒、27个模型，相比之下真实生产环境的请求规模和模型数量通常大得多

- **未考虑成本与功耗模型**：HBF在能耗、成本、耐久性方面的量化优势/劣势未讨论，缺乏对实际部署经济性的评估

- **未讨论HBF对训练场景的影响**：论文聚焦推理服务，未扩展到训练/微调场景中的权重更新和KV缓存行为
