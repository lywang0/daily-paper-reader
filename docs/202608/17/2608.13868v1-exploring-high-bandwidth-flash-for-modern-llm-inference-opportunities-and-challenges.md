## 摘要
这项工作探讨了使用高带宽闪存（HBF）进行大型语言模型（LLM）推理的潜在优势和技术挑战。HBF作为缓解现代LLM服务系统中内存容量瓶颈的一种有前景的解决方案，已受到越来越多的关注，但其优势与挑战在很大程度上尚未被深入研究。为了填补这一空白，我们在HBF作为主要GPU内存组件处理读写操作的各种系统配置和操作场景下，全面分析了基于HBF的LLM服务系统。我们的分析表明，尽管HBF的写入性能有限，但它可以显著提高LLM服务系统的批量大小、吞吐量和灵活性，同时降低最低GPU要求，但实现这些优势的关键在于保持与HBM相当的读取带宽，并且需要显著的耐久性提升。

## Abstract
This work investigates the potential benefits and technical challenges of using high-bandwidth flash (HBF) for large language model (LLM) inference. HBF has gained increasing attention as a promising solution to mitigate memory-capacity bottlenecks in modern LLM-serving systems, but its benefits and challenges remain largely uninvestigated. To address this gap, we thoroughly analyze HBF-based LLM-serving systems under diverse system configurations and operating scenarios in which HBF serves as a main GPU-memory component to handle both reads and writes. Our analysis shows that, despite its limited write performance, HBF can significantly improve the batch size, throughput, and flexibility of LLM-serving systems while reducing the minimum GPU requirements, but realizing these benefits critically depends on sustaining HBM-comparable read bandwidth and requires significant endurance improvements.

# 探索面向现代 LLM 推理的高带宽闪存：机遇与挑战

## 1. 核心问题与整体含义

- **研究背景**：现代 LLM 推理系统面临 HBM 容量严重不足的瓶颈。LLM 的模型参数规模和上下文长度增长远超 HBM 容量扩展速度，导致系统必须依赖多 GPU 部署来聚合 HBM 容量。
- **现有方案的痛点**：
  - 多 GPU 部署显著推高系统成本（需要大量 GPU 及昂贵的高速互连）。
  - 多 GPU 紧耦合服务单个查询限制了系统灵活性和调度粒度。
- **HBF 的提出**：高带宽闪存（High-Bandwidth Flash, HBF）利用低延迟 NAND 闪存替代 HBM 中的 DRAM，单堆栈容量可达 512 GB（约为 HBM4 的 14 倍以上），同时借助大规模 die 和 plane 级并行性，目标是提供与 HBM4 相当的每堆栈读取带宽（约 1.6 TB/s）。
- **研究空白**：尽管 HBF 在容量上优势显著，但其作为 GPU 主内存组件在实用 LLM 服务场景中的有效性此前未被系统研究。已有工作仅探讨了 HBF 作为只读内存扩展（用于 cache-augmented generation），无法覆盖一般 LLM 服务场景。
- **整体含义**：本文是首个系统研究 HBF 替代（大部分）HBM 用于现代 LLM 服务系统的机遇与挑战的工作，对判断 HBF 在 LLM 推理中的实际价值具有重要的前瞻性意义。

## 2. 方法论

- **核心思想**：利用模拟方法，对比 HBF 与 HBM 作为 GPU 主内存组件在 LLM 推理服务中的表现，识别 HBF 的实际收益来源与瓶颈所在。
- **系统配置设计**：定义五种 GPU 内存配置，均采用相同的最先进 GPU 核心架构：
  - **HBM4**：8 个 HBM 堆栈/GPU，每个 36GB、1.6TB/s 读带宽。
  - **HBF**：7 个 HBF 堆栈 + 1 个 HBM 堆栈（保留给中间数据），每 HBF 堆栈 512GB、1.6TB/s 读带宽。
  - **HBF+**：8 个 HBF 堆栈，用逻辑 die 上的 40MB SRAM 暂存中间数据（但实际支持高达 320MB/GPU 的 SRAM 缓冲容量）。
  - **CONV / CONV+**：与 HBF/HBF+ 结构相同，但每堆栈读带宽保守假设为 0.35TB/s（基于现有低延迟 NAND 闪存技术 Z-NAND 和 XL-Flash 的投影），用于考察读带宽不足的影响。
- **关键技术细节**：
  - 模型权重和 KV 缓存存放在 NAND 闪存中，因为二者容量需求大且主要呈读密集访问模式。
  - 假设每 HBF 堆栈在逻辑 die 上配备专用 3.13MB SRAM 暂存缓冲，用于预取和双缓冲读数据，以隐藏 μs 级读延迟。
  - 写入性能假设：100μs 页面编程延迟（基于三星 Z-NAND 数据）。
  - 目标读带宽实现依赖 25 planes/core die 和 1μs 4KiB 页面读取延迟。
- **模拟器扩展**：在 LLMSimulator 基础上进行了三方面扩展：
  - 加入 HBF 感知时序模型，独立配置读写带宽以反映 NAND 闪存读写性能不对称性。
  - 改进连续批处理建模和分离式 prefill-decode 执行中 KV 缓存写入开销的建模。
  - 实现分块注意力（chunked attention）和流水线并行等现代技术。
- **分析场景假设**：
  - 聚焦分离式 prefill-decode 执行中的 decode 节点（prefill 阶段受计算限制，受益于 HBF 不多）。
  - 采用连续批处理，保持满载运行。
  - 系统自动选择最大化吞吐的并行配置（数据、张量、流水线、专家并行），受 SLO、容量、SRAM 限制约束。
  - 系统包含高性能互连（NVLink 1800GB/s 节点内、InfiniBand 100GB/s 节点间）。

## 6. 主要结论与发现

1. **HBF 能显著扩大批大小**：在相同 GPU 数量下，HBF 和 HBF+ 分别比 HBM4 提供 1.3–4.5 倍和 1.7–5.3 倍的每 GPU 批大小增益（8-GPU 配置）。HBM4 至少需要 4 个 GPU 才能服务所选 LLM，而 1 个 GPU 的 HBF/HBF+ 在多数情况下就能超过 8-GPU HBM4 的批大小。
2. **读带宽是决定 HBF 收益的关键因素**：CONV/CONV+ 因读带宽不足，批大小甚至低于 HBM4，说明仅扩大容量不够，必须保持 HBM 相当的读带宽。
3. **HBF 能提升吞吐量和系统灵活性**：HBF+ 即使使用更少的 GPU 也能超过更多 GPU 的 HBM4 系统的每 GPU TPS；例如 4-GPU HBF+ 在 Llama4 LONG 场景下比 8-GPU HBM4 的每 GPU TPS 高 15%，意味着 8 个 GPU 可以运行两个独立实例，提升调度灵活性。
4. **上下文越长，HBF 收益越大**：HBF+ 在 MID/LONG 场景相比 SHORT 场景可获得 124%/200% 更高的平均增益。
5. **KV 缓存写入是重要性能开销**：在 HBF+ 中占执行时间的 5–13.9%（Llama4 场景），改善写入性能能进一步提升 HBF 的收益。
6. **SLO 越宽松，HBF 优势越大**：在离线场景中 HBF 的增益显著增加（如 Llama4 16-GPU 下从 4.1% 提升至 14.8%），HBF 特别适合吞吐导向或离线推理。
7. **耐久性是关键挑战**：HBF 和 HBF+ 在大多数情况下三年内的 P/E 周期数远超 SLC NAND 的 100K 限制，需要显著提升闪存耐久性或采用 retention-relaxed 写入策略。

## 7. 优点

- **首个系统性研究**：首次全面评估 HBF 作为 GPU 主内存组件在一般 LLM 服务场景中的表现，填补了此前仅关注只读场景（如 CAG）的研究空白。
- **实验设计周到**：引入保守读带宽配置（CONV/CONV+）作为下限对比，使结论不依赖于对 HBF 目标参数的激进假设，增强了可信度。
- **多层次评估指标**：不仅考察吞吐量和批大小，还通过运行时分解和 P/E 周期分析揭示瓶颈来源和耐久性风险，覆盖性能和可靠性两大维度。
- **多维度变量覆盖**：模型类型（稠密 vs MoE）、上下文长度、GPU 数量、SLO 松紧度的组合实验提供细致全面的视角。
- **发现反直觉结论**：如容量优势并不自动带来收益（读带宽是关键）、HBF 可以以更少 GPU 获得更高灵活性和吞吐量等，具有重要的架构设计指导价值。
- **将开源模拟器扩展**：有利于领域内后续研究和复现。

## 8. 不足与局限

- **缺乏硬件实测验证**：所有分析基于模拟器，HBF 本身尚处早期，但模拟参数（如 1μs 读延迟、100μs 写延迟、25 planes 等）与实际产品可能有偏差。

- **SRAM 容量假设乐观**：HBF+ 依赖 40MB SRAM（来自前作），支撑 327 的批大小（Llama 4 Maverick 下），该假设对中间数据生命周期较敏感，实际系统实现难度未知。
