## 摘要
检索增强生成（RAG）通过将生成建立在外部段落之上来改善语言模型的响应，但这会带来开销：检索到的上下文会延长提示词，增加预填充工作量、KV缓存占用、内存流量、延迟和能耗。上下文压缩提供了一种自然的补救措施，通过在生成之前修剪检索到的文本。然而，最先进的上下文压缩方法通常使用固定的压缩预算，或者离线选择压缩率然后在推理时应用。这种静态观点忽略了工作负载变化和边缘设备的实时状态。在边缘SoC上，压缩不是免费的：压缩器本身在同一SoC上运行，并消耗延迟和能量，这可能会抵消生成节省的收益。本文提出了一种基于遥测信息的边缘RAG自适应压缩的愿景，并以实验证据为基础。我们使用Llama和Qwen生成器、Natural Questions和HotpotQA数据集以及LLMLingua-2压缩来表征NVIDIA Jetson AGX Thor上的压缩权衡。我们的测量表明，对于较大的模型，生成在RAG预算中占主导地位，对于7B-8B生成器，大约占每次查询延迟的90%和GPU能量的91%。探索压缩率的影响揭示了一个自适应操作区域：轻度压缩可能错过节能机会，过度压缩可能损害推理质量。中间压缩可以将GPU能耗降低高达53.2%，SoC能耗降低高达48.2%，而质量损失可忽略不计。我们主张运行时的策略，在工作负载特征和边缘遥测信息的指导下动态管理压缩。

## Abstract
Retrieval-augmented generation (RAG) improves language-model responses by grounding generation in external passages, which comes with overhead: retrieved context lengthens the prompt, increasing prefill work, KV-cache footprint, memory traffic, latency, and energy. Context compression offers a natural remedy by pruning retrieved text before generation. However, state-of-the-art context-compression methods are typically used with a fixed compression budget, or with the rate selected offline and then applied at inference time. This static view ignores both workload variation and the live state of the edge device. On an edge SoC, compression is not free: the compressor itself runs on the same SoC and consumes latency and energy that can offset any generation savings.   This paper proposes a vision for telemetry-informed adaptive compression in edge RAG, grounded in experimental evidence. We characterize the compression tradeoff on the NVIDIA Jetson AGX Thor using Llama and Qwen generators, Natural Questions and HotpotQA datasets, and LLMLingua-2 compression. Our measurements show that generation dominates the RAG budget for larger models, reaching roughly 90% of per-query latency and 91% of GPU energy for 7B-8B generators. Exploring the impact of the compression rate reveals an adaptive operating region: mild compression can miss energy opportunities, and overly aggressive compression can hurt inference quality. Intermediate compression can reduce GPU energy by up to 53.2%, and SoC energy by up to 48.2%, with negligible quality loss. We argue for runtime policies that dynamically manage compression, guided by workload features and edge telemetry.

## 1. 核心问题与整体含义（研究动机和背景）

- **背景**：检索增强生成（RAG）通过将生成建立在外部检索段落之上来改善 LLM 响应，但检索上下文会延长提示词长度，显著增加 **prefill 工作量、KV-cache 占用、内存流量、延迟与能耗**。在边缘 SoC 上，这些开销又被有限的内存带宽、功耗预算和热余量进一步放大。
- **核心问题**：上下文压缩虽能通过修剪检索文本以降低生成成本，但现有最先进压缩方法（如 LLMLingua 家族）通常采用**固定压缩预算**，或仅在离线阶段选定压缩率后于推理时静态应用。这种静态视角存在两个缺陷：
  1. 忽视了**工作负载变化**（如模型规模、检索深度、上下文长度）；
  2. 忽视了**边缘设备的实时状态**（如功耗、温度、内存利用率）。
- **关键洞见**：在边缘 SoC 上，压缩并非免费——压缩器本身与检索器、生成器共享同一 SoC 资源，其自身的延迟和能耗开销可能抵消生成阶段节省的收益。因此，正确的评估指标是**净收益**（生成端节省 − 压缩器开销），而非单纯的生成加速比。
- **整体含义**：论文提出"遥测信息驱动的自适应压缩"（telemetry-informed adaptive compression）愿景，主张将压缩视为**运行时系统旋钮**而非固定预处理步骤，依据工作负载特征和实时设备状态动态决策是否压缩、以何种速率压缩。

## 2. 方法论：核心思想、关键技术细节与流程

### 2.1 核心思想

- 将上下文压缩从静态预处理转变为**运行时自适应决策**：由策略/控制器（Policy/Controller）根据工作负载特征（模型身份、检索上下文长度、top-\( k \)）和边缘 SoC 实时遥测（延迟、功率/能耗、温度、内存利用率）动态选择压缩率。
- 控制器目标可覆盖**延迟目标、能量预算、热限制和精度目标**，形成连续反馈回路（Feedback Loop）。

### 2.2 关键技术细节

- **压缩率定义**：采用 LLMLingua-2 暴露的 rate 参数，即**保留的检索上下文 token 比例**（rate = 0.5 即保留约一半 token）。压缩仅作用于检索上下文，系统提示词、指令和 few-shot 示例保持不变。
- **压缩方法选择**：使用 LLMLingua-2 作为代表性**抽取式硬压缩**方法——其轻量、可插拔，且暴露连续速率参数，便于扫描率值以刻画权衡曲线。论文明确指出目标并非宣称 LLMLingua-2 为最终边缘压缩器，而是将其作为可控代表工具。
- **净收益评估**：所有报告的节省/损失均**包含压缩器自身的开销**（压缩阶段与检索、生成共享 SoC），而非仅报告生成端加速。
- **两膝结构分析**：扫描压缩率后发现两个拐点——
  - **能量膝**：rate = 0.9 为净损失（压缩器固定开销未被 10% token 缩减摊销）；rate = 0.7 起为净收益；
  - **质量膝**：rate = 0.3 附近质量保持稳定，rate = 0.15 时 F1 崩溃（下降 4–10 个绝对点）。
  - 两膝之间即为**自适应操作区域**（宽度约 0.6 个 rate 单位）。
- **控制器简化策略**：首个实用控制器无需搜索连续速率空间，只需少量基于工作负载的离散决策——
  - 当预计生成节省 < 压缩器开销时跳过压缩；
  - 长上下文/高成本生成使用 rate = 0.3；
  - 在明确允许质量损失时保留更激进压缩选项。

## 6. 主要结论与发现

1. **生成主导预算（>3B 模型）**：7B–8B 生成器下，生成阶段占每次查询约 **90% 延迟、91% GPU 能量、92% 总 SoC 能量**；embed + retrieve 合计不超过 10%。1B 端则反转：embed + retrieve 占 33% 延迟和 39% GPU 能量，压缩回收空间有限。
2. **压缩可带来可观净节能，但非免费**：考虑压缩器开销后，rate = 0.3 可将 GPU 能耗降低最高 **53.2%**、SoC 能耗降低最高 **48.2%**，且质量损失可忽略（ΔF1 ≤ 0.016）。
3. **存在自适应操作区域**：两膝（能量膝≈0.7、质量膝≈0.3）之间宽度约 0.6 的速率区间是控制器可操作空间。rate = 0.9（轻度压缩）在所有配置下均为**净损失**（−1% 至 −13% 能耗），rate = 0.15（过度压缩）导致 F1 崩溃 4–10 点。
4. **最佳安全激进 setpoint 稳定，但收益随负载漂移**：rate = 0.3 在所有面板上均为最安全激进选择，但量化收益随模型规模和上下文长度从 +30%（Llama-3B, \( k=5 \)）到 +53%（Llama-8B, \( k=10 \)）变化，约 1.8 倍差异。
5. **工作负载决定压缩价值**：重负载（8B + \( k=10 \)）受益最大；轻负载下压缩可能得不偿失，因此需要运行时决策而非固定策略。

## 8. 不足与局限

- **平台单一性**：所有实验仅在 Jetson AGX Thor 上完成，缺乏跨边缘平台（如其他 Jetson 系列、移动 SoC、RISC-V 边缘平台）的验证，结论泛化性受限。

- **压缩器单一**：仅评估 LLMLingua-2 这一种抽取式压缩器；抽象式压缩（如 RECOMP）、流式/硬件感知压缩器可能改变能量膝位置和净收益边界，论文虽在展望中提及但未实验验证。

- **质量指标单一**：仅使用 EM 与 token 级 F1，未采用更细粒度的生成质量评估（如人工评测、LLM-as-a-judge），也无法捕捉 answerability（不可回答查询）场景下的压缩风险。
