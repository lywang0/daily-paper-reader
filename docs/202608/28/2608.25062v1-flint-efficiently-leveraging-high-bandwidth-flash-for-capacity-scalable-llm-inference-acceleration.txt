# FLINT: Efficiently Leveraging High Bandwidth Flash for Capacity-Scalable LLM Inference Acceleration 

*Geraldo F. Oliveira † *Arash Tavakkol † Xiangyu Zhu † Ahmet Caner Yüzügüler †

Vamanan Arulchelvan † Lukas Cavigelli † Renzo Andri † Mohammad Sadrosadati †

Jia Xinglei ‡ Onur Mutlu § Zhou Ke ∇ Shai Bergman † Ji Zhang ‡† Huawei Technologies Switzerland AG ‡ Huawei Technologies Co., Ltd. § ETH Zürich ∇ HUST 

Large language model (LLM) inference is increasingly con-strained by accelerator memory capacity rather than com-pute throughput. This constraint is especially acute in single-accelerator and small-node inference systems, where limited on-package memory capacity restricts the size of deployable models. High bandwidth flash (HBF) is an emerging 3D-stacked NAND flash technology that provides multi-terabyte near-accelerator capacity, making it a promising capacity tier for storing LLM weights. However, existing HBF-based proposals face three adop-tion challenges: they (i) rely on coarse-grained static prefetching for LLM weights aiming to hide the μs -level read latency of the NAND flash device while maximizing HBF’s read through-put, (ii) expose NAND flash management tasks (e.g., refresh operations) to the accelerator-visible critical inference path, and (iii) miss optimization opportunities to specialize and optimize the flash-management mechanisms to the workload behavior. Our goal is to design an efficient HBF substrate that integrates HBF as a memory-capacity tier alongside high bandwidth mem-ory (HBM) while addressing these three challenges. To this end, we propose FLINT (flash inference tier), a workload-driven HBF substrate for capacity-scalable LLM inference. FLINT introduces three mechanisms: (i) a hardware burst-buffer controller that 

dynamically coalesces and pipelines HBF reads aiming to utilize existing NAND flash buffers while sustaining high HBF band-width, (ii) a phantom-plane refresh mechanism, which removes refresh from the critical inference path by moving refresh-related NAND flash operations outside the read foreground back via low-cost resource duplication, and (iii) a read-only flash translation layer (FTL) , which replaces solid-state drive (SSD)-class support for arbitrary writes with a compact table that translates logical weight bursts to physical HBF locations. We evaluate FLINT across dense and mixture-of-experts (MoE) LLM inference models. Our evaluation shows that FLINT im-proves decode throughput by 1,205 ×, 2.2 ×, and 6.2 ×, and re-duces energy consumption by 408 ×, 1.1 ×, and 6.8 × that of an SSD-equipped GPU system, an HBM-only GPU system, and a prior hybrid HBM+HBF GPU system, respectively. FLINT meets a 50 ms time per output token (TPOT) service-level objective (SLO) with 3.1× fewer GPU packages than the HBM-only GPU system. FLINT adds small area cost to an HBF die (3.1 %) and HBF base die (3.9 mm 2 at 7 nm).

1. Introduction 

The progress of large language models (LLMs) [1–7] is increas-ingly shaped by a widening mismatch between model size and accelerator memory capacity [8–11]. On the algorithmic side, parameter counts have grown from hundreds of millions in early transformer-based models [1, 12] to hundreds of bil-lions and, most recently, trillions in frontier models such as Qwen3-235B-A22B [13] (235 B total parameters), Llama-4 Mav-erick [14] (400 B), Llama 3.1-405B [4] (405 B), DeepSeek-V3 [7] (671 B), Kimi K2 [15] (1 T), and DeepSeek V4 [6] (1.6 T). At inference time, this parameter growth becomes a memory-capacity problem , since serving a model requires keeping its weights resident near the accelerator, and weight capacity scales with parameter count. For example, in 16-bit brain floating-point (BF16) precision [16], model weights require two bytes per parameter, so weights alone require on-package storage capacity of roughly 1.3 TB for DeepSeek-V3 and 810 GB for Llama 3.1-405B. Recent frontier models cut the storage cost of each parameter by shipping in narrow bit-width data for-mats, such as the 8-bit floating-point (FP8) [17] weights of Llama-4 Maverick and Kimi K2, or mixed data formats, such as the FP8 weights with 4-bit floating-point (FP4) [18] experts in DeepSeek-V4-Pro. However, narrow bit-width data formats do not remove the capacity requirement: Kimi K2 still requires 1.0 TB of weights at its native precision, and DeepSeek-V4-Pro still requires 795 GB, before accounting for KV (key–value) cache, activations, and runtime metadata. On the hardware side, the required storage for weight pa-rameters alone significantly exceeds the on-package memory capacity of recent high-end GPUs [19–21], which provide only 80–192 GB of on-package memory capacity, often via multi-ple high bandwidth memory (HBM) [22, 23] stacks per GPU package [19–21]. Consequently, deploying frontier-scale LLMs often requires partitioning a model across multiple accelera-tors [10, 24–27], increasing deployment cost and introducing interconnect-induced bottlenecks when partial states must be communicated across devices [10, 28, 29]. In large-batch data-center serving, the workload exploits the arithmetic through-put and memory bandwidth that the added accelerator pack-ages supply for increased performance, and together they hold the model’s weights through tensor, pipeline, or expert paral-lelism [24, 28, 29]. However, in small-batch single-accelerator and small-node inference settings, such as edge servers, work-stations, laptops, and mobile-class systems, adding many accel-

1arXiv:2608.25062v1 [cs.AR] 25 Aug 2026 erator packages solely for model capacity is often physically and commercially impractical [30–32], even when a single ac-celerator package could potentially provide enough arithmetic and memory throughput for deployment. To address the memory-capacity wall, memory vendors [33, 34] and recent academic proposals [35–39] have explored emerging memory technologies as a near-accelerator ca-pacity tier. A prominent example is high bandwidth flash (HBF) [33, 34], which stacks dense 3D NAND flash dies in an HBM [22, 23, 40]-form-factor to provide multi-terabyte ca-pacity per stack with TB/s-class memory bandwidth. A com-mon approach to integrating HBF into the accelerator mem-ory subsystem uses die-to-die (D2D) links [41] to daisy-chain HBF with HBM, which allows expanding on-package capacity while preserving accelerator pin count and simplifying mem-ory controller integration [34–36]. In this organization, LLM weights are preloaded into HBF before inference, allowing HBM to remain available for latency-critical and dynamically generated state, such as the KV cache and intermediate acti-vations that otherwise could incur high write latency over-heads and endurance concerns to the HBF memory tier [42]. Thus, HBF effectively serves as a read-only , on-package mem-ory capacity tier for model parameters, making it especially compelling for reducing capacity-driven accelerator count in single-accelerator and small-node inference systems. Since HBF is built from NAND flash rather than DRAM, its read la-tency is expected to be microsecond-scale [34–36], roughly one to two orders of magnitude higher than HBM [23]. To hide this latency and allow HBF to reach read bandwidth on par with HBM, prior designs [34–36] exploit inter-layer weight prefetch-ing [43] alongside plane-level parallelism [44–46]: while the accelerator computes the current layer using weight blocks already placed in an SRAM staging buffer in the HBM base die, compiler- or programmer-directed prefetching commands move coarse-grained weight blocks belonging to the next layer from HBF into the SRAM staging buffer via a single coordinated multiple-plane flash read operation that collectively returns megabytes’ worth of weight data (i.e., a burst ). Subsequent accelerator requests for model weights, which are forwarded to HBF as fine-grained cache misses from the accelerator’s last-level cache (LLC), can then be served from the staging buffer rather than directly from HBF, hiding raw NAND flash access latency. In principle, this allows the accelerator to approach HBM-side peak memory throughput when the staging buffer is sized to cover the latency–bandwidth product implied by Little’s law [47] and when prefetches arrive timely. Although HBF offers a promising path to expand near-accelerator memory capacity for LLM inference, existing HBF proposals [34–36] either oversimplify or leave unresolved several challenges. First, prior designs [34–36] rely on ex-plicit SRAM staging buffers and static coarse-grained compiler-emitted prefetch hints to hide HBF read latency. Our analysis (§3) shows that this approach leaves two inefficiencies. ( i) The dedicated SRAM staging buffer introduces avoidable area over-head, because HBF already contains per-plane page and cache buffers that can collectively stage weight blocks. ( ii ) Static coarse-grained compiler-emitted prefetch hints cannot reliably align HBF burst issue with the fine-grained cache line demand stream, since the HBF burst consumption order depends on runtime behavior coming from both the application (such as mixture-of-experts (MoE) expert routing, token-dependent at-tention reuse) and the hardware (such as accelerator-side cache line request interleaving), which static layer-ahead prefetch hints cannot fully predict. Second, prior works [34–36] largely leave refresh management unspecified. Although HBF is used as a read-only weight tier, 3D NAND flash still requires main-tenance operations to mitigate retention loss [48–52] and read-disturb [48, 51–54]. Since in HBF, a refresh operation can take five orders of magnitude longer than an HBM accesses [23, 51], scheduling them on the accelerator’s critical request path can stall inference for the duration of the operation. Third, there are missed opportunities to specialize and optimize the flash-management layer to the workload access behavior in order to improve its efficiency and reduce its complexity. Conventional solid-state drive (SSD) flash translation layer (FTL) [51, 55–63] is designed for general-purpose storage, where out-of-place up-dates, garbage collection, and wear leveling are needed to sup-port arbitrary writes. However, these mechanisms are poorly matched to LLM inference, because weights are written once before inference and never updated. Our goal is to design an efficient HBF substrate for LLM in-ference that integrates HBF as a near-accelerator capacity tier alongside HBM, while addressing the adoption challenges iden-tified above. To this end, we propose FLINT (flash inference tier), a workload-driven HBF substrate. The key idea of FLINT is to drive the HBF substrate from the dynamic read access stream the accelerator actually produces, rather than from a 

static compile-time prediction. During runtime, the accelerator issues many fine-grained HBF read requests that arrive out-of-order but concentrate on a small number of weight blocks. From that, FLINT dynamically reconstructs a coarse-grained burst request by ordering and coalescing fine-grained read requests; thus, multiple fine-grained requests are serviced with 

one coordinated multi-plane NAND page-read latency. FLINT applies the same principle to read-disturb mitigation and to address translation via three mechanisms. First, FLINT replaces compiler-driven prefetching with a hardware burst-buffer controller co-located with the HBF base die. Because LLM inference accesses weights through pre-dictable burst-granularity sweeps, the burst-buffer controller serves cache line requests to the active burst and proactively is-sues an HBF request to the next burst identified by a lookahead window before the active burst finishes draining. This keeps the HBF channel continuously occupied. While the current burst streams to the accelerators, FLINT has already issued the next burst request to HBF, because it times that request from the progress of the active burst rather than from a pro-gram point fixed at compile time. By moving burst timing into hardware, FLINT provides two main benefits. It ( i) eliminates compiler-inserted prefetch directives and keeps the HBF tier 2transparent to existing inference kernels and software stacks; and ( ii ) removes the need for a dedicated SRAM staging buffer, since the page and cache buffers already present inside each HBF die collectively provide enough buffering for two in-flight bursts. Second, FLINT introduces phantom-plane refresh , a continu-ous refresh mechanism that exploits the read-only nature of LLM weight access. Each HBF die is provisioned with N +1 

physical planes for an N -plane application address space. At any moment, exactly one of the N +1 physical planes is offline and plays the role of phantom plane , while the remaining N

planes serve read requests at full bandwidth. When a block on a live plane A reaches its read-disturb threshold, the phantom-plane refresh controller forks the block’s contents from the foreground read path and programs an error correction code (ECC)-corrected copy into a free block of the phantom plane, using P ’s independent program circuitry and avoiding con-tention with the reads on A. Since flash programming opera-tions are only executed in P , such operations (which dominate a refresh’s cost) never occupy a plane that is serving decode reads. Third, FLINT adopts a simplified, read-only FTL design 

matched to the regularity of LLM weight access. Because each HBF access fetches a full burst, address translation is main-tained at burst granularity rather than page granularity. For a 512 GB Gen-1 HBF stack with 2 MB bursts, this requires only 256 K entries, 512 × fewer than a conventional page-level SSD FTL [51, 55], because one burst entry replaces the 512 page entries it fetches in parallel. The resulting FTL reduces to a burst translation table, a block-granular relocation table, and one read counter per block, together 1.8 MB per stack, which replaces the large, latency-sensitive metadata path of an SSD-class FTL with a compact, constant-time structure that fits in the HBF base die. We evaluate FLINT on six production LLMs: five MoE models (DeepSeek-V3 [7], DeepSeek-V4-Pro [6], Qwen3-235B-A22B [13], Llama-4 Maverick [14], and Kimi K2 [15]) and one dense model (Llama-3.1-405B [4]). We compare FLINT against three baselines: ( i) HBM+SSD , a single-GPU system that spills model weights to fast off-package SSDs once they exceed HBM capacity; ( ii ) HBM-only , a multi-GPU system that shards the model across enough GPU packages to keep all weights in aggregate HBM; and ( iii ) H3 [34], a prior HBM+HBF design that relies on an HBM-side staging buffer and compiler-emitted layer-ahead prefetch hints. Our results show that FLINT ( i) sus-tains 6.2× higher effective HBF throughput than prior HBF designs; ( ii ) improves decode throughput by 1,205 ×, 2.2×, and 

6.2×, and reduces energy consumption by 408 ×, 1.1×, and 

6.8× that of an SSD-equipped GPU system, an HBM-only GPU system, and a prior hybrid HBM+HBF system, respectively; (iii ) meets a 50 ms time per output token (TPOT) service-level objective (SLO) with 3.1× fewer GPU packages than the HBM-only GPU system (up to 8×); and ( iv ) incurs small area cost to an HBF die ( 3.1 % ) and HBF base die (3.9 mm 2 at 7 nm). We make the following key contributions: • We identify three key adoption challenges for HBF-tiered LLM inference: coarse-grained static prefetching underuti-lizes the HBF channel, on-channel refresh oversubscribes the foreground read path, and SSD-class FTLs overprovision metadata and write-path hardware for read-only weights. • We propose FLINT, a workload-driven HBF substrate that co-designs three mechanisms around the regularity of LLM weight access: ( i) a hardware burst-buffer controller that uses the page and cache buffers already inside each HBF die in-stead of a dedicated SRAM staging buffer, ( ii ) phantom-plane refresh that keeps refresh off the decode critical path, and (iii ) a read-only FTL , which replaces SSD-class support for arbitrary writes with compact logical-to-physical address translation for HBF-resident weight bursts. • We evaluate FLINT on dense and MoE models, showing that FLINT increases decode throughput and reduces energy consumption. 

2. Background 

HBF-Enabled System. Recent HBF proposals [33–36] in-tegrate NAND flash memory [64] directly into the accelera-tor memory subsystem. Fig. 1 shows a representative HBF-enabled package, where xPUs, HBM stacks [22, 23, 40], and HBF stacks [33–36] are co-packaged on a silicon interposer. Each HBM stack vertically bonds 12–16 DRAM dies over a logic-bearing base die , providing 24–36 GB of capacity and 1.2– 2 TB/s of memory bandwidth per stack [23]. HBF follows a similar form factor, stacking NAND flash dies (e.g., 16) over an HBF base die to provide 512–1024 GB of capacity and 1.6– 2 TB/s of aggregate NAND bandwidth per stack [33, 34]. In both memories, thousands of through-silicon vias (TSVs) and 

μbumps connect the memory dies to the base die. The base dies implement the control and interconnect logic needed to com-pose these two memories. The HBM base die contains DRAM channel controllers, refresh and ECC logic, HBM PHYs, and a D2D PHY [41] toward the xPU. Following current HBF litera-ture [34, 35, 42], the HBF base die contains the flash controller, which we model as comprising the FTL [51, 55], NAND com-mand sequencer, NAND ECC engine, and a D2D PHY toward the HBM base die. This physical integration increases memory capacity in the xPU package, but making flash usable as an xPU memory tier 3also requires hiding NAND latency and preserving a familiar memory interface. Therefore, current proposals [34–36] expose HBM and HBF as a unified physical address space, with HBF accessed transparently through the HBM base die [34–36]. To support this model, the HBM base die adds three mechanisms. First, an address decoder partitions the address space into ( i) an HBM-resident region for latency-sensitive and write-mostly state, such as KV cache, activations, and runtime metadata, and (ii ) an HBF-resident region for read-only inference state, such as LLM weights preloaded into HBF at deployment time. The address decoder routes each xPU request (in the form of fine-grained LLC misses in a graphics processing unit (GPU)-based system) either to local HBM banks or through the HBM →HBF D2D link, to the HBF stack. Second, a latency-hiding buffer 

(LHB) [34], implemented as megabyte-scale SRAM in the HBM base die, stages prefetched weight blocks from HBF. This buffer hides NAND page-read latency, which is in the microsecond range [34, 35] and two to three orders of magnitude longer than an HBM access [23]. Third, a prefetch controller consumes compiler- or programmer-emitted prefetch directives [43] and refills the LHB over the HBM →HBF D2D link. 

HBF Organization. A 3D NAND flash subsystem is organized as a hierarchy of components, as Fig. 2 illustrates. An HBF stack (Fig. 1) contains multiple (e.g., 16) flash dies [33, 34]. Each 

flash die (Fig. 2a) integrates tens (e.g., 32) of flash planes around a central TSV array that propagates command, address, and data signals through the die stack [35, 36]. A flash plane 

(Fig. 2b) consists of hundreds (e.g., 256) of NAND flash blocks 

and two small SRAM structures in the peripheral CMOS layer: the page buffer and the cache buffer [51]. The page buffer latches the page currently being sensed or programmed, while the cache buffer holds the previous sensed page. A NAND flash block (Fig. 2c) is the smallest erase unit and is organized as a 3D array of NAND strings . A NAND string is a vertical column of hundreds (e.g., 256) of flash cells along a bitline. The string connects through a string-select transistor to a bitline (BL) at the top and to a common source line at the bottom. Multiple (e.g., 4) NAND strings share each bitline through their respective string-select transistors, allowing each block to contain thousands of pages (e.g., 1024 pages). Flash cells in the same horizontal layer share a wordline (WL); together with the intersecting bitlines and the selected string, a wordline forms one page (Fig. 2, highlighted), the smallest read and program unit. With this organization, an HBF stack with 16 dies, 32 planes per die, 256–512 blocks per plane, 1024 pages per block, and 4 kB pages provides 512–1024 GB of single-level cell (SLC) (i.e., one bit per flash cell with two threshold-voltage levels) capacity per module, spanning current HBF Gen-1 and upcoming Gen-2 design points [33, 36].

Read Disturbance in Flash. Repeated operations and time gradually shift flash cell threshold voltages, eventually causing read errors [48]. Two mechanisms dominate this drift. First, 

read-disturb accumulates over many reads to the same block, because each read biases all non-selected wordlines to a high pass-through voltage [53]. Second, retention loss accumulates over time as trapped charge slowly leaks from the cells [49]. To bound the resulting bit-error rate, the flash controller peri-odically performs refresh : it reads a block, ECC-corrects any errors, reprograms the corrected data to a fresh location, and erases the stale block. Refreshing one SLC block costs one block erase, approximately 3 ms, plus one program per page, e.g., 1024 pages at approximately 50 μs each, for a total of about 55 ms [48, 51]. For SLC NAND, a block must be refreshed after roughly 10 5–10 6 reads to that block due to read-disturb, or after several years due to retention loss [51, 52]. 

3. Motivation 

In this section, we first highlight the opportunities that an HBF-equipped system provides for capacity-bound inference regimes. Second, we identify three major shortcomings of prior HBF architectures for LLM inference: ( i) static prefetching underutilizes the HBF channel; ( ii ) refresh competes with fore-ground reads and can saturate the HBF channel; and ( iii ) SSD-class FTLs retain unnecessary write-path machinery and over-provisioned metadata for a read-mostly inference workload.

3.2. Limitations of State-of-the-Art HBF-Based Sys-tems 

Static Prefetch Underutilizes the HBF Channel. An HBF read operation begins with a NAND flash page sensing, which takes tR ns (e.g., 1–2 μs) and returns a few kilobytes of data (e.g., a 4 kB page) per plane. To approach the HBM channel’s TB/s-class bandwidth, the HBF controller must amortize this fixed page read latency across many planes: for example, a co-ordinated sense at the same (block, page) coordinate across all 512 planes of an HBF stack returns one 2 MB burst in one tR.This burst size matches the channel bandwidth-delay product, BDP = 1 TB /s × tR = 2 MB , and is therefore the minimum 

granularity needed to sustain peak read HBF bandwidth. Prior HBF designs [34–36] adopt this BDP-sized operating point by provisioning two staging-buffer slots: one burst drains to the GPU while the next burst is in flight from HBF. These slots are filled using compiler-emitted, per-layer prefetch hints for model weights [43], with the goal of hiding NAND flash page-read latency from the GPU. To measure how a static controller uses the HBF channel, we run the prior-art H 3 design [34], which prefetches bursts one layer ahead in compile-time or-der, and classify every fetched byte from HBF as consumed by the GPU or wasted. On-Channel Refresh Saturates the HBF Channel. A naïve HBF controller would refresh blocks on the same channel used by foreground reads, which is prohibitively expensive. A single block refresh costs one block erase plus one program per page: 

trefresh = tERASE + 1024 × tPROG = 54 .2 ms at tERASE = 3 ms 

and tPROG = 50 μs. Reading the block’s 1024 pages out before the erase adds up to 1024 × tR on top, which we conservatively omit. This is more than four orders of magnitude longer than a single page read and stalls all foreground reads to the refreshed block’s plane for the full duration. We quantify this refresh pressure under the H 3 baseline. Each flash block tolerates a conservative SLC read-disturb threshold of Ndisturb = 10 6 page reads [34, 51] before it must refresh. Intuitively, refresh opera-tions can be triggered by at least two mechanisms: ( i) in-place burst refresh , where all per-block read counters are initialized together, and all always-on blocks reach their refresh thresh-old on the same token; ( ii ) in-place distributed refresh , where per-block read counters are initialized spread apart, allowing the steady refresh stream to be interleaved with foreground reads. 64. FLINT Overview 

FLINT is a workload-driven HBF substrate whose goal is to sustain HBM-side memory throughput for LLM inference at low hardware and software overhead. The key idea of FLINT is to drive the HBF access path from the dynamic read stream the accelerator actually produces, rather than from a static 

compile-time prediction, exploiting the burst-granular, read-only nature of weight access. FLINT realizes this idea with three mechanisms: ( i) a hardware burst-buffer controller (§4.1); (ii ) phantom-plane refresh (§4.2); and ( iii ) read-only FTL (§4.3). 

4.1. Burst-Buffer Controller 

The burst-buffer controller is a hardware unit in the HBF base die that converts the accelerator’s fine-grained cache line read stream into coarse-grained, plane-parallel HBF bursts. Its goal is to keep the HBF datapath continuously occupied without requiring an HBM-side SRAM staging buffer or prefetch hints. Fig. 7 shows the three main components of the burst-buffer controller. First, the cache request queue ( 1 in Fig. 7) buffers cache line read requests to HBF-resident weights after the HBM base die’s address decoder redirects them to the HBF base die. The cl-to-page mapping table bridges the granularity mismatch between accelerator cache line requests and the NAND flash page-read primitive, since a single page-read op-eration can serve multiple cache lines that reside in the same physical page. The burst-buffer controller operates in three main steps, as shown in Fig. 7. In the first step, cache line requests (from the accelerator) enter the cache request queue ( 1 ) and are grouped in the cl-to-page mapping table ( 2 ) according to their target

In the sec-ond step, the burst scheduler dequeues the first page-level group (following the pre-defined scheduling algorithm) and issues it as burst#0 , targeting (pg#0, blk#0) ( 3 ). Each plane activates blk#0 and senses pg#0 in parallel ( 4 ), paying one NAND flash page-read latency to fill its page buffer with the plane-resident slice of burst#0 ( 5 ). In the third step, while

blk#1 ’s pg#0 in parallel ( 7 ); the new data fills the page buffer, while burst#0 ’s data moves into the cache buffer and contin-ues draining ( 8 ). Because the page and cache buffers are dis-tinct per-plane latches, the NAND flash sense for the next burst overlaps with the I/O drain of the current burst. In steady state, the controller presents one complete burst to the HBM base die every drain interval, rather than every page-read latency plus drain interval. This is the timing condition required to reach peak HBF read bandwidth. The pipeline is self-sustaining: the cl-to-page mapping table observes the pending request stream, and the scheduler can issue the next burst as soon as the current burst moves from the page buffers to the cache buffers. Thus, FLINT exploits the existing per-plane page and cache buffers in HBF to hide NAND page-read latency without compiler-inserted prefetches or a dedicated SRAM latency-hiding buffer. 

4.2. Phantom-Plane Refresh 

Phantom-plane refresh is a background-maintenance mecha-nism that removes NAND flash refresh from the accelerator-visible read path. The mechanism provisions one additional physical flash plane per flash die and uses it as a rotating 

phantom-plane . At any time, N logical planes serve foreground flash reads (from the accelerator), while the extra phantom-plane absorbs refresh traffic in the background. Each block carries a read counter that trips at the read-disturb threshold, with trip-points staggered so that blocks fall due as a steady trickle rather than a storm (Sec. 3); a due block of the current source plane receives an ECC-corrected copy, page by page, into a free block of the phantom-plane. Once a block’s copy completes, the phantom-plane refresh controller remaps that block in a block-granular relocation table, erases the vacated block, and returns it to the free-block pool. The vacated blocks of the source plane accumulate into the next phantom-plane, so the phantom role rotates round-robin through the physi-cal planes and every plane is reprogrammed once every N +1 

rotation periods Trot .Fig. 8 shows the four new hardware structures that com-pose the phantom-plane refresh controller (plus the standard ECC engine). First, the per-block refresh state holds one read counter per block, which triggers refresh at the staggered dis-turb threshold, and the block-granular relocation table with its free-block pool, which records the physical block backing each logical block. The controller updates the relocation table one block at a time as copies complete, so every foreground read 7observes a consistent, single-cycle mapping. A small logical-to-physical (l2p) plane map records which physical plane currently holds the phantom role and masks it from the read stripe. Sec-ond, the migration bitmap tracks which (block, page) en-tries of the source plane have already been copied into the phantom-plane per-rotation. The migration bitmap is required because LLM inference rereads hot weight pages many times within a rotation period, while each page must be programmed into the phantom-plane only once. Without avoiding duplica-tion, the refresh path would try to program a page at every read, causing either an overflow over the refresh path or back-pressure foreground reads due to the mismatch between page read and programming throughput. 1 Third, a program queue 

decouples bitmap admission from NAND flash programming. Foreground reads opportunistically migrate hot pages into the phantom-plane, but they may not touch every (block, page) entry of the source plane within a rotation period. 4.3. Read-Only FTL Design 

FLINT uses a read-only FTL to translate each logical LLM weight-burst request into the physical HBF (block, page) 

coordinate read by the burst-buffer controller. Concretely, FLINT employs a single burst translation table in the HBF base die. Each entry maps a logical burst index to a physi-cal (block, page) coordinate. With 2 MB bursts on a 512 GB stack, the table contains 256 K entries and occupies about 1 MB of base-die SRAM, several orders of magnitude smaller than a page-granular FTL. The table is populated once from the compiler-emitted weight layout during model load and remains constant throughout inference. Thus, every foreground access performs a single-cycle SRAM lookup and obtains the physical coordinate used by the burst-buffer controller to issue the cor-responding plane-parallel read. The responsibilities normally handled by a full FTL are either unnecessary or moved off the foreground path. Out-of-place updates and garbage collection can be avoided because weights are not modified during infer-ence. Wear leveling is provided implicitly by phantom-plane refresh (§4.2), which rotates the phantom role and reprograms planes uniformly over time. The temporary exclusion of the current phantom plane is handled by the logical-to-physical plane map maintained by the refresh controller. 

4.4. Write Path: Model Load and Persistence 

Model Load and Address Striping. The runtime writes the model once at deployment time using a fixed mapping function that places each 2 MB burst in the physical layout expected by the burst-buffer controller. The layout ensures that one burst can be fetched by a single plane parallel NAND sense. An HBF Gen-1 SLC stack with capacity C = 512 GB 

and burst size B = 2 MB contains Nburst = C/B = 2 18 

bursts. Each burst is striped across all D×P = 16 ×32 = 512 

planes P of the HBF stack with D dies, one 4 kB slice per plane. For burst index b ∈ [0 , N burst ) and Npg/blk = 1024 

pages per block, the common physical coordinate is block( b) = 

⌊b/N pg/blk ⌋ and page( b) = b mod Npg/blk . Slice s ∈ [0 , 512) of the burst is placed at this same (block, page) coordinate in die( s) = ⌊s/P ⌋ and plane( s) = s mod P . Thus, each logical burst maps to one physical (block, page) coordinate 8that is shared across all 512 planes, while the slice-to-plane assignment is implicit. The burst translation table (§4.3) stores only the compact (block, page) coordinate for each logical burst index. 

Power-Loss Recovery. Although HBF is non-volatile, FLINT does not rely on preserving resident weights across an un-planned power loss. The outage duration is unbounded, and guaranteeing correctness after arbitrary retention drift would require persistent refresh state, read-disturb counters, and recovery metadata. Maintaining this state would reintro-duce write-path support that FLINT deliberately keeps off the foreground inference path. Instead, FLINT treats every power-up as a clean installation (which we estimate as taking 

terase + treload ≈ 6.7 min ). 

5. Methodology 

We evaluate FLINT with an in-house trace-driven simulator that models the five tiers a weight read crosses, namely the streaming multiprocessorss (SMs), the on-die L2 cache, HBM, the staging buffers, and HBF. It consumes a per-SM stream of compute, memory, communication, and synchronization events produced by the WSE workload model [69]. In multi-package configurations, it charges every transfer that crosses a GPU package boundary and stalls each GPU package at a layer barrier until its peers arrive, so the multi-package baselines pay their interconnect and synchronization costs. We calibrate our HBM model against Ramulator 2.0 [70], driving it with the address streams from our LLM inference traces spanning four batch sizes and four context lengths. We observe from Ramula-tor that the sustained-to-peak HBM bandwidth is 67.8–69.9 % and does not vary with model, batch size, or context length. We faithfully model a B200-class accelerator [21], deriving arith-metic from the tensor shapes the trace carries and executing it at the product of peak throughput and a machine-utilization factor. Resolving arithmetic analytically and spending fidelity on the memory system is the same approach that recent aca-demic LLM-inference simulators take [71]. Our energy model charges memory and inter-GPU traffic per bit while GPU arith-metic is computed per operated byte. Table 2 lists our system parameters.

7. Related Work 

To our knowledge, FLINT is the first HBF substrate that sustains high HBF bandwidth on the LLM decode critical path without a dedicated HBM-side SRAM staging buffer or compiler-emitted prefetch hints. FLINT co-designs a runtime-aware burst-buffer controller, phantom-plane refresh, and a burst-granular read-only FTL for immutable LLM weight ac-cess. In this section, we contrast FLINT with prior work along two themes. 

HBF-Based Systems. Prior HBF-based systems for LLM infer-ence [34–37] commonly employ ( i) an HBM-side SRAM staging buffer that holds prefetched weight bursts, and ( ii ) compiler- or programmer-emitted hints fill this buffer at layer boundaries. Our analysis shows that this organization cannot saturate the HBF channel bandwidth, since static issue memory request order does not reliably match the runtime memory access order under MoE routing and attention reuse. Other HBF-related works [38, 39] are orthogonal to FLINT. MemExplorer [39] explores heterogeneous memory systems that include HBF as one possible capacity tier but does not propose new HBF control mechanisms. FLINT provides such a mechanism and raises the attainable bandwidth of the HBF tier toward the HBF bandwidth channel ceiling assumed by [39]. Lincoln [38] tar-gets LPDDR-interfaced compute-enabled flash and near-flash compute. In contrast, FLINT targets HBF attached through the HBM-side D2D link, requires no in-flash compute, and ob-tains its bandwidth from plane-parallel burst staging through unmodified NAND flash dies. 

Non-Volatile Memory for LLM Inference. Several prior works [28, 30–32, 76, 77] integrate non-volatile memory into deep neural network (DNN) and LLM inference systems at sev-eral layers of the stack. FLINT differs from these systems in three ways: ( i) the non-volatile tier is on-package HBF reached through the HBM-side D2D link rather than off-package stor-age; compute remains on the GPU rather than moving into the storage device; and ( ii ) the storage-class FTL is replaced with a burst-granular read-only translation table on the HBF base die, eliminating OS-mediated page faults, page-granular meta-data, and write-path machinery from the foreground inference path. 

8. Conclusion 

We introduce FLINT, a workload-driven HBF substrate that specializes the HBF access path for the burst-granular, read-only behavior of LLM inference weights through three mech-anisms: a hardware burst-buffer controller that stages bursts in the buffers already inside each HBF die, phantom-plane re-fresh that keeps NAND maintenance off the foreground read path, and a read-only FTL that reduces address translation to a compact burst-granular table. We conclude that workload-specialized HBF control turns on-package flash into a practical capacity tier for frontier LLM inference.
