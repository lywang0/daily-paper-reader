## 摘要
大语言模型（LLM）推理服务日益受内存而非算力的限制。随着长上下文和长形式推理工作负载的普及，键值（KV）缓存在LLM令牌生成（即解码）过程中主导了内存占用和内存流量。特别是，HBM容量已成为稀缺且昂贵的资源，严重限制了推理批大小和系统吞吐量。本文提出了OasisKV，一种以内存为中心的LLM推理系统设计，通过在LLM解码期间将完整KV缓存存储与HBM解耦来缓解HBM容量压力。由于解码时的注意力天然稀疏，OasisKV在HBM中仅保留最相关令牌的KV条目用于注意力计算。我们观察到，未来的重要令牌可以通过投机解码（SD）生成的前瞻令牌提前准确预测。OasisKV采用高效的注意力后台流水线来识别重要的KV块，然后从更高容量的内存层级（如主机或远程内存）预取这些块，并在下一步解码使用前将其暂存于HBM中。我们基于vLLM实现了OasisKV。在2,048令牌的KV预算下，前瞻预测的准确性足以将精度保持在完整注意力的0.7个点以内。这使得OasisKV能够将稀疏性转化为吞吐量增益：在推理工作负载上，相比密集vLLM达到1.69倍吞吐量，精度损失仅0.1个点；在多GPU长上下文服务上最高可达2.1倍。在预填充-解码分离下，OasisKV达到约2倍的密集吞吐量，同时每个请求的KV需求减少6.5–9.7倍，且解码节点主机内存比完整KV传输减少2.2–2.6倍。

## Abstract
Large language model (LLM) inference serving is increasingly constrained by memory rather than compute. As long-context and long-form reasoning workloads become more prevalent, the key-value (KV) cache dominates both memory footprint and memory traffic during LLM token generation, i.e., decode. In particular, HBM capacity has become a scarce and costly resource that heavily limits inference batch size and system throughput. This paper presents OasisKV, a memory-centric LLM inference system design that alleviates HBM capacity pressure by decoupling full KV-cache storage from HBM during LLM decoding. Because decode-time attention is naturally sparse, OasisKV keeps only the KV entries of the most relevant tokens in HBMs for attention computation. We observe that future important tokens can be predicted accurately in advance using lookahead tokens drafted by speculative decoding (SD). OasisKV employs an efficient attention background pipeline to identify important KV blocks. They are then prefetched from higher-capacity memory tiers (e.g., host or remote memory) and staged in HBMs before being used in the next decode step.   We implement OasisKV based on vLLM. The lookahead prediction is accurate enough to keep accuracy within 0.7 points of full attention under a 2,048-token KV budget. This lets OasisKV turn sparsity into throughput gain: $1.69\times$ over dense vLLM on the reasoning workload at 0.1 points of accuracy loss, and up to $2.1\times$ on multi-GPU long-context serving. Under prefill--decode disaggregation, OasisKV reaches about $2\times$ dense throughput while admitting each request with $6.5$--$9.7\times$ less KV and holding $2.2$-$2.6$ less decode-node host memory than full KV transfer.

# OasisKV 论文总结

## 1. 核心问题与研究动机

- **背景**：LLM 推理服务已从计算受限转向内存受限。随着长上下文（long-context）和长形式推理（如 agentic 工作负载）的普及，KV 缓存（Key-Value Cache）在解码阶段同时主导了内存**容量占用**和**内存流量**。
- **瓶颈**：HBM（高带宽内存）容量稀缺且昂贵，直接限制了推理的批大小（batch size）和系统吞吐量。例如，一个 32B 类 GQA 模型在 32.7K 平均上下文下，单请求 KV 缓存约需 8.6 GB，仅能支撑极少并发请求。
- **现有方案的不足**：
  - **稀疏注意力**（如 NSA、Quest）：可以减少计算和 KV 读取，但 KV 缓存仍需完整驻留 HBM，不解决容量问题。
  - **KV 检索**（如 ShadowKV、RetroInfer）：将完整 KV 放在主机内存，按需取回，但取回延迟在解码关键路径上，且带宽受限（图 2 显示即使只取 10% 的 KV 也会显著增加 TPOT）。
  - **KV 预取**（如 InfiniGen、FreeKV）：尝试预测并预取，但预测不够准确、缺少生产级跨层内存管理，且难以支持多 GPU 和 PD 分离。
- **核心问题**：如何在解码过程中将 KV 缓存扩展到 HBM 之外，同时保证低延迟、高吞吐和可接受的精度？

## 2. 方法论：OasisKV 的设计

### 核心思想
- **解耦存储与计算**：完整 KV 缓存存放于主机 DRAM 或远程内存，GPU HBM 仅保留每步注意力实际需要的稀疏工作集（bounded working set）。
- **利用投机解码（SD）的 lookahead 信号**：投机解码产生的 draft token（前瞻令牌）可准确预测下一步注意力将关注的重要 KV 块，无需训练专用预测器。
- **异步预取流水线**：将 top-K 预测、KV 选择、KV 传输三个步骤放在后台与前台解码重叠执行，使 off-GPU 传输不在关键路径上。

### 关键技术细节
1. **Look-ahead Attention（前瞻注意力）**：
   - 前台：正常 token 和 draft token 共享同一前向传播，将两者注意力拼接处理，仅读取一次稀疏 KV 工作集。
   - 后台：draft query 扫描压缩键摘要（compressed-key summaries），对全量 KV 块进行全局 top-K 排名（采用 Quest 风格的逐块 min/max pooling 摘要，占完整 KV 的 1/16），从而预测下一步需要的块。
   - 实验表明，用 draft token 预测的 top-K 集与真实 next-token 的 top-K 集逐层一致性平均达 98.74%。

2. **全异步后台流水线**：
   - 每层维护独立的预测→选择→传输链，各层任务相互独立，可并行执行。
   - 使用多个 CUDA stream 和 CUDA events 协调依赖，前台只在执行每层注意力前等待该层上一轮的 KV 传输完成（layer-local sync）。
   - 流水线稳态周期由最慢阶段决定：\( T_{pipe} = \max(T_{pred}, T_{select}, T_{transfer}) \)。

3. **Delta Selection 和 Capped Eviction（差额选择与封顶淘汰）**：
   - 选择阶段：先比较预测集与当前驻留集，只传输缺失块；采用 LRU 风格淘汰，限制每步每个 KV head 最多传输 C 个块，从而将 PCIe 流量控制在解码带宽预算 \( C_{token} = B_{link} \cdot T_{decode} \) 内。

4. **KV 内存管理与调度（vLLM 集成）**：
   - 保留原有 GPU 和 CPU page table，新增 head-wise 逻辑到逻辑映射，使不同 KV head 可维护不同的稀疏块集合，且不需跨 GPU 同步。
   - 请求在上下文超过阈值后从密集解码切换为稀疏解码，GPU 页表不变，仅更新 head-wise 映射。

5. **远程部分获取（Remote Partial Fetching, RPF）**：
   - **部分传输**：仅传输第一解码步骤所需的 KV 块（由 prefill 节点额外执行一次解码来确定）、压缩键缓存和 draft KV 状态，避免全量 KV 网络传输。
   - **网络预取**：解码过程中缺失的块通过后台流水线从远端 staging pool 按需读取，重复块只传一次，实现“按需填充”的稀疏驻留。
   - 好处：降低 TTFT、减少解码节点主机内存占用（每请求 KV 从全量变为 top-K 联合集大小）。

## 6. 主要结论与发现

- **性能提升**：
  - 单 GPU Qwen3-8B：相比 dense vLLM，吞吐最高提升 **1.69×**（AIME24 真实负载，精度损失仅 0.1 点）；合成负载 16K 上下文下最高 **2.1×**（1,398 vs. 676 tok/s）。
  - 多 GPU Qwen3-235B（TP8）：长上下文吞吐提升最高 **1.9×**（16K 下 1,102 tok/s）。
  - PD 分离：吞吐约为 dense 的 **2.1–2.3×**（24K/32K 上下文下 1,204/888 tok/s）。
- **精度保障**：
  - 在 2,048 token KV 预算下，与 full attention 精度差距 **≤0.7 点**；实际多数场景在 0.1–0.6 点内。
  - 与 Quest、FreeKV 相比，OasisKV 的精度离其 full-attention 锚点更近。
- **内存与网络节省**：
  - RPF 使每个请求的 KV 传输量减少 **6.5×（24K）和 9.7×（32K）**，但解码过程中的 drift 会部分抵消，最终端到端节省约 1.33–1.5×（无 fetch cap），在 fetch ratio 0.05 时可达 2.2×。
  - 解码节点主机内存占用减少 **2.2×–2.6×**。
- **关键机制验证**：
  - fetch cap（0.05）可在几乎不损失精度（75.94 vs. 76.04）的情况下，将吞吐从 824 tok/s（fetch all）提升至 2,083 tok/s（2.5×）。
  - draft token 的 lookahead 预测精度高（平均 top-K 一致性 >98%），优于 previous-token 代理。

## 7. 优点

- **训练无关**：利用投机解码天然产生的 draft token 作为预测信号，无需训练专用预测器或绑定模型架构，通用性强。
- **系统完备**：基于 vLLM 的 V1 引擎实现，支持多 GPU（TP）、PD 分离和分层 KV 存储，接近生产级部署。
- **异步流水线设计巧妙**：将预测、选择、传输拆分为跨层独立的 CUDA 流，用 CUDA events 同步，实现了细粒度的 overlap。
- **带宽感知**：通过 capped eviction 主动限制每步 PCIe/网络流量，将传输量控制在解码延迟预算内，避免带宽成为瓶颈。
- **评估全面**：从性能、精度、消融到网络流量和 TTFT 建模，覆盖多场景，且对比方法选取合理（包含 SOTA 检索/预取系统）。
- **结果直观**：通过 roofline 模型和头部预测准确率等分析，清晰地解释了设计动机和优势来源。

## 8. 不足与局限

- **依赖 draft 模型质量**：预测准确性依赖 EAGLE-3 等 draft 头的可用性，若 draft 模型效果差，前缀预测精度可能下降。
- **未支持 prefix caching**：文中提到原型尚未实现 prefix caching，仅做了分析模型估计，实际收益有待验证。
- **全量 KV 仍驻留 prefill 节点**：尽管 decode 节点内存占用降低，prefill 节点仍需保留完整 KV 直到请求完成，可能将压力转移给 prefill 或远程内存池。
- **超参数敏感**：自稀疏阈值、top-K 大小、fetch ratio、块大小等需针对工作负载调优，文中未给出自动化调参机制。
- **硬件覆盖有限**：仅在 H100 + PCIe + RoCE 环境下评估，未涉及 A100、AMD 或 CXL 等新兴内存/互联技术。
- **对比不完整**：部分基线在特定场景下无法运行（如多 GPU），且未与更新的系统（如 KVDrive、HiSparse）直接对比。
- **未来工作未实现**：当前强制拒绝 draft token，尚未将投机解码的接受率与预取联合优化，存在进一步提升空间。
