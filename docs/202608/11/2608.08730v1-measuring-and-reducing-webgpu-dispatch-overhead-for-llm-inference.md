## 摘要
大型语言模型被部署到多种环境中，从互联网浏览器到边缘设备，而WebGPU作为一种现代跨平台标准应运而生。基于浏览器的LLM推理引擎已经大量涌现，但WebGPU每次操作的调度开销仍缺乏系统的表征。在这项工作中，我们引入了一种顺序调度测量方法，并表明朴素的单操作测量会因混淆调度与同步而高估每次调度的成本。使用我们的方法，我们测量了每次调度的成本，并表明它与所使用的数据类型无关。我们证明，在批量大小为1时，调度开销（而非内核质量）是瓶颈，并将调度次数确定为根本原因。因此，我们得出结论：在批量大小为1时，WebGPU中LLM推理优化的有效途径是减少调度次数。我们的研究结果表明，调度摊销（在推理引擎和WebGPU规范中）是实现实用浏览器推理的路径。

## Abstract
Large Language Models are deployed to multiple types of environments, from internet browsers to edge devices, and WebGPU serves as a modern cross-platform standard. The engines for browser-based LLM inference have proliferated, yet the overhead of WebGPU per-operation dispatch remains poorly characterized. In this work, we introduce a sequential-dispatch measurement method and show that naive single-operation measurements overestimate per-dispatch cost by conflating dispatch with synchronization. Using our method, we measure the per-dispatch cost and show that it is independent of data type used. We show that the dispatch overhead, not kernel quality, is the bottleneck at batch size 1, and isolate the dispatch count as the cause. Therefore, we conclude that at batch size 1, the effective approach to LLM inference optimization in WebGPU is reducing dispatch count. Our findings point to dispatch amortization, in the inference engines and in the WebGPU specification, as a path to practical browser-based inference.

- **研究背景**：LLM 正被广泛部署到浏览器和边缘设备中，WebGPU 作为现代跨平台 GPU 标准，是支撑浏览器端 LLM 推理的关键基础设施。已有多种基于 WebGPU 的推理引擎（如 WebLLM、Transformers.js、LlamaWeb）涌现，但其性能优化大多沿袭传统路径（量化、内核优化、内存效率），**WebGPU 逐操作（per-operation）调度开销的系统性刻画仍是空白**。
- **核心问题**：本文要回答两个关键问题：
  1. WebGPU 单次调度的真实成本到底是多少？如何准确测量？
  2. 在 batch size = 1 的 LLM 推理场景下，性能瓶颈究竟是 **调度开销** 还是 **内核质量**？
- **整体意义**：作者发现传统的单操作测量方法把“调度”和“同步”混为一谈，导致调度成本被高估约 20 倍；通过受控实验证明在 batch size = 1 时，**调度次数** 才是真正的性能瓶颈，而非内核计算质量。因此，WebGPU 上 LLM 推理优化的有效方向应是**减少调度次数**（如算子融合）和**调度摊销**（specification 层面的改进），这与传统 native 推理中“优化内核”的优先级形成鲜明对比。

## 二、方法论：核心思想与关键技术细节

### 1. 顺序调度测量方法（Sequential-Dispatch Measurement Method）
- **针对问题**：朴素单操作测量一次 dispatch 的耗时，实际上包含了 **调度本身** + **一次完整的 GPU-CPU 同步** 两部分的成本，后者在真实自回归解码中每个 token 只发生一次，而非每次操作都发生，因此该测量会严重高估 dispatch 成本。
- **核心思想**：模拟真实解码的同步模式——一次性提交 N 个 dispatch，最后只做一次同步，将总耗时除以 N，从而将一次性同步成本摊还掉，**分离出单次调度的真实边际成本**。
- **技术实现**：
  \[
  \text{per-dispatch cost} = \frac{T_{\text{total}} - T_{\text{sync}}}{N}
  \]
  其中 \( T_{\text{total}} \) 为 N 次 dispatch 加一次同步的总耗时，\( T_{\text{sync}} \) 为最终同步的耗时。
- **测量平台**：基于自研的 torch-webgpu 后端（PyTorch PrivateUse1 机制 + Dawn 实现），覆盖 Dawn 和 wgpu-native 两个 WebGPU 实现，Vulkan 和 Metal 两个后端，以及 NVIDIA、AMD、Intel、Apple 四家 GPU 厂商的硬件。

### 2. 受控内核融合实验（Controlled Kernel Fusion Experiment）
- **目的**：厘清吞吐量提升的真正来源——是调度次数减少，还是内核质量提升，抑或内存流量减少。
- **做法**：将前向传播中的操作逐步融合（如 RMSNorm、MLP gate/up/SiLU、K+V projection 等），将每 token 的 dispatch 数从 876 逐步降至 564。
- **控制变量**：
  - **内核质量不变**：融合前后使用相同的 WGSL shader，不改变计算本身；
  - **内存流量可忽略**：融合消除的中间内存流量约 1.8 MB，耗时 <1 μs；
  - **唯一显著变化**：dispatch 次数减少了 312 次。
- **推理逻辑**：如果吞吐量提升只能归因于 dispatch 次数减少，则说明调度开销而非内核质量是瓶颈。

## 三、实验设计：场景、基准与对比

- **工作负载**：LLM 自回归解码的前向传播（batch size = 1），非传统数据集评测，而是以模型前向传播中的 dispatch 行为为测量对象。
- **核心基准（Benchmark）**：
  1. **调度成本测量**：对比朴素单操作测量 vs. 顺序调度测量，在多种硬件和后端组合下进行（Dawn/Vulkan on RTX 5090、wgpu/Vulkan on RTX 5090、wgpu on AMD iGPU、Safari/wgpu on Apple M2、Chrome on RTX 5090 等）。
  2. **融合实验**：逐步融合 4 组算子，测量 dispatch 数量与吞吐量（tok/s）和 TTFT 的变化。
  3. **调度内部耗时分解**：将单次 dispatch 细分为 Submit、Encoder create、Encoder finish、Pass begin、Set pipeline、Set bind group、Pass end、Dispatch call、GPU sync 等步骤，找出主要开销来源。
- **对比方法**：
  - 朴素单操作计时（naive single-op timing）vs. 顺序调度计时（sequential method）；
  - 不融合（876 dispatches）vs. 逐步融合（636 / 588 / 564 dispatches）；
  - 不同数据类型（float32 vs. float16）下的调度成本对比；
  - 不同浏览器（Chrome、Safari；Firefox 因发现存在速率限制被排除）和不同 WebGPU 实现（Dawn、wgpu）的对比。

## 六、主要结论与发现

1. **朴素单操作测量严重高估调度成本**：通过将一次完整的 GPU-CPU 同步误计入单次调度，调度成本被高估约 **20 倍**（在部分平台上更高，如 Chrome 上达 63 倍），实际同步成本约为 450 μs。
2. **真实单次调度成本与数据类型无关**：
   - Vulkan 后端：**24–36 μs**；
   - Metal 后端：**32–71 μs**；
   - float32 和 float16 的结果一致，说明调度成本主要反映命令编码和提交，而非计算强度。
3. **调度次数（而非内核质量）是 batch size = 1 时的性能瓶颈**：在保持 WGSL shader 不变、内存流量节省可忽略（~1.8 MB, <1 μs）的条件下，将 dispatch 数从 876 减至 564，吞吐量提升 **53%**（TTFT 从 71.4 ms 降至 41.6 ms）。
4. **命令缓冲提交（Submit）是单次调度中的主要开销**：约占 CPU 端总耗时的 40%（12.9 μs），其次是 encoder 创建（6.4 μs）和 encoder finish（6.1 μs）；管线设置与绑定开销相对较小。这为 WebGPU 实现层面的优化提供了具体方向。
5. **优化建议**：在 WebGPU LLM 推理中，优先策略应为**减少调度次数**（算子融合、megakernel 式调度摊销），而非单纯追求内核微优化；更深层的改善可能需要 WebGPU 规范层面引入类似 CUDA Graphs 的命令图捕获与重放机制，但需与浏览器安全模型（逐操作校验）相权衡。

## 七、方法或实验设计的亮点

1. **测量方法的原创性**：顺序调度测量法精准地分离了“调度”与“同步”两类成本，直击朴素测量的系统性偏差，方法简洁且可复现。
2. **因果隔离的受控实验**：融合实验通过严格保持内核不变、量化内存流量影响可忽略，将吞吐量提升**唯一归因于 dispatch 次数减少**，逻辑链条清晰。
3. **多维度覆盖**：调度成本测量覆盖了四家 GPU 厂商、两种 WebGPU 实现、两种后端、两种数据类型和多个浏览器，结论具有较好的代表性。
4. **开源工具支撑**：基于自研 torch-webgpu 后端（开源、基于 PyTorch PrivateUse1 机制），降低了复现门槛，方便社区验证和扩展。
5. **细粒度性能分解**：对单次 dispatch 内部 9 个步骤的耗时分解，为后续 API 设计优化提供了具体的数据支撑（定位 Submit 为主要瓶颈）。
6. **与既有研究的互补性**：明确说明与 WeInfer（优化跨 token 同步）互补——本文优化的是每个 forward pass 内部的调度开销，WeInfer 优化的是同步阶段，两者可叠加。
