## 摘要
在统一内存系统上，端侧助手会同时运行基于GPU的LLM推理与CPU检索。在饱和的本地检索负载下，四个并发检索工作线程使两台M4系统上的第95百分位（p95）解码延迟升高60-61%，而预填充延迟仅升高5.7-6.9%。我们研究将LLM阶段作为受控LLM负载下独立CPU检索的准入信号。PHASEGATE为预填充和解码分别校准并发上限，在我们的基础M4配置上分别选择4和1。在积压队列下，其聚合检索吞吐量达到所测试的最佳可行固定策略的2.0倍，同时在全部七次留出运行中，两项p95 LLM延迟指标均不超过其无检索基线的1.25倍。一个不感知阶段的对照方案TimeGate，在不观察LLM阶段的情况下，将相同的两个限制用于由校准导出的调度。它取得了相近的检索吞吐量，但在每次运行中都违反了输出token延迟限制。M2和M2 Pro Mac mini复现了策略排序，而输出长度扫描表明，随着解码在每次请求中占比增加，该优势会缩小。

## Abstract
On-device assistants run GPU-based LLM inference alongside CPU retrieval on unified-memory systems. Under a saturated local-retrieval workload, four concurrent retrieval workers raise 95th-percentile (p95) decode latency by 60-61% on two M4 systems, whereas prefill latency rises by only 5.7-6.9%. We study LLM phase as an admission signal for independent CPU retrieval under controlled LLM workloads. PHASEGATE calibrates separate concurrency limits for prefill and decode, selecting four and one on our base-M4 configuration. Under a backlogged queue, it achieves 2.0 times the aggregate retrieval throughput of the best tested feasible fixed policy, with both p95 LLM latency metrics within 1.25 times their no-retrieval baselines in all seven held-out runs. A phase-blind control, TimeGate, uses the same two limits on a calibration-derived schedule without observing LLM phase. It achieves similar retrieval throughput but violates the output-token latency limit in every run. M2 and M2 Pro Mac minis reproduce the policy ordering, while output-length sweeps show that the advantage narrows as decode occupies more of each request.

## 1. 核心问题与整体含义

- **研究背景**：端侧助手通常在统一内存 SoC 上同时运行两类任务：GPU 上的 LLM 推理，以及 CPU 上的本地检索、上下文记忆查找、索引维护、解析和工具执行。
- **关键矛盾**：Apple Silicon 等统一内存架构中，CPU 与 GPU 共享同一内存池。CPU 检索的指针追逐、图遍历会与 GPU LLM 推理的权重流式读取竞争内存服务；而服务器离散 GPU 的 HBM 与主机 DRAM 分离，问题形态不同。
- **核心观察**：LLM 推理分为 prefill 和 decode 两个阶段。prefill 并行处理 prompt token，权重复用较多；decode 逐 token 生成，重复流式读取模型状态。实验发现，4 个并发 HNSW 检索工作线程会使 M4 系统上的 p95 解码延迟 TPOT 上升 60–61%，而 prefill 敏感指标 p95 TTFT 仅上升 5.7–6.9%，呈现显著“阶段非对称干扰”。
- **研究目标**：不修改 GPU 上的 LLM 执行，而是把 LLM 的当前阶段作为独立 CPU 检索任务的准入信号，在 prefill 阶段允许更高检索并发，在 decode 阶段收紧并发，从而在不破坏 LLM 延迟约束的前提下提高检索吞吐。

## 2. 方法论：PhaseGate

- **核心思想**：为 prefill 和 decode 分别设置 CPU 检索并发上限 \(p\) 与 \(d\)，允许 \(p > d\)。传统固定策略使用单一上限，例如 Fixed-1 表示全程并发上限为 1；PhaseGate 用“阶段感知准入”替代“阶段无关固定上限”。
- **标定流程**：
  - 给定一个相对无检索基线的延迟预算 \(B\)，论文主实验取 \(B = 1.25\)，即允许 p95 TTFT 和 p95 TPOT 相对无检索基线最多上升 25%。
  - 枚举候选 \((p,d)\) 组合，例如 PhaseGate 2→0、2→1、4→0、4→1、4→2。
  - 每个候选运行多次，检查是否在每次运行中两项 p95 延迟都不超过 \(B\)。
  - 在满足延迟约束的候选中，选择检索吞吐 QPS 最高者。基础 M4 上选中 PhaseGate 4→1，即 prefill 并发上限 4、decode 并发上限 1。
- **运行时机制**：
  - instrumented MLX-LM harness 发出 prefill 和 decode 事件。
  - 当活跃检索调用数低于当前阶段上限时，才准入队列中的新检索调用。
  - 已有调用**不抢占**。当阶段从 prefill 切到 decode、上限从 4 降到 1 时，正在运行的调用会继续完成，新调用等待活跃数降到 1 以下。
  - decode 上限是“准入阈值”，不是对活跃工作的瞬时硬上限；因此要求残余工作能相对 decode 快速排空。
  - 不请求 CPU 核绑定或线程优先级 QoS 覆盖。
- **延迟指标**：
  - TTFT：请求开始到第一个 decode step 完成的时间。
  - TPOT：后续 decode step 之间的 token 间隔。
  - M4 主实验采用“先请求内 p95，再跨请求 p95”的 TPOT，并直接跨请求计算 p95 TTFT。
- **对照方法 TimeGate**：
  - 使用与 PhaseGate 相同的高/低并发上限，但按校准导出的 wall-clock 调度交替切换，不观察运行时 LLM 阶段。
  - 用于隔离“阶段对齐”本身是否带来价值。

## 3. 实验设计

- **模型与推理框架**：
  - 4-bit Qwen2.5-1.5B，使用 MLX-LM v0.31.3。
  - 合成执行负载：2,048 个输入 token ID，后接 128 个顺序单 token decode forward pass。
  - 不采样 logits，不把生成 token 回馈模型，因此不测试自然语言生成质量，只控制执行形态。
- **检索负载**：
  - FAISS HNSW 只读索引，100,000 个 384 维向量，图连接度 \(M=32\)，efSearch=128，top-k=10。
  - 检索任务独立于当前 LLM 请求，不是该响应的前置 RAG 检索。
  - 队列在活跃期间保持非空，以测量 LLM 延迟约束下的聚合检索容量。
  - 并发单位是“调用”，每个单线程 FAISS 调用处理 16 条向量查询；吞吐按完成的向量查询数计。
- **对比策略**：
  - 固定并发：Fixed-0、Fixed-1、Fixed-2、Fixed-4。
  - PhaseGate：2→0、2→1、4→0、4→1、4→2。
  - 阶段盲控制：TimeGate 4/1。
- **主要实验场景**：
  - 基础 M4 Mac mini 校准与主评估。
  - 七次留出配对随机运行，每次每策略 250 个 LLM 请求。
  - 间歇检索需求：检索活跃占 wall-clock 的 5%、25%、100%，每个 duty 做 5 组三策略匹配比较。
  - 输出长度敏感性：M4 上 64、128、512 output tokens；M2 Mini 上 128 和 512 tokens。
  - 跨设备复现：M4 Mini、M2 Mini、M2 Pro Mini；另有 M4 Air 用于访问模式控制。
  - 非抢占工作分析：统计 decode 开始后残余调用排空时间、服务时间、过渡开销。
- **Benchmark 性质**：没有使用外部数据集，benchmark 是受控合成 LLM 执行 trace + 积压 H
