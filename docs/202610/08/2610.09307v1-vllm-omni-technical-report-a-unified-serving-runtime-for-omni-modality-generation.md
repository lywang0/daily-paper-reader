## 摘要
与智能系统的交互正在超越以文本为中心的聊天机器人和编码智能体。语音原生助手、视觉生成与编辑、世界模型环境以及机器人动作循环，都需要能够输出文本、音频、图像、视频和动作的模型。这些模型在执行模式上各不相同：多阶段自回归全模态与 TTS 流水线、迭代式扩散或流匹配生成器，以及跨步骤携带状态的更长时间运行的世界模型或机器人循环。因此，服务不再是一个单一的文本解码循环，而是一个异构的多阶段工作流，涉及跨阶段传输、流式传输和会话形态的交互。现有推理栈通常针对单一架构族进行优化。LLM 服务器深化了自回归调度和 KV 管理，而扩散栈则深化了去噪和并行生成。二者都没有为通过独立生成器输出语音、像素或动作的流水线提供共享控制平面，因此生产部署常常退化为跨互不相交运行时的临时拼凑。我们提出 vLLM-Omni，一个面向全模态生成的统一服务运行时。vLLM-Omni 将每个工作负载组织为单一编排器下的多阶段流水线，该编排器接纳请求、推动请求跨阶段推进，并解复用流式输出。专用引擎和阶段副本提供计算；连接器在数据平面上承载大负载；面向会话的控制支持长时双工、世界模型和机器人工作负载。本报告涵盖架构（阶段级 KV 路径、副本池、多硬件平台和效率栈），以及面向全模态、TTS、图像/视频、世界模型、机器人和双工工作负载的 OpenAI 兼容 API 与 OpenPI API。我们在 H100 上的多模态 nightly CI 上进行评估（TTS 和 MiniCPM-o 在 H200 上），重点关注 Qwen3-Omni。

## Abstract
Interaction with intelligent systems is expanding beyond text-centric chatbots and coding agents. Speech-native assistants, visual generation and editing, world-model environments, and robot action loops require models that emit text, audio, images, video, and actions. These models differ in execution pattern: multi-stage autoregressive omni and TTS pipelines, iterative diffusion or flow-matching generators, and longer-lived world-model or robot loops that carry state across steps. As a result, serving is no longer a single text decode loop, but a heterogeneous multi-stage workflow with cross-stage transfer, streaming, and session-shaped interaction.   Existing inference stacks are typically optimized for one architecture family. LLM servers deepen autoregressive scheduling and KV management, while diffusion stacks deepen denoising and parallel generation. Neither provides a shared control plane for pipelines that emit speech, pixels, or actions through separate generators, so production deployments often fall back to ad-hoc composition across disjoint runtimes.   We present vLLM-Omni, a unified serving runtime for omni-modality generation. vLLM-Omni organizes each workload as a multi-stage pipeline under a single orchestrator that admits requests, advances them across stages, and demultiplexes streaming outputs. Specialized engines and stage replicas provide compute; a connector carries heavy payloads on the data plane; and session-oriented control supports long-lived duplex, world-model, and robot workloads.   This report covers the architecture (stage-level KV paths, replica pools, multi-hardware platforms, and efficiency stack) and OpenAI-compatible and OpenPI APIs for omni, TTS, image/video, world-model, robot, and duplex workloads. We evaluate on the multimodal nightly CI on H100 (TTS and MiniCPM-o on H200), focused on Qwen3-Omni.

## 1. 核心问题与研究动机

- **背景迁移**：与智能系统的交互正从纯文本聊天/编码智能体，扩展到语音原生助手、视觉生成与编辑、世界模型环境、机器人动作循环，模型需要同时输出文本、音频、图像、视频与动作。
- **执行模式高度异构**：
  - 多阶段自回归全模态（thinker → talker → code2wav）与 TTS 流水线；
  - 迭代式扩散 / 流匹配生成器（DiT 去噪多步）；
  - 长时世界模型 / 机器人循环，需跨步携带状态。
- **现有推理栈的缺口**：
  - LLM 服务系统（vLLM、SGLang）擅长 AR 解码、KV 管理与连续批处理，但不原生支持通过独立生成器输出语音、像素、动作的多阶段流水线；
  - 扩散栈（Diffusers、xDiT 等）擅长去噪、缓存与并行，但缺少跨 AR 阶段、跨阶段传输、会话交互的共享控制平面；
  - 生产部署常退化为多个互不相交运行时的"临时拼凑"，重复了准入与生命周期逻辑，无法把阶段级流式与 KV 传输当作单一请求管理。
- **核心主张**：服务不再是一个文本解码循环，而是一个带跨阶段传输、流式输出、会话形态交互的**异构多阶段工作流**，需要一个统一控制平面。

## 2. 方法论

### 2.1 核心思想：阶段图 + 单一编排器
- 每个工作负载被组织为**多阶段流水线**：一个 stage 绑定一个模型组件、一个执行引擎和明确的资源预算；stage 之间交换类型化中间状态，可同机或跨进程/设备/主机拆分。
- 上层由**单一 Orchestrator** 持有请求准入、跨阶段推进、客户端可见进度与完成判定；它不调度 token、不管分页 KV、不做去噪步调度、不搬运大张量。
- 配置分三层：pipeline registry（逻辑阶段/默认引擎/桥接处理器）、deploy overlay（放置、连接器、流式边、采样默认值、硬件覆盖）、可选并行策略（TP/DP/stage-replica 展开为设备布局）。

### 2.2 请求准入与推进
- 两个编程入口共用同一引擎栈：同步离线路径 + 异步在线路径（生产服务器用）；OpenAI 兼容 HTTP/WebSocket 与 OpenPI 均为异步路径上的薄适配器。
- 控制平面状态：记录 pipeline 端点、各阶段采样配置、粘性提交水位、可恢复流式簿记；**完成条件是"模态集合完成"**——每个请求带 final-output stage 集合，全部完成才算结束（如 omni 语音可一边流文本一边合成波形）。
- 推进循环：准入 → 提交 stage 0 → 轮询/事件驱动唤醒 → 结果分两路：①客户端投递（多阶段可并发产出增量输出）；②阶段推进（batch 全量路径或 chunked 路径）。
- **async_chunk 跨阶段分块流式**：下游阶段预提交占位请求并预热，上游产出 token/codec 帧即经连接器发布，下游并行解码；编排器保留生命周期所有权但抑制冗余控制面转发。这是降低首包时延（TTFP）的核心机制。
- 客户端流式被建模为"请求进度"：输入 chunk 与输出 delta 共享同一请求身份；未知 ID 更新被丢弃，防止已中止请求被"复活"；支持生成中 prompt 更新（交互提交）。
- 支持 AsyncOmni 的 pause/resume 与 sleep/wake。

### 2.3 执行引擎与阶段副本
- **AR worker**：复用 vLLM 的 worker/scheduler，连续批处理、token 采样、KV 管理，可导出 hidden states / pooled tensors 作为跨阶段产物。
- **Generation worker**：非自回归 codec / 波形阶段（如 code2wav），返回张量而非词表 logits。
- 每个阶段可独立选择 **vLLM V1 runner** 或实验性 **MRv2**（请求级采样与生成状态驻留设备、重放 FULL CUDA graph、支持自定义采样与把采样 token 嵌入传给下一阶段）。
- **扩散引擎**：独立调度器 + 去噪驱动，支持批内共享、跨去噪步的连续批处理、步级可调度（用于流式帧/中途取消）；TeaCache、Cache-DiT、序列/CFG 并行、offload/量化都挂在这一层。
- **AR–Diffusion 后端**：在扩散引擎上加入基于 vLLM block manager 的 runner-local 分页 KV 池，使世界模型在分块 rollout 中保留会话级 KV。
- **StagePool 与副本**：每个逻辑阶段一个池，可含多个独立副本引擎；粘性亲和保证流式更新/多轮追加/阶段内 KV 局部性落在同一副本，未绑定请求按轮询或最短队列负载均衡；TP/DP/PP/EP 在副本内部应用。

### 2.4 中间数据管理
- 交换的是**类型化负载**，不是不透明 blob，四类为主：
  1. **Hidden states / embeddings**（thinker → talker，含 prompt 嵌入与 TTS 特殊嵌入）；
  2. **Codec codes**（RVQ 行，talker → code2wav，带左上下文长度与 finished 标志）；
  3. **分页 KV 块**（PD 分离与 AR → DiT 边，来自 vLLM 分页块表，是注意力缓存而非激活）；
  4. **Latents / 多模态张量**（DiT/VAE 边、世界模型边）。
- **两种传输模式**：async_chunk（生产者就绪即发，消费者预热）与 full-payload（阶段结束一次性发布，消费者可能等待调度门）。TTS 路径还可根据下游缓冲反馈做**自适应 chunk ramp**。
- **KV 作为特殊负载**：PD 分离用 Mooncake 类连接器，编排器注入远端 bootstrap 与请求 ID，并保留多模态侧输出使 omni PD 不止文本；AR → DiT 由 Omni KV transfer manager 抽取已完成块、按 KV 专用键发布，扩散 runner 在去噪前注入 past_key_values。
- 边界：中间数据管理回答"这条边要哪些张量、何时就绪"；连接器回答"字节放在哪、怎么拷"；编排器永不做大张量总线。

### 2.5 OmniConnector
- 窄接口：put / get / cleanup / health check；生产者按 key 发布并返回可走控制队列的小元数据（共享内存名或远端句柄），消费者据此取回。
- 语义无关：不解释 blob 是 hidden state、codec 帧还是 KV 块；chunk-transfer 与 KV-transfer 层在其之上负责键的创建、重试、预取、回收。
- **放置感知后端**：单机默认共享内存；跨机支持 store 型与 transfer-engine 后端（Mooncake TCP / RDMA 及平台专用传输）；每条边可独立选后端。
- 不变式：**准入、路由、完成归编排器；负载字节归连接器**。

### 2.6 面向会话的控制
- 会话身份可跨单次 generate 存活，支持 open / update / signal / close；容量准入可在部署饱和时拒绝新会话；空闲租约、显式 reset、驱逐回收资源。
- **状态连续性**：AR–Diffusion 的分页 KV 留在引擎 KV 池内；非 KV 世界模型产物（如 latent ring）由类型化会话状态层管理，做字节记账与主机 offload，支持 allocate/commit/view/reset/evict；fencing 元数据防止旧轮次延迟更新污染新响应。
- **并发双向 I/O**：双工语音在播放中继续追加麦克风音频；流式视频可在去噪中摄入帧或交互；机器人按粘性会话 ID 反复观测→动作。
- 定位：会话控制是**同一控制平面的扩展**，不是第二套运行时；双工与世界模型状态被明确定位为能力层而非默认全开。

### 2.7 平台与效率栈
- **OmniPlatform 插件**：进程启动解析唯一平台；内置 CUDA / ROCm / MUSA（复用共享 GPU worker）、Ascend NPU / Intel XPU（专用 worker + 厂商集合通信 + 平台本地 hook，如 TTS code2wav、NZ 权重格式、融合 MoE 上下文）；支持 out-of-tree 插件注册。
- **量化**：统一工厂扩展 vLLM quant registry，覆盖 FP8/INT8 权重-激活、ModelOpt FP8/NVFP4、GGUF、AutoRound/INC、SVDQuant 风格 W4A4、CUDA-only bitsandbytes；Ascend 另有 MXFP8/MXFP4/msModelSlim；默认只量化 DiT transformer 主体或 thinker 阶段，非 AR 阶段保持高精度。
- **Offload / Sleep**：DiT 层/模块 CPU offload；Level-1 sleep 把权重卸到 CPU 并可唤醒，服务 RL 共置。
- **编译与缓存**：AR 继承 vLLM cudagraph/compile；codec/vocoder 按形状桶捕获 CUDA graph；扩散默认对热点块做 regional torch.compile；TeaCache 与 Cache-DiT 为一等步间复用后端（二者不可同时启用）。
- **生态**：厂商化部署 recipes、ComfyUI 作为 Omni 服务器客户端、与上游 vLLM 主次版本对齐并在 import 时检测版本偏斜、VeRL-Omni 把 vLLM-Omni 当作 rollout/serving 后端（LoRA add/remove、sleep/wake、自定义 pipeline 重初始化）。

### 2.8 API 与模型族
- **OpenAI 兼容面**：chat（SSE，文本 + base64 音频 delta）、speech（全量/分块/SSE、流式输入 WebSocket）、audio-generate、images、videos（异步 job + 同步）、video-chat / realtime video / duplex WebSocket；`--api-server-count` 可起多 API 进程共享同一组阶段引擎（当前拒绝扩散阶段）。
- **OpenPI 机器人面**：msgpack over WebSocket，连接时广播 policy 配置（action horizon、action keys、图像分辨率），每次 infer 传观测返回动作，支持 reset 与空闲超时。
- 六个工作负载族共享一套运行时：AR Omni、TTS/Speech、Diffusion I/V、World Models、VLA/Robot、Full-Duplex。

## 3. 实验设计

### 3.1 硬件与软件设置
- **H100** 用于多模态 nightly 池（图像、视频、世界模型、Qwen3-Omni 的 async-chunk 与副本扫描）。
- **H200** 用于语音表（Qwen3-Omni Fixed-Len / Random-MM / text-only、TTS 组合、MiniCPM-o）。
- GPU 数量随 recipe：Omni 2–3 卡，TTS/Voxtral 默认 2 卡、融合 Qwen3-TTS 用 1 卡，Qwen-Image 1 或 4 卡，Wan 1 卡，Cosmos3 demo 2 卡，MiniMax-H3 4 卡。
- 软件 SHA 为各表对应夜晚 nightly job 记录值；图像/视频/世界模型表取自冻结日 **2026-09-14** 的公开 CI，Qwen3-Omni async-chunk 与副本表用 **2026-07-05 至 07-11** 的 H100 recipe 基线均值。

### 3.2 负载与 Benchmark
