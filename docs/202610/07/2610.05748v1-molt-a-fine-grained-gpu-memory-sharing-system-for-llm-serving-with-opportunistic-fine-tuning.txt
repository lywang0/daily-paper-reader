## Abstract 

Large language model (LLM) serving scales its replica count with the request load, yet GPU memory still stands idle in-side the replicas. Adding a replica takes minutes, while the memory that a replica needs changes within seconds. Even instant autoscaling could not return this idle memory, be-cause the smallest unit that it can remove is a whole replica. Colocating parameter-efficient fine-tuning (PEFT) with in-ference can use this memory, but inference must be able to reclaim it within seconds, before requests that wait for memory exceed their latency service-level objective (SLO). Existing colocation systems either keep the tuning memory resident or let inference reclaim it at the coarse granularity of a whole training sample. Each such reclamation also dis-cards the running tuning step. To address these limitations, we present MOLT, a fine-grained memory sharing system that lets inference reclaim the memory of individual activa-tions that a running tuning step has saved for its backward pass. The step continues, and its backward pass recomputes those activations. Inference reclaims only memory that no in-flight GPU work can still access, even under CPU–GPU asynchrony and tensor parallelism. On four model deploy-ments (24B–70B) across H100 SXM and B200 GPUs under trace-driven workloads, MOLT keeps inference SLO attain-ment at or above 99.7% and completes 1.9–3.3 × the tuning work of discard-based memory sharing. 

## 1 Introduction 

Request load in large language model (LLM) serving fluctu-ates heavily. Provisioning enough GPUs to meet the latency service-level objective (SLO) at peak load leaves them under-utilized the rest of the time, so production systems autoscale. They add and remove replicas, each an independent serving instance that holds one copy of the model on one or more GPUs, as the load changes [8, 9]. Autoscaling follows the slow part of this fluctuation well, the daily cycle in which user-facing services peak during working hours and fall at night [45, 54], and removes the capacity that a lower load leaves idle [20]. Each replica must therefore keep headroom to absorb the load that arrives before new replicas come up. One production autoscaler tar-gets 60% GPU utilization by default, leaving each GPU idle 40% of the time [9]. A deployment thus runs at an autoscal-ing floor , the fewest replicas that keep this headroom, where GPU compute and memory stay idle even with autoscaling. This memory cannot be returned to the provider, because a replica is withdrawn only as a whole. Colocating another workload with inference can put this idle capacity to use. Parameter-efficient fine-tuning (PEFT) is a natural candidate. It is the standard way to adapt a deployed model [12], and demand keeps growing, with Hugging Face hosting 256,295 PEFT adapters published at a rising rate since 2024 [14]. It also fits colocation well. PEFT freezes the pretrained weights and trains only a small adapter [17], so when applied to the model that inference is serving it reuses the weights resident on the GPU. Its progress is measured in throughput rather than latency, so it can yield memory to inference during a burst and take it back afterwards.

Existing colocation systems dynamically share either the compute or the memory of the GPU. LLMStation [14] shares compute by interleaving tuning operations with inference iterations, but its tuning memory stays resident. Memory, however, is what determines whether inference meets its SLO during a burst. Inference admits a request only when the KV cache has room for it [23, 56], so a shortage of mem-ory delays admission and lengthens the time to first token (TTFT). Likewise, a running request whose KV cache cannot grow for lack of memory stalls until memory frees up [23, 46]. SIRIUS [53] focuses on sharing memory, treating the training batch as elastic. When inference needs memory, it aborts the running step, restarts it with a smaller batch, and hands the freed memory to inference in a handover fast enough for the SLO. The memory boundary between the two workloads thus moves at runtime. SIRIUS uses the idle memory that autoscaling removes, the memory a fixed number of GPUs leaves free as the load changes over minutes and hours. At the autoscaling floor, however, resizing the training batch moves the boundary in increments too coarse and at a cost too high. First, the small-est increment is one training sample, whose memory is large relative to the idle memory. A one-sample Mistral-Small-24B-Instruct tuning step at 1024 tokens holds 15.8 GiB beside the frozen weights, against 20–31 GiB idle on one H100. Tuning halts once the idle memory cannot hold one sample. Second, each handover discards the running tuning step and restarts it with a smaller batch, losing the work already done (Fig-ure 1(a)). At the floor, this cost recurs whenever the KV cache outgrows the free memory, which happens within seconds. Avoiding both limitations requires a unit of memory finer than a training sample, one that inference can reclaim with-out discarding the running step. We observe that the saved activation is such a unit. A saved activation is a tensor that the forward pass keeps for the backward pass to compute gradients. Saved activations hold most of a PEFT step’s mem-ory [28] and can be recovered by recomputation [4, 19, 21]. When inference reclaims the memory of some of them, the step continues, and its backward pass recomputes them (Fig-ure 1(b)). Recomputation itself is well studied, but activation checkpointing fixes its memory budget before tuning starts. Here, the budget must change during the step, whenever inference reclaims memory. Based on this observation, we present MOLT, a fine-grained memory sharing system that lets inference reclaim memory from a running tuning step one saved activation at a time. MOLT places the KV cache and the saved activations in one shared pool of physical GPU memory, and binds each saved activation to a fixed virtual-address range, called a 

slot . A slot is backed while physical pages of the pool are mapped behind it. When the KV cache needs more memory than the pool has free, MOLT unbacks slots and hands their pages to the KV cache while the tuning step continues. We call this mechanism continuous memory handover .Handing memory over inside a running step raises two challenges. First, the tuning step must remain correct al-though its slots can be unbacked at any point. With flexible activation checkpointing , MOLT checks whether a slot is backed before each kernel that uses it, saves activations only into backed slots, and recomputes every activation whose slot is unbacked. Second, a handover must never unback a slot that GPU work may still access. Because the CPU dis-patches kernels ahead of the GPU [30], a kernel dispatched several layers earlier may still access a slot when a handover arrives. With asynchronous-aware slot protection , MOLT pro-tects every such slot, limits how far CPU dispatch runs ahead to keep the protected slots few, and makes every rank of a tensor-parallel deployment unback the same slots. We evaluate MOLT on four model deployments (24B–70B) across H100 SXM and B200 GPUs under trace-driven work-loads, where it keeps inference SLO attainment at or above 99.7% while tuning continues. Colocation that shares only compute reaches an SLO attainment of at most 5.0%. Against the discard-based memory sharing of SIRIUS, which also lets inference reclaim memory, MOLT completes 1.9–3.3 ×

the tuning work. On both Mistral-Small-24B-Instruct de-ployments, MOLT with step-level handover, which moves the boundary only between steps, attains the SLO less of-ten and completes less tuning work, which shows that the gain comes from the finer granularity rather than from the implementation. In summary, this paper makes the following contributions: 

• We identify the GPU memory that autoscaling leaves idle in LLM serving, and show that existing memory sharing cannot use it, because its unit, one training sample, is too coarse and each handover discards the running tuning step. 

• We propose MOLT, a fine-grained memory sharing sys-tem whose continuous memory handover lets inference reclaim memory from a running tuning step one saved activation at a time. 

• We design flexible activation checkpointing, which keeps the tuning step correct, and asynchronous-aware slot pro-tection, which makes each handover safe under CPU–GPU asynchrony and tensor parallelism. 

• We evaluate MOLT against compute sharing, discard-based memory sharing and MOLT with step-level han-dover, and show that it sustains inference SLO attainment while completing more tuning work than discard-based memory sharing.

2.3 Inference-first Tuning Colocation 

A second workload colocated with inference can use the memory idle at the autoscaling floor, but only until inference needs it again. When load rises, inference must reclaim that memory within seconds, before the arriving requests wait for it [23, 56]. This move across the boundary between the two workloads is a handover. The second workload must there-fore tolerate interruption and hold a small resident footprint ,the memory that inference can never reclaim from it. PEFT meets both requirements (§2.1). ## 3 Motivation 

3.1 Limitations of Existing Memory Sharing 

SIRIUS uses the idle memory that autoscaling removes, not the memory autoscaling leaves behind. Its target is the mem-ory a fixed GPU count leaves free. This memory is large, so the boundary can move at the coarse granularity of whole training samples. It is also long-lived, so inference rarely takes it back and handovers are rare. Neither property holds at the autoscaling floor, where the idle memory is smaller and inference takes it back within seconds (§2.2). A first limitation is granularity. Within a batch, samples are independent, so adding or removing a whole sample cleanly adds or removes its memory. That memory is large relative to what the floor leaves idle. A Mistral-Small-24B-Instruct tuning step of one sample at 1024 tokens holds 15.8 GiB beside the frozen base weights (Figure 4), against the 20–31 GiB left idle on one H100 at the floor (Figure 2(b)). There is no setting below one sample, so tuning halts entirely once the idle memory cannot hold one. A second limitation is the cost of the handover itself. SIR-IUS reclaims memory by discarding the current tuning step and restarting it with a smaller batch, so a handover late in a step wastes every operation the step has performed. At the floor, the KV cache can grow 3.2 × in ten seconds (Fig-ure 2(b)), and each rise takes memory back from tuning. The cost of a discarded step is therefore paid at the rate the KV cache moves, not at the rate the day’s load changes. 

3.2 Activation as the Unit of Memory Sharing 

The limitations of SIRIUS point to two requirements for PEFT colocation. First, the sharing granularity must be much finer than a whole sample, so that idle GPU memory is used effi-ciently and tuning is not forced to halt the moment a single sample no longer fits. Second, a handover must preserve the progress of the running PEFT step rather than discard it, so that frequent handovers do not starve tuning. The saved activation meets both. A saved activation is a tensor that the forward pass keeps for the backward pass to compute gradients. It is the only unit in a PEFT step that meets both requirements. Persistent state, namely the adapter parameters, gradients and optimizer state, must stay resident to preserve progress, and only 0.4 GiB of a step’s memory is persistent, at every input length (Figure 4). In-termediate tensors live too briefly for their memory to be reclaimed. Saved activations dominate the rest of the step’s memory and can be recovered by recomputation [4, 19, 21, 39]. An activation is a fine-grained unit, because each one is small and can be dropped individually, at per-layer or per-operator granularity, rather than a whole sample at once. It also preserves progress, because a dropped activation is recomputed in the backward pass, and a handover then costs only that recomputation rather than the work that the step has already performed. 

3.3 Key Challenges of Fine-grained Memory Sharing 

Using the saved activation as the sharing unit raises two challenges. 

C1. Adapting execution to a dynamically changing saved-activation set. Because activations are dropped dy-namically during the step, the backward pass cannot assume that a saved activation is still available. An activation may have been dropped at any point after it was produced, so reading it directly could lead to a memory fault. The system must therefore check, at each backward access, whether the activation is still in memory, and recompute it when it is not. 

C2. Dropping activations safely during execution. 

The CPU decides which activations to drop, but it dispatches GPU kernels asynchronously and runs far ahead of the GPU execution [30, 37], so a kernel it launched several layers back may still be reading or writing the activations of its layer. ## 4 MOLT 

4.1 Overview 

MOLT provides continuous memory handover, which allows inference to reclaim memory from a running tuning step at the granularity of a single saved activation. The tuning step continues across a handover, and its backward pass recomputes each activation whose memory was reclaimed, so no completed work is discarded. MOLT is a fine-grained memory sharing system with three components (Figure 5). The inference-side allocator and the 

tuning-side allocator run inside vLLM and PyTorch, respec-tively (§5.1). Each saved activation is bound to its slot, and the slot state table (SST) records whether physical pages back each slot. The handover controller manages the shared pool, which is preallocated and holds the KV cache and the pages of backed slots, the only memory a handover moves. When the KV cache exhausts the pool’s free pages, the inference-side allocator requests pages over inter-process communication (IPC), and the handover controller unbacks slots and hands their pages to the KV cache. With flexible activation checkpointing, MOLT ensures that a tuning step remains correct when its slots are un-backed mid-step (C1, §3.3). The tuning-side allocator reads a slot’s backing state from the SST before each kernel that produces or consumes the slot’s activation (§4.3). The acti-vation is saved in the forward pass only if its slot is backed, and in the backward pass, it is read from its slot if the slot is backed and recomputed otherwise. Unlike prior recompu-tation schemes [4, 19, 21], MOLT decides which activations to recompute from backing state that changes whenever inference reclaims memory, while the step is still running. With asynchronous-aware slot protection, MOLT ensures that a handover unbacks no slot that in-flight GPU work may still access (C2, §3.3). The SST sets a slot’s enqueued flag while a kernel that uses the slot has been dispatched but has not completed, and the handover controller unbacks only slots whose flag is clear on every rank (§4.4).

In the backward pass, layer 6 comes first, and MOLT recomputes its activations before its operators run. The operators of layer 5 then read their activations from their slots. Unlike discard-based handover, MOLT never restarts the step, and a handover costs only the recomputation of the activations whose slots it unbacks (Figure 8). Discard-based handover couples every memory-boundary change to abort-ing and restarting the running step (§3.1). In Figure 8(b), the forward work already done is discarded, and in Figure 8(c), it is kept and only the activations of unbacked slots are recom-puted in the backward pass. Pages reach inference through the same handover path that discard-based systems use [53]. Memory is handed back to tuning only at step bound-aries, by re-backing unbacked slots. At the start of each step, the handover controller maps free pages of the pool behind unbacked slots again, highest recomputation cost first, and stops when the pool has no free pages left. The remaining unbacked slots wait for a later step boundary. Re-backing a slot in the middle of a step would spare recomputation only for activations that the step has not produced yet. Waiting for the next step boundary therefore costs at most the ex-tra recomputation of the rest of the current step. Because re-backing discards nothing, MOLT re-backs at every step boundary at which the pool has free pages. A discard-based system instead waits until free memory exceeds a threshold, because it moves the boundary only at a coarse granular-ity [53]. 4.4 Asynchronous-aware Slot Protection 

MOLT protects every slot that in-flight GPU work may still read or write, and a handover unbacks only the other slots (C2). Under TP, every rank must also unback the same slots (Figure 10). MOLT protects these slots without discarding the GPU work dispatched before the handover. MOLT classifies every slot by the enqueued flag that §4.1 defines. A slot is 

claimed while the enqueued flag of the slot is set. A handover leaves the backing state of a claimed slot unchanged, whether the slot is backed or was unbacked by an earlier handover. A slot is evictable when the enqueued flag of the slot is clear. The set of claimed slots, the protection window , contains the slots of every layer from the layer before the completion frontier to the dispatch frontier (Figure 9(a)). The completion frontier is the layer that the GPU is executing, and the dis-patch frontier is the last layer that the CPU has dispatched. The window includes the layer before the completion fron-tier because the first operators of a layer read the output of the previous layer. MOLT tracks GPU completion with a host-side callback, a CPU function that runs once the GPU has completed a layer [33]. MOLT sets the enqueued flag of every slot of a layer when the CPU dispatches the first operator of the layer. The enqueued flag covers a whole layer rather than one operator, because a later operator of the same layer, such as a residual connection, may read a slot that an earlier operator wrote [51]. MOLT clears the flag of a layer only when the host-side callback of the next layer runs. The dispatch frontier usually runs several layers ahead of the completion frontier, because CPU dispatch is asynchronous to GPU execution. In Figure 9(a), the CPU has dispatched layer 8 while the GPU still executes layer 1. The protection window thus contains layers 0 to 8, drawn in orange. The 

> 7Yang et al.

CPU has not yet dispatched layers 9 onward, whose slots are evictable and drawn in yellow. When a handover request arrives, MOLT freezes the pro-tection window until the handover controller has decided which slots to unback and has unbacked those slots. We call this mechanism the protection snapshot . Without the pro-tection snapshot, the CPU could dispatch an operator that uses one of the slots to unback, and that operator would then access a slot that has no physical pages. The protection snapshot therefore pauses CPU dispatch and holds the dis-patch frontier in place. The pause has little effect on tuning, because the GPU continues to execute the operators already dispatched. The protection snapshot also defers the host-side callbacks that would advance the completion frontier, and thereby keeps every slot of the protection window claimed until the slots to unback are decided. A slot may remain claimed slightly longer than necessary, but no slot becomes evictable too early. After the handover controller has un-backed the chosen slots, MOLT runs the deferred callbacks and resumes CPU dispatch. MOLT keeps the protection window small by limiting how far CPU dispatch may run ahead of GPU execution, which leaves more slots evictable when a handover request arrives (Figure 9(b)). We refer to this mechanism as dispatch throt-tling . Without dispatch throttling, the protection window contains every layer that the CPU has dispatched ahead of the GPU, seven layers in Figure 9(a), and no slot in the pro-tection window can be unbacked. MOLT enables dispatch throttling by modifying the software GPU kernel manage-ment technique used in SIRIUS [53]. The technique holds dispatched operators in a queue until the GPU executes the operators, and MOLT adds a dispatch cap on the number of operators in the queue. When the queue reaches the dispatch cap, CPU dispatch waits until the GPU has executed enough operators to bring the queue below a threshold, which we set to half of the dispatch cap. In Figure 9(b), CPU dispatch waits after each layer, and the gap between the dispatch and completion frontiers shrinks from seven layers to one. MOLT chooses the dispatch cap by offline profiling, as the smallest dispatch cap that does not lengthen the tuning step. A larger dispatch cap only widens the protection window, and a smaller dispatch cap leaves the GPU waiting for the CPU. The chosen dispatch cap therefore keeps the protection window as small as possible without slowing tuning. Under TP, each rank keeps a separate protection win-dow, and the handover controller unbacks only slots that lie outside the union of the rank-local protection windows (Figure 10(b)). Collectives such as NCCL all-reduce [34] keep the GPUs of the ranks nearly aligned, but the dispatch fron-tiers of the ranks can differ (Figure 10(a)). ## 5 Evaluation 

We evaluate MOLT in inference-first colocation, where tun-ing uses the GPU memory that inference leaves idle and inference reclaims it whenever the KV cache needs more. The evaluation answers three questions. 1. Does inference keep its SLO attainment while MOLT com-pletes more tuning work than discard-based memory shar-ing (§5.2, §5.3)? 2. Is the gain caused by handover granularity rather than by the implementation that carries it (§5.2, §5.4)? 3. How much tuning speed does the dispatch cap cost, and how long does a handover delay inference (§5.5, §5.6)?

5.1 Experimental Setup Hardware. We run Mistral-Small-24B-Instruct on 1 ×H100 SXM and 2 ×H100 SXM [5], and Llama-3.1-70B-Instruct on 4×H100 SXM and 1 ×B200 [35] (Table 1). 

Models and adapters. We tune rank-8 LoRA [17] adapters on Mistral-Small-24B-Instruct [29] and Llama-3.1-70B-Instruct [10]. 

Datasets and traces. We use ShareGPT [1] prompts for inference and the Alpaca [47] dataset for tuning. A tuning se-quence has 768, 2048, 1024 and 512 tokens in the deployments of Table 1, respectively. Inference requests arrive according to the BurstGPT trace [54]. 

Implementation. MOLT is implemented as a patch to vLLM v0.11.0 [23] and an extension library for LLMStation’s build of PyTorch 2.8.0 [37]. The patch changes 2.7K lines in 23 of vLLM’s files and adds a 9.7K-line module. The module ports LLMStation’s execution interleaving [14] to vLLM’s V1 engine [52] and integrates MOLT with it. The 13.1K-line library backs and unbacks slots through CUDA virtual memory management [31] on SIRIUS’s page pool [53]. 

Baselines and ablation. We compare MOLT with con-tinuous handover, the full design, against two baselines and one ablation. The ablation, MOLT with step-level handover, differs from MOLT with continuous handover only in when the boundary may move, so it isolates handover granular-ity. LLMStation-only shares only compute. It keeps tuning memory resident by excluding the same amount of memory from KV cache admission. LLMStation+SIRIUS also shares memory. At each handover, it resizes the training batch and discards the running step [53]. Its shared pool is the same size as that of MOLT. At each step boundary, MOLT with step-level handover reserves memory for inference. The reserve is the KV cache that the waiting requests need, multiplied by a reserve factor, plus a fixed margin. We report the factor with the highest SLO attainment among five factors from 2.0 to 4.0 (§5.4). 

Metrics and SLOs. We report SLO attainment and tuning throughput over a measurement window. SLO attainment is the fraction of requests arriving in the window that meet the SLO [27, 57]. Tuning throughput is the number of tokens in the tuning samples completed in the window, per second. A request meets the SLO when its TTFT and its time per output token (TPOT) are each within 3 × the mean for the same deployment running inference alone [2, 15, 24, 38].

5.6 Handover Overhead Analysis 

A handover takes at most 1.3% of a tuning step, and only page allocation on the inference side grows with the handover size. A handover delays the inference request that needs its pages, from the page request of the inference-side allocator to the completion of page allocation. Under MOLT with step-level handover, that request waits instead until the running step ends (§5.3), so we state the latency as a share of a tuning step. In Figure 14, each bar is the mean latency of at least 19 handovers of one size, broken into four stages and Other, the time between them. In time order, the inference-side allocator requests pages over IPC (IPC request), and the handover controller takes the slot-unbacking decision and unbacks the chosen slots (Slot unbacking). The controller then acknowledges over IPC (IPC ack), and the allocator allocates their pages to the KV cache (Page alloc). At the largest size drawn for each deployment, 256, 128, 128 and 512 MiB in the order of Table 1, the mean handover takes 1.0, 1.3, 0.7 and 0.8% of a step. Three stages change little with the handover size: the IPC request, slot unbacking and the IPC acknowledgment. They take 0.64–0.87 ms on the two deployments at TP=1 and 1.09– 1.47 ms on the two with tensor parallelism, and they are more than half of a handover at the smallest size on every de-ployment. Of the three, slot unbacking grows the most with the tensor-parallel degree, yet it remains within 0.07% of a tuning step at every degree. It takes 0.05–0.12 ms at TP=1, 0.22–0.32 ms at TP=2 and 0.38–0.53 ms at TP=4. It grows be-cause, under tensor parallelism, the slot-unbacking decision also waits for every rank’s protection snapshot (§4.4). Page allocation changes little at small handover sizes and grows almost in proportion to the size at large ones. In Fig-ure 14, on both deployments at TP=1, allocation remains within 0.44–0.72 ms up to 64 MiB per GPU. Beyond that size, each doubling of the size multiplies it by 1.5–2.0. The growth comes from allocation taking each page from the free list of the shared pool and zero-filling it. At TP=2, allocation grows from the smallest size drawn. At TP=4, it rises at 64 MiB, the first size measured with a longer interval between han-dovers. 

## 6 Related Work 

Colocation of LLM inference and tuning. Unlike prior colocation systems, MOLT reclaims memory from a run-ning tuning step without discarding the step. FineInfer runs inference between tuning steps [13]. FlexLLM interleaves tuning and inference tokens in each iteration and reserves the KV cache statically [36]. LLMStation interleaves tuning operations with inference iterations while tuning memory remains resident (§2.3). SIRIUS moves the memory bound-ary by discarding the running step and restarting it with a smaller batch (§3.1). MOLT reuses LLMStation’s interleaving and SIRIUS’s page pool (§5.1), but its unit of memory sharing is a saved activation rather than a training sample. 

Activation checkpointing. MOLT builds on activation checkpointing and differs from it in the memory budget, which inference changes while the tuning step runs (§4.1). Checkpointing chooses which activations to recompute un-der a budget fixed before training starts [4, 11, 19, 22]. DTR and Capuchin decide at run time under such a budget [21, 39]. Like DTR [21] and selective recomputation [22], MOLT gives up the activations that are cheapest to recompute first (§4.3). In these systems, the memory an activation gives up stays with the training job. In MOLT, inference reclaims it while dispatched kernels may still access it, which asynchronous-aware slot protection makes safe (§4.4). 

## 7 Conclusion 

Autoscaling leaves GPU memory idle inside LLM serving replicas, because it cannot follow a KV cache that changes within seconds and removes a replica only as a whole. Ex-isting colocation systems either keep the tuning memory resident or let inference reclaim it only in whole training samples, discarding the running tuning step each time. We 

> 12

MOLT: A Fine-Grained GPU Memory Sharing System for LLM Serving with Opportunistic Fine-Tuning 

present MOLT, a fine-grained memory sharing system for colocating LLM inference and tuning. MOLT lets inference reclaim memory one saved activation at a time, safely un-der CPU–GPU asynchrony and tensor parallelism, while the running step continues and recomputes those activations. Experiments show that MOLT keeps inference SLO attain-ment at or above 99.7% while completing 1.9–3.3 × the tuning work of discard-based memory sharing.
