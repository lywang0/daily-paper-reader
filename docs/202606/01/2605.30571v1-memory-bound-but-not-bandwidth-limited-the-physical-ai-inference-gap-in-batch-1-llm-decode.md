## 摘要
物理AI系统，包括机器人、自动驾驶车辆、具身智能体和边缘副驾驶，通常运行与云端LLM服务不同的推理工作负载：单流、批量1的自回归解码，其中单个机器人、摄像头输入或用户会话等待下一个token。这种工作负载通常被描述为内存带宽受限。每个解码步骤都会流式传输模型权重和活跃KV缓存，因此延迟应与峰值HBM带宽成比例。我们证明这种说法正确但不完整。我们在四款NVIDIA GPU上测量了三种7至8B类GQA变压器的批量1解码：H100 SXM5、A100-80GB SXM4、L40S和L4。我们评估了从2048到16384的上下文长度，在受控的bf16 SDPA设置下产生了44个有效数据点。达到的峰值HBM带宽分数随着峰值带宽的增加而下降。在标题性的Qwen-2.5-7B ctx=2048单元上，L4达到了约81%的分析内存下限，而H100仅达到27%。物理AI解码是内存主导的，但更快的内存并不会带来成比例的延迟增益。我们通过CUDA Graphs A/B实验测试了缺失项。在H100上，ctx=2048时，CUDA Graphs在N=10个新会话中将解码延迟提高了1.259倍，95%自助置信区间为1.253至1.267。在L4上，相同的干预仅带来1.028倍。这隔离了一个启动端开销，它在快速GPU上变得可见，但在较慢的、带宽受限的GPU上大多隐藏。部署的含义是，只有运行时实现了内存节省，内存节省才有意义。在L4上，bf16解码接近内存下限，但常见的量化路径并未恢复预期的4倍权重流量减少：bnb-nf4达到59.36 ms/步，AutoAWQ+Marlin达到45.24 ms/步，而bf16基线为62.32 ms。具有Ada调优int4内核的GPTQ+ExLlamaV2达到17.36 ms/步。

## Abstract
Physical AI systems, including robots, autonomous vehicles, embodied agents and edge copilots, often run a different inference workload from cloud LLM serving: single-stream, batch-1 autoregressive decode, where one robot, camera feed or user session waits on the next token. This workload is usually described as memory-bandwidth-bound. Each decode step streams model weights and the active KV cache, so latency should scale with peak HBM bandwidth. We show that this account is true but incomplete. We measure batch-1 decode for three 7 to 8B-class GQA transformers across four NVIDIA GPUs: H100 SXM5, A100-80GB SXM4, L40S and L4. We evaluate context lengths from 2048 to 16384, producing 44 valid cells under a controlled bf16 SDPA setup. The achieved fraction of peak HBM bandwidth falls as peak bandwidth rises. On the headline Qwen-2.5-7B ctx=2048 cell, an L4 reaches roughly 81 percent of its analytic memory floor, while an H100 reaches only 27 percent. Physical-AI decode is memory-dominated, but faster memory does not translate into proportional latency gains. We test the missing term with a CUDA Graphs A/B experiment. On H100 at ctx=2048, CUDA Graphs improves decode latency by 1.259x across N=10 fresh sessions, with a 95 percent bootstrap confidence interval of 1.253 to 1.267. On L4, the same intervention gives only 1.028x. This isolates a launch-side overhead that becomes visible on fast GPUs but remains mostly hidden on slower, bandwidth-bound GPUs. The deployment implication is that memory savings matter only when the runtime realises them. On L4, bf16 decode sits close to the memory floor, but common quantised paths do not recover the expected 4x weight-traffic reduction: bnb-nf4 reaches 59.36 ms/step and AutoAWQ+Marlin reaches 45.24 ms/step from a 62.32 ms bf16 baseline. GPTQ+ExLlamaV2, with Ada-tuned int4 kernels, reaches 17.36 ms/step.

## 1. 核心问题与整体含义（研究动机和背景）

- 物理AI系统（机器人、自动驾驶、具身智能、边缘副驾驶等）运行的工作负载与云端LLM服务不同：**单流、批量1的自回归解码**。每个解码步骤流式传输全部模型权重和活跃KV缓存，带宽压力大。
- 传统观点认为此类工作负载是**HBM带宽受限**（memory-bandwidth-bound），因此延迟应随峰值带宽提升而线性下降。GPU升级（L4→L40S→A100→H100）通常被视为成本-延迟阶梯。
- **问题：** 实际测量发现，高带宽GPU并未带来成比例加速。例如Qwen-2.5-7B ctx=2048时，L4达到理论下限的81%，而H100仅达到27%。H100的11倍带宽只带来约1.4倍真实加速（经CUDA Graphs优化后）。存在一个“物理AI推理差距”。
- **动机：** 找出导致差距的根本机制，并评估实际部署的优化方向（launch开销 vs. 带宽 vs. 量化运行时）。

## 2. 方法论：核心思想、关键技术细节

### 核心思想
- 定义分析下限 `t_floor = (W + K) / B_peak`，其中W为权重字节数，K为每步KV缓存字节数，B_peak为峰值HBM带宽。
- 定义实际利用率 `R_floor = t_floor / t_obs`，衡量每步解码接近带宽理论极限的程度。
- 通过 **CUDA Graphs A/B实验** 隔离CPU launch开销：将整个解码步骤的kernel序列捕获为图并回放，消除CPU侧的每次kernel启动开销。若launch是主要瓶颈，则Graphs应显著加速H100，而对带宽受限的L4影响很小。

### 技术细节
- **测量协议：** 每个配置（架构- GPU - 上下文长度）为一个单元（cell）。加载模型bf16，运行固定长度prefill填充KV cache，然后执行5次预热解码+30次测量解码，取中位数作为步时间。
- **CUDA Graphs A/B：** 同一个容器内先运行eager模式（标准PyTorch），再捕获图并回放，比较两个窗口的p50延迟。预先设定假说阈值：若H100 Graphs加速低于1.15倍或L4加速高于1.15倍则拒绝launch假说。
- **Attention后端对比：** 在H100上固定Llama-3-8B解码形状，强制不同的SDPA后端（FLASH_ATTENTION、EFFICIENT_ATTENTION、MATH、CUDNN_ATTENTION）以及FlashInfer、FlashAttention-3，测量单层attention p50。
- **L4量化对比：** bf16基线 vs. bitsandbytes nf4 vs. AutoAWQ+Marlin (int4) vs. GPTQ+ExLlamaV2 (int4, Ada调优)，观察实际步时间变化。

## 3. 实验设计：数据集/场景、Benchmark、对比方法

- **模型：** 三种7-8B GQA变压器：
  - Qwen-2.5-7B-Instruct（28层，28 Q头，4 KV头，head dim 128）
  - Mistral-7B-Instruct-v0.3（32层，32 Q头，8 KV头）
  - Llama-3.1-8B-Instruct（32层，32 Q头，8 KV头）
- **GPU：** 4款Modal云GPU：
  - H100 SXM5 (3,350 GB/s), A100-80GB SXM4 (2,039 GB/s), L40S (864 GB/s), L4 (300 GB/s)
- **上下文长度：** 2048, 4096, 8192, 16384 tokens
- **默认设置：** bf16权重，PyTorch SDPA注意力，batch=1
- **对比方法：**
  - **主要矩阵：** 3模型 × 4GPU × 4上下文 = 48个单元，4个因L4 OOM无效，共44个有效单元。
  - **CUDA Graphs A/B：** 在H100 ctx=2048（N=10独立会话）、H100 ctx=8192、L4 ctx=2048上进行，测量eager vs graphed延迟。
  - **Attention后端：** H100上Llama-3-8B形状，对比default SDPA、FLASH_ATTENTION、FlashInfer、FlashAttention-3、EFFICIENT_ATTENTION、MATH、CUDNN_ATTENTION。
  - **L4量化：** bf16、bnb-nf4、AutoAWQ+Marlin、GPTQ+ExLlamaV2 (4.25bpw)，均在Qwen-2.5-7B ctx=2048 L4上测量。

## 4. 资源与算力

- **硬件平台：** Modal云GPU。具体型号：H100 SXM5、A100-80GB SXM4、L40S、L4。根据论文，共使用了至少 **1个H100、1个A100、1个L40S、1个L4**（不同会话可能使用多个实例，但未明确总数）。H100 headline实验使用了10个独立会话，每个会话一个容器。

- **测量规模：** 每个单元30步解码，加上预热。N=10 headline实验共300步eager+300步graphed。总共44个有效单元+若干额外实验。**未涉及训练**，仅为推理基准测试。

## 5. 实验数量与充分性

- **主要矩阵：** 44个有效单元覆盖3模型×4GPU×4上下文（部分OOM），系统性地揭示了R_floor随带宽上升而下降的单调模式。
- **机制验证：** CUDA Graphs A/B在H100上N=10独立会话，95% Bootstrap CI [1.253, 1.267]，跨会话CV 0.9%，统计显著性高。L4 null result复制三次。预先注册了拒绝阈值，增加了客观性。
- **Attention后端：** 在H100上3个新鲜容器、每个后端300步测量，误差棒<2%，结果稳健。
- **L4量化：** ExLlamaV2在3个容器上测量，p50标准差仅0.004ms，高度可重复。
- **消融/敏感性：** 包括批次4的AB实验（H100）、不同上下文长度、不同模型。还列出了失败实验（OOM、编译错误），体现透明性。
- **充分性评价：** 实验设计考虑了控制变量（相同容器、相同测量协议、多会话重复），统计显著性检验，覆盖了主要的优化维度（带宽、launch、量化）。对于声明范围（7-8B GQA bf16 batch1）来说，实验充分且公平。

## 6. 主要结论与发现

1. **batch-1 decode在高带宽GPU上并非纯带宽受限，CPU launch开销是主导瓶颈。** R_floor从L4的0.81降至H100的0.27，差距约3倍。CUDA Graphs在H100上加速1.259倍，L4仅1.028倍，直接证明launch tax的存在。
2. **Attention kernel在H100上不是主要瓶颈。** PyTorch默认SDPA（36 μs/layer）比FlashAttention-3（79 μs）、FlashInfer（48 μs）更快。最慢的MATH后端(178 μs)也只需5.68ms总attention时间，而launch tax约3ms且影响所有kernel。
3. **L4上量化路径的实际收益差异巨大：** bf16 (62.32ms) → bnb-nf4 (59.36ms, 1.05x) → AutoAWQ+Marlin (45.24ms, 1.38x) → GPTQ+ExLlamaV2 (17.36ms, 3.59x)。同样的int4位宽，运行时实现决定实际加速。ExLlamaV2专为Ada SM89优化，几乎达到4倍理论带宽节省。
4. **部署成本阶梯反转：** L4+ExLlamaV2 (17.36ms/step, $0.30/hr) 与H100+CUDA Graphs (11.78ms/step, $3.50/hr) 相比，H100仅快1.47倍但贵11.7倍，每百万token成本L4远低于H100。物理AI场景下，更便宜的GPU配合合适内核可能是更优解。

## 7. 优点

- **实验严谨性：** 跨GPU系统性测量、N=10统计重复、95% Bootstrap置信区间、预先设定假说拒绝阈值。
- **机制验证：** 通过CUDA Graphs A/B直接隔离launch开销，不改变GPU kernel本身，是干净的对比实验。
- **关注实际部署：** 针对物理AI特定工作负载（batch-1 decode），而非通用LLM服务，提供了针对性指导。
- **量化运行时对比：** 揭示了“位宽不是一切，内核实现决定一切”，对边缘硬件选型有直接意义。
- **透明性：** 公开所有测量JSON、失败实验、分析脚本，可高度复现。
- **客观性：** 不回避冲突数据（如H100 earlier single-session 1.72x被N=10结果修正），态度诚实。

## 8. 不足与局限

- **范围狭窄：** 仅限7-8B GQA模型，head dim 128，bf16权重，batch=1。不覆盖MHA、MQA、MLA，或更大/更小模型，不覆盖其他批次大小（仅少量batch=4）。
