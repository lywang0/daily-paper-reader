## 摘要
现代AI服务越来越依赖NPU进行常规推理和大语言模型服务。然而，当前的NPU部署通常将物理设备直接暴露给应用程序，这限制了运行时对调度的控制，并且难以根据阶段级工作负载行为调整执行。这种限制在LLM服务中尤为明显，其中预填充阶段是计算密集型的，而解码阶段通常受内存带宽和KV缓存访问的限制。静态预填充-解码（PD）分离减少了阶段干扰，但可能导致资源不平衡和不必要的数据移动。我们提出了FlexNPU，这是一个面向昇腾NPU的透明用户空间虚拟化层。FlexNPU拦截AscendCL API，并通过每设备守护进程路由NPU操作，将未修改的应用程序与物理NPU设备解耦，无需修改模型代码、AI框架或NPU驱动程序。这个运行时边界使FlexNPU能够虚拟化NPU对象，控制算子调度，并支持LLM服务的阶段感知调度。特别是，FlexNPU实现了动态PD共置，根据预填充和解码的互补资源特性自适应调整两者之间的调度。我们在华为昇腾NPU上实现了FlexNPU，并使用典型的LLM工作负载进行了评估。与直接NPU直通相比，FlexNPU没有引入可测量的推理开销，并且在某些场景下略微提高了吞吐量。在384卡昇腾910C部署的DeepSeek-R1上，FlexNPU相比静态PD分离将吞吐量提高了5.15%和26.33%。在Qwen2.5-7B上，与静态PD共置相比，FlexNPU在保持可比吞吐量的同时，在测试工作负载中将TTFT降低了超过92%，且TPOT几乎不变。这些结果表明，透明NPU虚拟化是实现高效且响应迅速的LLM服务的实用基础。

## Abstract
Modern AI serving increasingly relies on NPUs for conventional inference and large language model serving. However, current NPU deployments commonly expose physical devices directly to applications, which limits runtime control over scheduling and makes it difficult to adapt execution to phase-level workload behavior. This limitation is particularly evident in LLM serving, where the prefill phase is compute-intensive while the decode phase is often constrained by memory bandwidth and KV-cache accesses. Static prefill-decode (PD) disaggregation reduces phase interference, but can introduce resource imbalance and unnecessary data movement. We present FlexNPU, a transparent user-space virtualization layer for Ascend NPUs. FlexNPU interposes on AscendCL APIs and routes NPU operations through per-device daemons, decoupling unmodified from physical NPU devices without modifying model code, AI frameworks, or NPU drivers. This runtime boundary allows FlexNPU to virtualize NPU objects, control operator dispatch, and support phase-aware scheduling for LLM serving. In particular, FlexNPU enables dynamic PD co-location, which adapts scheduling between prefill and decode according to their complementary resource characteristics. We implement FlexNPU on Huawei Ascend NPUs and evaluate it with typical LLM workloads. Compared with direct NPU passthrough, FlexNPU introduces no measurable inference overhead and slightly improves throughput in some scenarios. On a 384-card Ascend 910C deployment of DeepSeek-R1, FlexNPU improves throughput over static PD disaggregation by 5.15% and 26.33%. On Qwen2.5-7B, compared with static PD co-location, FlexNPU maintains comparable throughput while reducing TTFT by over 92% across tested workloads with nearly unchanged TPOT. These results show that transparent NPU virtualization is a practical substrate for efficient and responsive LLM serving.

## 1. 核心问题与整体含义（研究动机和背景）

- **研究动机**：现代AI云平台越来越多地依赖NPU（如华为昇腾）进行大模型服务。然而，当前NPU部署普遍采用直接物理设备直通（passthrough）模式，将物理NPU直接暴露给应用程序。这种模式虽然简单高效，但缺乏运行时的调度控制能力，系统很难在不修改应用、框架或驱动的情况下观察和调整执行行为。
- **具体问题**：LLM推理中预填充（prefill）阶段是计算密集型，解码（decode）阶段受内存带宽和KV缓存访问限制。这两种阶段对加速器的资源压力截然不同。静态地将两者共置（co-location）会导致阶段干扰；静态分离（disaggregation）则可能造成资源不平衡（如预填充worker内存带宽利用率低，解码worker计算能力闲置），并引入不必要的KV缓存移动和协调开销。
- **整体含义**：需要一个能够动态适应工作负载变化的运行时控制层，在不改动上层应用和底层驱动的前提下，实现预填充与解码的高效协同，平衡计算与带宽资源利用率，提升LLM服务效率。

## 2. 方法论：核心思想、关键技术细节

- **核心思想**：在昇腾NPU的运行时API边界（AscendCL）处插入一个透明的用户空间虚拟化层，解耦应用与物理设备，从而在不修改模型代码、AI框架或NPU驱动的情况下，实现对NPU操作的观察、控制和动态调度。
- **关键技术细节**：
  - **架构组成**：FlexNPU包含三个组件：
    1. **FlexNPU客户端**：通过`LD_PRELOAD`注入到应用进程中，拦截选择的一组AscendCL API（设备/上下文管理、内存分配、流/事件、同步、模型/算子执行等），虚拟化应用可见的句柄，并将请求转发给守护进程。
    2. **FlexNPU守护进程**：运行在用户空间，管理本地物理NPU，维护虚拟句柄到物理资源的映射，接收客户端请求，维护请求队列，并分派操作到物理设备。同时收集运行时统计信息（算子延迟、排队延迟、内存使用等）。
    3. **FlexNPU调度器与性能分析器**：记录不同模型和阶段的执行特征（计算需求、内存占用、带宽压力），结合在线测量值，动态调整预填充和解码的分派比例。
  - **透明拦截与代理**：拦截点选择低层稳定API，大型张量数据不经过控制路径，只转发元数据和虚拟句柄。客户端与守护进程通过高效的共享内存通信，避免重量级RPC。
  - **句柄虚拟化**：应用看到的是虚拟NPU对象（虚拟设备、上下文、流、内存等），守护进程维护映射。这使得运行时调度成为可能。
  - **动态PD共置（Dynamic PD Co-location）**：
    - 预填充和解码作为独立的逻辑实例运行，但它们的NPU操作都路由通过FlexNPU守护进程。
    - 守护进程维护独立的预填充队列和解码队列，根据运行时条件（待处理操作数、执行时间、内存带宽压力、活跃序列数、NPU队列占用率等）动态调整两者的分派比例。
    - 当解码成为瓶颈且内存带宽接近饱和时，更多分派预填充工作以利用空闲计算资源；当解码积压严重时，增加解码分派份额。
    - 无需硬件级空间分区，依赖用户空间分派控制和流调度。
  - **低开销优化**：仅拦截必要API，不复制张量数据，批量化轻量记账操作，重用虚拟-物理映射。

## 6. 主要结论与发现

1. **低开销验证**：FlexNPU的透明拦截相比原生直通没有引入可测量的端到端推理开销，甚至因异步代理设计在DeepSeek-R1-Distill-Llama-8B上实现了1.08%的吞吐量提升。
2. **大规模服务提升**：在384卡昇腾910C上部署DeepSeek-R1，FlexNPU动态PD共置相比静态PD分离：
   - 1K-1K平衡负载：吞吐提升26.33%。
   - 1K-4K解码重型负载：吞吐提升5.15%。
3. **小模型共置改进**：在Qwen2.5-7B上，与静态PD共置相比：
   - 大部分工作负载下吞吐量相当或略有提升（最大3.57%）。
   - **TTFT大幅降低**：从数百秒降至亚秒级，降低超过92%（如256/1024场景从488099ms降至331.5ms，降幅99.93%）。
   - TPOT几乎不变（变化幅度在±3%以内），表明吞吐改善并非牺牲延迟获得。
4. **关键洞察**：静态PD分离的资源分配比例依赖于工作负载特征，固定分配在负载变化时导致资源失衡；FlexNPU的动态调度能够在线调整，避免死板分配，改善资源利用率。

## 7. 优点

- **设计巧妙**：在AscendCL这个窄而稳定的接口处实现透明虚拟化，无需修改应用代码、AI框架和NPU驱动，部署成本低。
- **低开销**：通过共享内存通信、不复制张量数据、仅拦截关键API等优化，实测性能无退化甚至有提升。
- **实用性**：不依赖硬件级空间分区，仅靠用户空间调度即可实现动态PD共置，对现有昇腾平台友好。
- **验证充分**：兼顾了大型MoE模型和小型密集模型，覆盖了多种工作负载特征，并同时报告吞吐量和延迟指标，结论全面。
- **增量贡献明确**：相对于现有GPU上的PD调度工作，填补了昇腾NPU平台透明虚拟化的空白，并提供了实际部署验证。

## 8. 不足与局限

- **实验覆盖有限**：
  - 仅测试了DeepSeek-R1（MoE）和Qwen2.5-7B（密集）两类模型，其他流行模型（如Llama系列、GPT系列）未涉及。
  - 未在不同规模的NPU集群（如更小或更大卡数）上验证可扩展性。
  - 静态PD分离的基线只测试了一种资源配置（6P2D），未进行最优静态比例搜索，可能高估了FlexNPU的相对收益。
- **调度策略简略**：当前调度仅基于队列深度、执行时间等简单信号，未使用更先进的机器学习预测或SLO感知策略，也未实现完全的自动缩放。
- **未覆盖多租户、迁移、容错**：论文承认这些能力是未来工作，当前仅聚焦于虚拟化和PD共置。
- **可能存在的偏差**：
  - Qwen2.5-7B实验的过载条件（request_rate等于最大并发序列数）可能使得静态共置的TTFT异常高，放大了FlexNPU的效果。
  - 实验重复次数较少（开销测试5次，Qwen实验仅2次），随机波动可能影响精度。
- **硬件平台依赖**：设计基于昇腾NPU和AscendCL API，迁移到其他NPU或GPU需要重新实现拦截层，通用性受限。
