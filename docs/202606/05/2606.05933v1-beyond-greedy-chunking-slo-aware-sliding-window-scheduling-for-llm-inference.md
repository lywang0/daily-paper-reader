## 摘要
随着大语言模型（LLM）在线服务中交互式应用的快速增长，在确保用户感知延迟的同时维持高系统吞吐量已成为推理调度的关键问题。现有LLM服务系统依赖粗粒度的输出约束，难以有效处理多请求间的资源竞争，导致资源利用效率低下，且对细粒度服务质量（QoS）区分的支持有限。我们提出SlidingServe，一种面向在线LLM推理的滑动窗口驱动的SLO感知调度系统。SlidingServe设计了一种轻量级批次延迟预测器来估计批次的执行时间。基于此，SlidingServe使用SlidingChunker结合当前迭代与下一次迭代的信息，实现动态分块，在保持严格QoS保证的同时提升系统整体吞吐量。SlidingServe引入多级优先级排序器对候选请求进行排序，以平衡公平性与效率。此外，当同一批次内的多个请求存在SLO违反风险时，SlidingServe引入BatchConstructor，通过动态规划选择当前轮次执行的请求集，缓解关键请求的SLO违反风险。我们的评估表明，在不同负载条件下，与先进调度系统相比，SlidingServe可将服务容量提升高达30%，并在高负载推理模式下进一步将SLO违反率降低16%-53%。

## Abstract
With the rapid growth of interactive applications in large language model (LLM) online services, maintaining high system throughput while ensuring user-perceived latency has become a key issue in inference scheduling. Existing LLM service systems rely on coarse-grained output constraints, making it difficult to effectively handle resource contention among multiple requests, resulting in low resource utilization efficiency and limited support for fine-grained quality of service (QoS) differentiation. We present SlidingServe, a sliding-window-driven SLO-Aware scheduling system for online LLM inference. SlidingServe designed a lightweight batch latency predictor to estimate the execution time of a batch. Based on this, SlidingServe uses SlidingChunker to combine information from the current iteration and the next iteration to achieve dynamic chunking and improve the overall system throughput while maintaining strict QoS guarantees. SlidingServe introduces Multi-Level Priority Sorter to sort candidate requests in order to balance fairness and efficiency. Additionally, when multiple requests within the same batch are at risk of SLO violating,SlidingServe introduces BatchConstructor, which uses dynamic programming to select the set of requests to execute in the current round, mitigating the SLO violation risk of critical requests.Our evaluation demonstrates that SlidingServe can improve service capacity by up to 30% compared to advanced scheduling systems under various load conditions, and further reduces the rate of SLO violation by 16%-53% under heavy-load inference mode.

## 1. 核心问题与整体含义（研究动机和背景）

- **背景**：随着LLM在线服务（如智能问答、代码生成、交互式Agent）的普及，系统需同时满足**高吞吐量**和**用户可感知的低延迟**（TTFT、TBT）。现有系统采用连续批处理和分块预填充（chunked prefill）技术来平衡吞吐与延迟，但存在关键局限。
- **核心问题**：
  - **粗粒度输出约束**：现有调度依赖固定的或者局部贪心的分块策略，无法有效处理多请求间的资源竞争，导致资源利用率低，对细粒度QoS（服务质量）区分支持不足。
  - **单步决策短视**：传统方法仅优化当前迭代的分块大小，忽略跨迭代的累积效益，容易陷入局部最优。
  - **批次内请求相互影响**：同批次中多个请求共享执行时间，若某请求接近TTFT截止时间，即使被纳入批次，仍可能因批次执行过长而违反SLO。
- **整体含义**：本文提出SlidingServe系统，旨在通过**滑动窗口驱动的SLO感知调度**，在保证严格QoS的前提下提升系统整体吞吐量，降低SLO违反率。

## 2. 方法论

### 核心思想
- **滑动窗口动态分块（SlidingChunker）**：将调度决策从单步贪心扩展为**连续两个迭代（窗口大小2，步长1）的联合优化**，通过平衡当前与下一迭代的预算分配，避免贪心导致的效率损失。
- **多级优先级排序（Multi-Level Priority Sorter, MLPS）**：综合请求的SLO紧迫性、剩余预填充工作量及保护状态，对混合负载中的请求进行统一排序，优先服务紧急且工作量小的请求。
- **批次内请求选择（BatchConstructor）**：当批次执行时间可能使部分请求违反TTFT时，通过**动态规划（0/1背包问题）**选择最优子集，确保关键请求完成预填充，同时最大化调度收益。

### 关键技术细节
1. **Batch Latency Predictor（批次延迟预测器）**：
   - 输入：批次中每个请求的分配token数、缓存token数；将请求分为解码集（D）和预填充集（P）。
   - 特征工程：提取7维特征（包括预填充注意力复杂度、解码请求数、总预填充token等），并根据批次场景（纯解码、纯预填充、混合）使用**专家模型**（场景专用线性模型）或**全局模型**。
   - 训练方式：离线初始化 + 在线增量更新（后台线程热替换）。
2. **SlidingChunker算法**（Algorithm 1）：
   - 根据当前解码请求的TBT slack计算当前迭代允许的最大执行时间 \( T_{\text{cur}} \) 和下一迭代的 \( T_{\text{next}} \)。
   - 通过**TimeToBudget**函数（二分搜索）将时间约束转化为token预算 \( B_{\text{cur}} \) 和 \( B_{\text{next}} \)。
   - 对总预算 \( B_{\Sigma} = B_{\text{cur}} + B_{\text{next}} \)，使用**离散三分搜索**寻找最优当前预算 \( b \)，最小化两轮预测执行时间之和 \( \hat{T}(b) + \hat{T}(B_{\Sigma} - b) \)。
3. **Multi-Level Priority Sorter**（公式7-13）：
   - 定义归一化紧迫度 \( u_i(t) = \frac{\text{剩余预填充时间}}{\text{TTFT剩余时间}} \)；若 \( u_i > \alpha \) 则标记为紧急。
   - 构造字典序优先级键 \( K_i(t) = (1 - g_i, 1 - e_i(t), r_i(t)) \)，其中 \( g_i \) 为保护标志（解码请求或高优先级），\( e_i \) 为是否紧急，\( r_i \) 为剩余预填充token数。
   - 按升序排序，先排保护请求，再排紧急请求，最后排短任务。
4. **BatchConstructor算法**（Algorithm 2）：
   - 触发条件：原始批次预测延迟 \( \hat{T}_{\text{full}} \) 超过某些请求的TTFT slack。
   - 锚点（anchor）选择：对每个风险请求 \( a \)，以其slack \( s_a \) 作为最大可接受执行时间，计算可用预算 \( C_a \)。
   - 强制包含锚点请求，然后对其余候选请求（slack≥\( s_a \)）求解0/1背包问题：目标是在剩余容量内最大化总价值（价值函数 \( v_j \) 综合slack和剩余工作量）。
   - 最终选择方案：优先最大化完成预填充的请求数，再最大化总价值，最后最大化使用预算。
