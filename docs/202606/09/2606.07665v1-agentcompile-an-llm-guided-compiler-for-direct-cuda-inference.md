## 摘要
Transformer推理越来越依赖于专门的编译器和运行时支持，但实际的模型图仍然需要语义决策，以确定哪些区域值得专门化以及哪些CUDA实现家族是可行的。我们提出了AgentCompile，一个LLM引导的CUDA推理编译器，它仅将LLM输出用作辅助搜索元数据。给定编译器生成的区域摘要和有界候选空间，LLM提出语义标签、候选优先级、参数提示和风险注释；编译器通过模板具体化CUDA候选，检查接口和硬件约束，经验性地验证候选，根据测量延迟选择实现，并在不支持专门化或无利可图时回退。在端到端自回归生成中，AgentCompile在五个代表性工作负载上，相对于PyTorch eager模式，分别在Qwen3-1.7B、Qwen3-4B和Llama-3.2-1B-Instruct上实现了平均5.66倍、4.05倍和4.26倍的加速。我们将开源该项目。

## Abstract
Transformer inference increasingly depends on specialized compiler and runtime support, but real model graphs still require semantic decisions about which regions are worth specializing and which CUDA implementation families are plausible. We present AgentCompile, an LLM-guided CUDA inference compiler that uses LLM outputs only as advisory search metadata. Given compiler-derived region summaries and bounded candidate spaces, the LLM proposes semantic labels, candidate priorities, parameter hints, and risk annotations; the compiler materializes CUDA candidates through templates, checks interface and hardware constraints, validates candidates empirically, selects implementations by measured latency, and falls back when specialization is unsupported or unprofitable. In end-to-end autoregressive generation, AgentCompile averages 5.66x, 4.05x, and 4.26x speedup over PyTorch eager on Qwen3-1.7B, Qwen3-4B, and Llama-3.2-1B-Instruct, respectively, across five representative workloads. We will open-source the project.

## 1. 核心问题与整体含义（研究动机和背景）

- **研究对象**：现代Transformer推理依赖编译器（如TVM、PyTorch 2、Triton等）和运行时（如vLLM）将高层模型映射到加速器执行，但真实模型图仍需要**语义决策**——判断哪些区域值得CUDA专门化以及哪些CUDA实现族可行。
- **现有挑战**：
  - PyTorch eager执行保留大量Python分发、动态缓存管理和逐token启动开销；torch.compile通过融合减少开销，但长上下文生成仍暴露开销；vLLM优化调度和页式KV缓存，但侧重服务层面。
  - 直接让LLM生成CUDA代码存在正确性风险（索引、同步、内存边界等）。
- **核心动机**：需要一个系统，既能利用LLM的语义理解能力来指导搜索，又不将正确性关键决策交给LLM，而是由编译器控制的确定性机制保证。

## 2. 论文提出的方法论

### 2.1 核心思想
- **LLM仅作为辅助搜索元数据**：编译器提供区域摘要和有界候选空间；LLM输出语义标签、候选优先级、参数提示和风险注释；编译器负责模板生成、约束检查、经验验证、基准测试和回退。
- **分离决策责任**：LLM影响搜索顺序和风险标注，但从不直接生成或接纳可执行代码。

### 2.2 关键技术细节（八阶段编译器流水线 + 混合运行时）

#### 流水线三阶段：
1. **模型捕获**：获取追踪计算图（节点为张量操作，边为依赖），包含形状、dtype、布局等元数据。
2. **分析与生成**：
   - **图分析器（Graph Analyzer）**：将图分区为候选区域（基于依赖、别名、副作用等确定性规则），记录操作序列、接口、归约轴、动态形状标志等。仅对混合、复杂GEMM-epilogue或归约-逐点区域才调用LLM。
   - **规划器（Planner）**：对每个区域枚举合法融合/调度/内存/并行化选择，形成有界候选空间。LLM可在此空间中建议参数（如向量宽度、线程数），但参数必须已属于枚举空间。
   - **CUDA代码生成器**：基于确定性模板生成CUDA代码（模板库包含向量化逐元素、归约、softmax、LayerNorm、tiled GEMM、Tensor-Core GEMM、decode GEMV等）。LLM只提供模板偏好或诊断提示，不修改源代码。
3. **验证与发射**：编译、接口检查、数值对比（有参考路径时）、内存安全检查；基准测试择优；发射CUDA源文件、头文件、封装器、构建脚本。

#### 关键算法（Algorithm 1）：
```
1. 捕获模型图并构建标准化IR。
2. 将IR分区为区域{r}。
3. 对每个区域r：
   a. 构建摘要S(r)，从模板和硬件约束枚举候选空间C(r,H)。
   b. 查询LLM获得建议元数据（标签、优先级、参数提示、风险注释）。
   c. 将建议转换为检查后的计划：拒绝不支持标签、违反约束的融合、无效参数、候选空间外的候选。
   d. 通过模板实例化CUDA候选，编译、验证、基准测试。
4. 选择最快的验证候选；否则回退到原始框架路径。
```

#### 混合运行时边界：
- **流水线生成的核**：编译器产出。
- **运行时集成的核**：手动实现的Triton/C++扩展（融合RoPE、残差-RMSNorm、融合激活-乘等），消除已知解码开销。
- **第三方核**：FlashAttention、cuBLAS。
- 只有第一类支持编译器生成声明；后两类提供竞争性端到端解码的运行时上下文。

#### 自定义线性替换（CUDALinear）：
- 替换PyTorch nn.Linear，解码时选择M=1的GEMV路径（权重预转置，使用256线程块、128位向量化加载、warp shuffle归约）。
- 可根据N大小自适应切换输出并行化策略。

#### KV缓存管理：
- FlashKVCacheManager预分配固定大小K/V缓冲区，跟踪序列长度，与FlashAttention配合。

## 6. 主要结论与发现

1. **端到端加速显著**：在五个代表性工作负载上，AgentCompile相对于PyTorch eager的平均加速比为Qwen3-1.7B: 5.66×, Qwen3-4B: 4.05×, Llama-3.2-1B: 4.26×。
2. **优于torch.compile**：torch.compile平均加速比仅为1.79×~2.27×，AgentCompile显著更优。
3. **与vLLM竞争**：在Qwen3-1.7B和Llama-3.2-3B上，AgentCompile平均比vLLM快1.06×和1.07×，且vLLM优化了不同层，方法可互补。
4. **长输出优势更明显**：速度随输出长度增加而更加突出，反映了解码导向设计（CUDA Graph重放、专用GEMV、融合核）降低逐token开销的效果。
5. **消融分析揭示关键贡献**：CUDA Graph重放是最大单一改进（2.06×），其次是CUDALinear+GEMV（1.45×），LLM引导+融合核带来1.33×额外提升。最后一步并未单独分离LLM贡献。

## 7. 优点

- **设计优雅且安全**：将LLM置于语义建议角色，编译器和运行时控制所有可执行决策，避免LLM直接生成代码带来的正确性风险。
- **通用性**：方法不依赖特定模型，可应用于任意Transformer图，只要区域可被编译器分区。
- **实验透明度高**：明确划分了编译器生成核、手工集成核、第三方核的边界，便于理解加速来源。
- **消融设计清晰**：逐步添加组件，量化每个模块贡献，尽管最后一步是捆绑的。
- **实践可复用**：项目将开源，有助于社区复现和扩展。
- **性能优秀**：在长输出场景下大幅超越PyTorch eager和torch.compile，与vLLM相当，且可融合服务于层优化。
