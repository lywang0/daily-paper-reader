## Abstract 

Transformer inference increasingly depends on specialized compiler and runtime support, but real model graphs still require semantic deci-sions about which regions are worth special-izing and which CUDA implementation fam-ilies are plausible. We present A GENT COM -

> PILE

, an LLM-guided CUDA inference com-piler that uses LLM outputs only as advisory search metadata. Given compiler-derived re-gion summaries and bounded candidate spaces, the LLM proposes semantic labels, candidate priorities, parameter hints, and risk annotations; the compiler materializes CUDA candidates through templates, checks interface and hard-ware constraints, validates candidates empiri-cally, selects implementations by measured la-tency, and falls back when specialization is un-supported or unprofitable. In end-to-end autore-gressive generation, A GENT COMPILE averages 

5.66 ×, 4.05 ×, and 4.26 × speedup over Py-Torch eager on Qwen3-1.7B, Qwen3-4B, and Llama-3.2-1B-Instruct, respectively, across five representative workloads. We will open-source the project. 

## 1 Introduction 

Modern neural-network inference relies on com-pilers and runtimes that map high-level model pro-grams to efficient accelerator execution. Systems such as TVM, PyTorch 2, MLIR, XLA, Triton, FlashAttention, and vLLM provide graph capture, lowering, kernel generation, optimized attention, and serving-oriented execution paths (Chen et al., 2018a; Ansel et al., 2024; Lattner et al., 2021; OpenXLA Project, 2024; Tillet et al., 2019; Dao et al., 2022; Kwon et al., 2023). However, specializ-ing transformer inference graphs remains difficult because profitable regions often emerge only af-ter tracing, decomposition, framework lowering, model-specific implementation choices, and shape specialization. 

Figure 1: The comparison between standard PyTorch and A GENT COMPILE for the inference stack. 

Existing optimization paths address different layers of the inference stack but leave an impor-tant gap. PyTorch eager execution retains sub-stantial Python dispatch, dynamic-cache manage-ment, and per-token launch overhead during autore-gressive decoding. torch.compile reduces over-head through fusion and compiled graph fragments, but long-context generation still exposes dynamic cache updates, graph breaks, shape variation, and attention/GEMM costs. Serving runtimes such as vLLM optimize request scheduling and paged KV cache management, which is complementary to region-level kernel specialization. Directly ask-ing an LLM to generate CUDA code is also risky because kernel correctness depends on indexing, synchronization, memory bounds, dtype handling, launch configuration, layout assumptions, and hard-ware behavior. The resulting challenge is to use the semantic strengths of LLMs without moving correctness-critical decisions outside the compiler. A useful system should let an LLM interpret graph frag-ments, rank implementation families, and sug-gest parameter hints, while ensuring that exe-cutable candidates remain constrained by graph metadata, template availability, hardware limits, validation, and measurement. It should also sep-arate compiler-pipeline evidence from end-to-end 1

generation speedups in a realistic runtime. To address this challenge, we present A GENT -COMPILE , an LLM-guided compiler framework for transformer-style inference optimization. The compiler constructs graph regions, structured sum-maries, and bounded executable candidate spaces. The LLM provides advisory metadata–semantic labels, candidate priorities, parameter hints, and risk annotations–while compiler mechanisms per-form constraint checks, template-based CUDA gen-eration, empirical validation, benchmarking, and fallback. Thus, LLM outputs guide search but do not define executable behavior. Figure 1 shows AGENT COMPILE as a compiler/runtime substitu-tion layer between Python model code and CUDA execution. This paper makes three contributions: (i) it for-mulates LLM-guided inference optimization as se-mantic search within compiler-defined candidate spaces constrained by graph, interface, and hard-ware requirements; (ii) it implements a compiler-controlled pipeline that maps LLM advice to template-generated CUDA candidates admitted only through checks, validation, benchmarking, and fallback; and (iii) it evaluates the resulting hy-brid inference runtime while separating end-to-end gains from custom GEMV kernels, CUDALinear replacement, custom KV cache management, fused decode kernels, CUDA Graph replay, and LLM-guidance claims. 

## 2 Problem Formulation and Design Goals 

Given a captured inference graph, A GENT COM - 

> PILE

seeks to replace only those graph regions that can be safely specialized by CUDA implementa-tions. The central constraint is that LLM guid-ance may affect search, but it may not define exe-cutable semantics. Graph construction, candidate-space construction, CUDA materialization, valida-tion, benchmarking, and fallback remain compiler-controlled. We model an inference program as a directed graph G = ( V, E ), where nodes are tensor oper-ations and edges are data dependences. A region 

r ⊆ V is a connected subgraph with an external interface: input tensors, output tensors, boundary dependencies, dtype/layout assumptions, reduction axes, and a calling convention. A CUDA replace-ment is admissible only if it preserves this interface and passes the validation protocol for the surround-ing inference path. For a region r and target hardware/runtime con-figuration H, the compiler constructs an executable candidate space C(r, H ). Each candidate specifies an implementation family and realizable parame-ters, such as fusion boundary, template type, tile size, thread count, vector width, reduction map-ping, shared-memory policy, and launcher inter-face. This space is induced by deterministic region extraction, template availability, tensor metadata, and hardware constraints. The LLM can rank candi-dates or suggest parameters inside this space, but it cannot create candidates outside C(r, H ) or bypass compiler-side constraint and interface checks. The LLM observes a compiler-generated region summary S(r) rather than raw source code. It re-turns advisory metadata of 

ALLM (S(r), C(r, H )) = ( ℓr, π r, η r, ρ r),

where ℓr is a semantic label, πr is a candidate pref-erence order, ηr contains parameter hints, and ρr

contains risk annotations. These outputs are treated as hypotheses: unsupported labels, invalid parame-ters, and suggestions that cross hard graph bound-aries are rejected by compiler checks. When a reference path is available, Check 

includes numerical comparison under dtype-appropriate tolerances; otherwise it uses structural, smoke-test, and end-to-end consistency checks. This is empirical validation, not formal equivalence. Among validated candidates V(r), the compiler selects c⋆ = arg min c∈V (r) T (c) by measured la-tency. If no candidate is valid or faster than the original path, the region falls back to the frame-work or library implementation. This formulation separates region-level candidate generation, inte-grated end-to-end speed, and the still-pending iso-lated contribution of LLM guidance. 

## 3 Method 

AGENT COMPILE implements the formulation above as an eight-stage compiler pipeline plus a hybrid runtime layer. It captures a PyTorch or HuggingFace model, forms compiler regions, con-structs bounded CUDA candidate spaces, uses the LLM only to prioritize and annotate candidates, and selects executable kernels through validation and measurement. Figure 2 illustrates the key con-tract on a representative region r5: LLM output is advisory metadata, while candidate admission remains deterministic. 2Figure 2: Running example of compiler-guided LLM assistance on a representative region named r5. In Graph Analyzer, a structured region summary is first derived from graph analysis, and given to the LLM. The LLM may identify the region as a softmax or normalization pattern, and return semantic labels, candidate preferences, parameter and risk hints. Such labels are considered hypotheses rather than correctness guarantees. In Planner, the compiler still checks that the recommended candidates respect dependencies, reduction semantics, dtype and layout constraints, template availability, and hardware limits before any CUDA implementation is materialized. Only kernel-plan candidates that pass constraint filtering are sent to the Code Generator and materialized as CUDA candidates. Once they pass validation checks, the best validated kernels are selected as the final CUDA kernel outputs.

3.1 Graph Analyzer: Region Construction 

The analyzer decides which operations may form a candidate region before the LLM is consulted. It builds use-def dependencies and topologically traverses the IR. Non-compute and layout-only nodes such as placeholders, model-attribute ac-cesses, views, reshapes, contiguity conversions, transposes, broadcasts, and slices are treated as boundary metadata or attached to nearby compute regions when safe, rather than optimized as stan-dalone kernels. Consecutive pointwise, activation, softmax, norm, and reduction nodes may be merged under compatible dtype and layout assumptions. Matmul nodes usually form independent regions, but simple epilogues can be attached when depen-dency and interface constraints allow. In-place operations, side effects, unresolved aliasing, un-supported dtypes, and ambiguous dynamic shapes form hard boundaries. For each accepted region, the analyzer records operator sequence, tensor shapes, dtype and ac-cumulation dtype, reduction axes, dominant op-eration kind, memory-access pattern, estimated FLOPs/bytes, arithmetic intensity, and dynamic-shape flags. Rule-based recognition assigns se-mantic categories such as GEMM regions, GEMM regions with epilogues, softmax-like regions, RMSNorm-like regions, elementwise chains, or reduction followed by pointwise computation. The LLM is invoked only when this semantic layer is useful, such as mixed regions, complex GEMM epi-logues, or reduction–pointwise regions. Its labels may refine priorities or risk annotations, but the re-gion boundary is accepted only after deterministic dependency, alias, and side-effect checks. 

3.2 Deterministic CUDA Planner 

The planner converts each region into a bounded set of kernel plans rather than asking the LLM to invent implementations. It first constructs a prod-uct of deterministic design choices. The fusion planner chooses among single-kernel execution, full fusion, no fusion, or partial fusion depend-ing on region size, side effects, dtype consistency, and layout compatibility. The schedule planner then maps recognized patterns to template families: tiled or Tensor-Core GEMM, row-wise softmax, block/warp reductions, row-based normalization, grid elementwise kernels, and decode-oriented GEMV. Memory and parallel choices then attach vector width, shared-memory policy, grid/block shape, warp mapping, and reduction strategy. Plans are filtered before ranking. Shared-memory usage, thread count, vector alignment, reduction semantics, template availability, and launcher signatures must all match the target re-gion and hardware. Remaining plans are ranked by deterministic heuristics such as fusion benefit, vec-torization, estimated occupancy, template-pattern match, and risk level. For high-value regions, the LLM receives a structured candidate summary and may reorder top candidates or suggest parameters such as vector width, number of threads per block, or unroll factors. Such suggestions are accepted only if they already belong to the enumerated plan space; a diversity filter preserves multiple template families when possible. 

3.3 CUDA Code Generation, Validation, and Selection 

The code generator materializes checked plans using deterministic templates. The template library covers vectorized elementwise ker-nels, reductions, numerically stable softmax, LayerNorm/RMSNorm-style normalization, tiled GEMM, Tensor-Core GEMM for supported archi-tectures, and decode-oriented GEMV. Templates own the executable details–indexing, boundary checks, dtype conversion, synchronization, shared-memory layout, and launch signatures. The LLM may provide template preferences or diagnostic hints after failed compilation, but source code is still produced under compiler control. 

Generated GEMV kernels. GEMV is the most important generated family for autoregressive de-4coding because each decode step applies many lin-ear projections with effective batch size M = 1 .The generated GEMV stores weights in an [N, K ]

layout so each output column reads a contiguous weight row, launches a 256-thread block for re-duction work, uses 128-bit vectorized loads when aligned, and reduces partial sums with warp shuf-fles rather than shared-memory trees. This avoids shared-memory bank conflicts and reduces synchro-nization overhead. A dual-path adaptive-N strategy changes output parallelization for large N to keep enough blocks resident. Compared with a general GEMM path, this specialization removes unneces-sary GEMM machinery and layout handling, and better matches the low-arithmetic-intensity, single-row decode workload. Generated candidates pass an admission pipeline: compilation failures are removed; interface checks ensure compatibility of tensor shapes, dtypes, lay-outs, and launcher signatures; numerical checks compare candidate outputs against the framework path when a reference is available; and auxiliary kernels use structural or smoke tests and must pass end-to-end consistency checks before integration. Optional memory-safety tooling can also be en-abled. The benchmark selector measures only vali-dated candidates under a fixed warmup/repetition protocol and selects the fastest candidate per re-gion; LLM confidence scores never select kernels directly. 

3.4 Runtime Integration Boundary 

End-to-end generation uses a hybrid runtime be-cause not every transformer operation should be replaced by generated code. We distinguish three implementation sources. Pipeline-generated ker-nels are emitted by the compiler pipeline. Runtime-integration kernels are manually implemented Tri-ton or C++ extension components that remove known decode overheads. Third-party kernels in-clude FlashAttention and cuBLAS. Only the first class supports the compiler-generation claim; the latter two provide the runtime context for compet-itive end-to-end decoding. This boundary is im-portant for interpreting experiments: end-to-end speedups measure the complete hybrid path, while compiler-pipeline statistics supports the generated-candidate process. 

Fused runtime kernels. The hand-written fused kernels target frequent decode operations that are not always exposed as single compiler regions. Fused RoPE applies rotary embeddings to Q and K in one Triton launch; fused residual–RMSNorm combines residual addition and normalization with float32 accumulation; fused activation–multiply covers the MLP gating path; and the C++ extension provides fused GEMV epilogues such as Gate/Up GEMV with SiLU or GELU and Down-projection GEMV with residual addition. 

Custom linear replacement. CUDALinear re-places PyTorch nn.Linear in the decode path and dispatches to custom CUDA GEMM/GEMV ker-nels through either ctypes or a C++ extension. The module pre-transposes weights at construction time, selects an M =1 GEMV path for single-token decoding, and can fall back to cuBLAS for prefill or CUDA Graph capture. We use the C++ extension path when possible to reduce Python-side dispatch overhead and integrate the generated kernels with the hybrid runtime. 

KV cache management and attention compu-tation. FlashKVCacheManager is our memory-management layer for FlashAttention-based decod-ing. It preallocates fixed-size K/V buffers, tracks per-layer sequence lengths on the GPU, imports prefill states produced by the HuggingFace Dynam-icCache, and exposes reset and length-update utili-ties. Actual attention computation and in-place KV appends are performed by the FlashAttention with KV cache update API: the manager owns buffer lifetime and valid-length metadata, while the third-party attention kernel reads and writes the buffers and computes attention for the current query token. 

Component accounting. For Qwen3-1.7B, which has 28 transformer layers, a direct 

CUDALinear replacement covers seven projections per layer, or 196 potential pipeline-generated GEMV calls per decode step across 28 layers. With fused epilogue extensions enabled, the four attention projections remain on the generated GEMV path, while the three MLP projections use fused runtime kernels for gate–up SiLU computation and residual-add GEMV computation. This approximate 57% / 43% split by projection groups is component accounting, not isolated speedup attribution.

## 6 Conclusion 

This paper presented A GENT COMPILE , an LLM-guided compiler framework for transformer-style inference optimization. The key idea is to place the LLM at semantic decision points while keep-ing executable behavior under deterministic com-piler and runtime control. A GENT COMPILE con-structs structured region summaries and bounded candidate spaces, using LLM outputs to guide se-mantic search while relying on compiler checks, empirical validation, benchmarking, and fallback for executable decisions. In end-to-end genera-tion experiments, the resulting hybrid runtime sub-stantially outperforms PyTorch eager execution, remains competitive with vLLM, and shows in-creasing advantages in long-output regimes where decode-side overheads dominate. These results sup-port a conservative design in which LLMs improve semantic search without taking over correctness or selection decisions. 87 Limitations 

AGENT COMPILE is a prototype. It targets transformer-style inference regions, and unsup-ported regions fall back to the original framework or library path. LLM guidance is a search policy over compiler-defined candidate spaces, so it may improve ordering or provide useful semantic hy-potheses but does not guarantee optimal implemen-tations. To further augment the performance of the proposed method, we will explore more delicate and efficient CUDA kernels in future work.

## A Supplementary Implementation Notes 

This appendix records implementation details that support, but do not repeat, the main method. The frontend supports single-file modules, project direc-tories, and HuggingFace identifiers. The IR builder normalizes operator names and records numerical contracts such as precise softmax/norm behavior, associative reduction or matmul behavior, and re-laxed elementwise behavior. The analyzer calls the LLM only for regions whose rule-based pattern is mixed, complex GEMM-epilogue, or reduction-pointwise and whose region size justifies semantic analysis. Accepted LLM metadata is stored as re-gion hints and planner preferences; rejected advice is ignored without changing the graph. The planner constructs candidates using fusion, schedule, memory, and parallel sub-planners. Can-didate generation is deliberately bounded: every plan must have a known template, a compatible launcher signature, and hardware-valid parame-ters before code generation. The code genera-tor includes templates for elementwise chains, re-ductions, softmax, normalization, GEMM, Tensor-Core GEMM, GEMV, and selected fused epilogues. Validation combines compilation, interface checks, empirical numerical checks when available, and optional memory-safety tooling. The benchmark selector records latency for validated candidates and the emitter writes source, headers, wrappers, metadata, and build scripts.

## C Systems Compared 

Table 1 summarizes the runtime path of each sys-tem. PyTorch eager uses HuggingFace/PyTorch generation with DynamicCache, framework dis-patch, cuBLAS linear layers, and PyTorch SDPA when applicable. torch.compile with FlashAtten-tion evaluates a PyTorch-native optimization path with Inductor fragments and a FlashAttention patch, but it still follows the framework generation path with dynamic KV cache growth. vLLM represents a serving runtime with PagedAttention, paged KV blocks, scheduling, and CUDA Graph replay for common decode shapes. AGENT COMPILE uses a hybrid path: one-time preparation pre-allocates fixed-size KV buffers (FlashKVCacheManager ), patches attention lay-ers for FlashAttention-based KV cache decode (FlashAttention with KV cache update), replaces linear layers with CUDALinear , warms up the path, and captures single-token decode into a CUDA Graph.
