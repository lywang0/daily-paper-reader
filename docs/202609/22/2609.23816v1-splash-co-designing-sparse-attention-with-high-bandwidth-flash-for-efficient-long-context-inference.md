## 摘要
随着上下文长度、并发量和请求生命周期不断增长，键值（KV）缓存已成为大语言模型（LLM）服务系统中内存的主要消耗者。高带宽内存（HBM）可提供注意力解码所需的带宽，但容量有限；而封装外内存和存储虽能增加容量，却缺乏维持注意力解码的带宽。高带宽闪存（HBF）是一种有前景的介质，兼具太字节级容量与接近 HBM 的读取带宽。有限的写入耐久性使其天然适合只读模型权重，但我们认为，将 HBF 与 HBM 组成层级结构也可用于存放 KV 缓存。与以往层级结构中次级层受带宽瓶颈制约不同，二者带宽相当，因此可作为用于长上下文 KV 缓存的一个逻辑内存。HBF 的容量支持长上下文服务，而稀疏注意力通过限制内存受限解码期间的 KV 缓存读取，使其变得高效。由于 HBF 读取整个闪存页，并通过访问数千个并行闪存平面来聚合带宽，稀疏注意力必须与这些物理特性协同设计。我们提出 SPLASH，一种算法与架构协同设计，将 KV 缓存虚拟化到 HBM 和 HBF 之上，并使稀疏注意力适应 HBF 的页粒度和平面级并行性。在不同模型和上下文长度下，在每 token 100 ms 延迟目标下，SPLASH 相比所评估的基线将每 GPU 解码吞吐量提升 3.5 倍至 11.4 倍，同时在长上下文套件上将准确率保持在密集注意力 4% 以内。

## Abstract
The key-value (KV) cache has become the dominant consumer of memory in large language model (LLM) serving systems as context lengths, concurrency, and request lifetimes grow. High-bandwidth memory (HBM) provides the bandwidth attention decode needs but limited capacity, while off-package memory and storage add capacity but lack the bandwidth to sustain attention decode. High-Bandwidth Flash (HBF) is a promising substrate that combines terabyte-scale capacity with near-HBM read bandwidth. Limited write endurance makes read-only model weights its natural use, but we argue that HBF paired with HBM as a hierarchy can also hold the KV cache. Unlike prior hierarchies, whose secondary tiers are bandwidth bottlenecked, the comparable bandwidths let the two act as one logical memory for the long-context KV cache. HBF capacity enables long-context serving, and sparse attention makes it efficient by limiting KV-cache reads during memory-bound decode. Since HBF reads full flash pages and aggregates bandwidth by accessing thousands of parallel flash planes, sparse attention must be co-designed with these physical properties. We present SPLASH, an algorithm and architecture co-design that virtualizes the KV cache across HBM and HBF and adapts sparse attention to HBF's page granularity and plane-level parallelism. Across models and context lengths, SPLASH improves decode throughput per GPU by 3.5x-11.4x over the evaluated baselines under a 100 ms per-token latency objective, while keeping accuracy within 4% of dense attention across long-context suites.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景矛盾**：LLM 服务中 KV 缓存已成为内存的主要消耗者。上下文长度、并发量、请求生命周期三者叠加，使容量需求急剧膨胀。文中举例：Qwen3-235B-A22B 上 64 个百万 token 并发请求需要 12.9 TB KV 缓存，足以填满 68 张 B200 的 HBM（且尚未计入模型权重）。
- **现有方案的两难**：
  - HBM 带宽足够但容量有限；单纯堆叠 GPU 会浪费本已闲置的解码算力，KV 池化又带来复制/通信开销。
  - host DRAM、CXL、SSD 等次级存储容量大，但 PCIe/CXL 带宽比 HBM 低约两个数量级，prefetch/chunking/buffering 无法弥合这一鸿沟，内存受限的解码会退化为传输受限。
- **HBF 的机遇与约束**：高带宽闪存（HBF）通过 TSV 堆叠闪存裸片置于封装内，兼具 TB 级容量与接近 HBM 的读带宽（12.9 TB 的 KV 缓存从 68 张 GPU 的 HBM 缩至 5 张 GPU 的 HBF 容量）。但 HBF 存在三重物理约束：
  - 以 **页（4 KiB 级）** 为最小读单位，非 HBM 的百字节粒度；
  - 带宽靠 **上千个并行 plane** 聚合，单 plane 读串行，需处理 plane 负载不均衡；
  - **写耐久性有限**，页不可原地覆盖，写/擦代价高（100 μs 编程、10⁵ P/E 周期）。
- **核心论点**：以往层级结构的次级层都是带宽瓶颈，而 HBM 与 HBF 带宽可比，因此可**作为一个逻辑内存**共同承载长上下文 KV 缓存；HBF 提供容量，稀疏注意力提供效率。但稀疏注意力必须与 HBF 的页粒度、平面并行、写一次放置特性**协同设计**——这正是既有 token 级稀疏方法（为 HBM/DRAM/PIM 设计）无法直接迁移的原因。
- **整体含义**：SPLASH 是首个 HBM–HBF KV 缓存虚拟化工作，也是首个围绕 HBF 物理组织设计的稀疏注意力机制，试图用"容量与算力解耦"打破长上下文推理的内存墙。

## 2. 方法论：核心思想与关键技术

### 2.1 总体分层协同设计
- **算法层**：HBM 中保留窗口 $W$（attention sinks + 近期 token）做稠密注意力，HBF 中的长历史 $H$ 做 HBF 原生稀疏注意力；两路输出按注意力质量加权合并：
  $o = (Z_W o_W + Z_S o_S)/(Z_W + Z_S)$。
- **软件层**：服务运行时管理跨层放置与生命周期，对外呈现单一逻辑 KV 缓存。
- **硬件层**：定制 HBM/HBF base die 在 GPU 内存接口之下完成翻译、稀疏选择与闪存管理。

### 2.2 HBF 原生稀疏注意力（算法关键细节）
- **页对齐的预算制选择**：逻辑 KV 页直接映射物理闪存页，K/V 分开存储。4 KiB BF16 页在 $d=128$ 时容纳 16 个 token（单 KV head）。每层每 KV head 选择 $K_p$ 个 key–value 页对，构成固定比例的检索预算（实验用 10%）；sink 常驻 HBM，不占预算。
- **共选打包（co-selection packing）**：闪存页不可重排，页构成必须在写入时固定。SPLASH 利用 token 在 HBM 驻留期间的稠密注意力打分，采样 512 次观测记录"是否落入 top-$K_p n_p$"的 1 bit 位图（1,024 token 驱逐批每 KV head 需 64 KiB）；压缩为 16 维分量后，在 HBM 侧对每个驱逐批做一次**平衡递归二分**，把被相似查询共同选中的 token 归入同一页，使页均值 key 更具代表性。共享前缀无观测历史，改用 key 相似度分组。
- **质心打分（centroid scoring）**：每页用其 token key 的均值 $\bar{k}_p$ 作为摘要，打分 $s(p) = q \cdot \bar{k}_p$。由线性性，它恰等于该页精确的 mean pre-softmax logit；误差仅在于"按均值排序"这一近似（检索后仍对页内所有 K/V 计算精确注意力）。扫描流量从 $N S_p$ 降到 $N S_s$，即降低 $n_p$ 倍，而存储仅增加 $1/(2n_p) = 3.125\%$（$n_p=16$）。
- **GQA 池化**：$G$ 个 query head 共享一个 KV head，若各自独立选择会产生最多 $G$ 个页集、超出物理预算；SPLASH 用池化查询 $\bar{q} = \frac{1}{G}\sum_h q_h$ 排序，由线性性等价于逐 head 打分求和，同时把打分工作量除以 $G$（Llama-3.1-8B 上为 4 倍）。
- **扫描隐藏**：质心扫描（$N S_s$ 字节）与 HBM 窗口注意力重叠，注意力路径成本 $T_{attn} = \max(T_{dense}, T_{scan}) + T_{read}$，仅暴露 $\max(0, T_{scan} - T_{dense})$；当窗口注意力足以覆盖扫描时暴露为零。
- **平面均衡选择**：检索轮数 $R = \max_u L_u$ 由最忙 plane 决定。页按 $u(p,h) = (p + hP/2n_h) \bmod P$ 条带化跨 plane 放置，并施加每 plane 上限 $k = \lceil 2K_p n_h / P \rceil$；plane 满则跳过该候选，取下一个未满 plane 的最高分候选。检索至多 $k$ 轮完成，代价是 top-k 召回变化 ≤0.002、PG-19 困惑度变化 ≤0.04。

### 2.3 架构与微架构
- **统一控制平面**：每个 GPU 内存端口接定制 HBM base die，再以菊花链连到一个 HBF base die；两条独立 UCIe（2×512 GB/s、Raw Mode）链路，HBM base die 负责地址译码与响应仲裁。
- **四重虚拟化**：(1) 单一地址空间；(2) 页选择对 GPU 抽象（GPU 只发一条 `SelectFetch`，携带 request id、KV head、query）；(3) 页粒度隐藏在内存接口后（SRAM bridge 把跨 plane 的 MB 级读出重整为 HBM 粒度突发）；(4) 初始读延迟被同层 HBM 访问掩盖，双缓冲 SRAM bridge 重叠后续 sense 与传输。
- **稀疏 KV 内存控制器**：读路径用 token 元数据把 `SelectFetch` 解析到请求的 HBF region，在 die 内完成质心打分、按 plane 预算选择、生成 `HBFReadList`；写路径按请求放置被驱逐页与质心。
- **超块（superblock）放置**：超块包含每 plane 一个擦除块，独属于一个请求；连续页跨 plane 条带化，KV head 偏移 $P/2n_h$，key/value 页落在不同 plane。请求级隔离与跨 plane 条带化在超块粒度上共存，回收以超块为单位整块擦除，消除页级重定位与垃圾回收。
- **查询驱动的地址翻译**：选择引擎扫描质心，保留每 plane top-$k$，把 offset 与 valid bit 写入 page offset table；闪存控制器每轮每 plane 读一条表项并 sense 对应页。未选中页不产生物理读。选择不再先于翻译，因为数据相关的选择**本身决定**了映射。
- **简化 FTL**：页写一次、原地驻留、请求粒度回收，只需 region block table（$j=i+o$，$p = j \bmod P$，$r=\lfloor j/(PB)\rfloor$，$q=\lfloor j/P\rfloor \bmod B$，查 $T[\text{request},r,p]$），2.25 MiB SRAM，替代传统 L2P（1 TiB flash 需 1 GiB DRAM）。
- **软件与编程模型**：以单调的 horizon 区分 HBM/HBF 驻留，每请求元数据固定 4 KiB；四个定长描述符 `HBFBind / HBFAppend / SelectFetch / HBFRelease`，百万 token 请求与 128K 请求使用相同命令接口与发射率。
- **仿真框架 OpenHBF**：以 Vidur 提供事件驱动服务模型（含实测 Blackwell 解码 kernel 延迟），自研 plane 级闪存后端融合 MQSim 器件模型与 Ramulator 架构模型。

## 3. 实验设计

- **模型与场景**：Llama-3-8B、Llama-3-70B、Mixtral-8x22B、DeepSeek-67B、Qwen3-235B-A22B，各在 128K / 512K / 1M 上下文（共 15 个模型×长度组合）；batch size 1–128，张量并行度 1–8。模型权重以 BF16 存于 HBF，HBM 窗口上限 16,000 token，所有稀疏设计统一 10% 检索预算。

- **指标**：在 50/100 ms p50 TPOT 目标下最大化 goodput/GPU（$1000 B / (\text{TP} \cdot \text{TPOT}_{p50})$）、TPOT p50/p99、tokens/J。
- **精度评测**：Llama-3.1-8B-Instruct，16-token 页、1,024 plane、平面均衡选择、GQA 均值池化。长上下文套件包括 RULER、LongBench、PG-19、LV-Eval、InfiniteBench、L-Eval；对比 Quest、STARC、PyramidKV、SnapKV、Recency、Random、token oracle（按精确 q·k 逐 token 选择的参考上界）、Dense。公平性控制：所有方法同样给 16 个 sink token、无 recent-token 窗口，预算为唯一差异。
- **专项实验**：6 个 LongBench 任务的 2%–50% 预算扫描；PG-19 128K/32K 困惑度曲线；64K 下 48 needle 多针检索；共选页 vs 位置页 vs STARC vs 几何聚类的页构造对比；plane 负载不均衡测量（aliasing/striping/balanced）；能耗模型在 243 组能量系数组合下的敏感性；耐久性与寿命分析（基于 Mooncake、BurstGPT、OpenHands、生产 API 保留策略等真实轨迹）。
