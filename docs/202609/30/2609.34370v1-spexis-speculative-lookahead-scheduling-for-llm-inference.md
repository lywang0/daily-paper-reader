## 摘要
Spexis 是一个多 GPU LLM 推理框架，通过推测并行提升流水线并行和张量并行的效率。Spexis 并非仅将推测解码用于加速 token 生成，而是让推测与正常执行并行运行，在不增加 KV 缓存内存占用的情况下引入新的并行维度。这提高了内存效率，并有助于缓解多 GPU 推理的瓶颈。Spexis 进一步采用前瞻调度来预测推测质量和未来内存压力，从而减少无效推测、KV 缓存驱逐和重计算。Spexis 构建于 vLLM 之上，在多种 GPU 配置下大幅提升服务性能，相比采用流水线并行和张量并行最优组合的基线，最高可实现 34% 的加速。Spexis 的源代码公开在 https://github.com/mlsys-seo/spexis。

## Abstract
Spexis is a multi-GPU LLM inference framework that improves the efficiency of pipeline and tensor parallelism through speculative parallelism. Rather than using speculative decoding only to accelerate token generation, Spexis runs speculation in parallel with normal execution, introducing a new parallelism axis without increasing KV-cache memory usage. This improves memory efficiency and helps mitigate the bottlenecks of multi-GPU inference.   Spexis further uses lookahead scheduling to predict speculation quality and future memory pressure, allowing it to reduce wasted speculation, KV-cache eviction, and recomputation. Built on top of vLLM, Spexis largely improves serving performance across a range of GPU configurations, achieving speedups of up to 34% over a baseline that uses the optimal combination of pipeline and tensor parallelism. Spexis's source code is publicly available at https://github.com/mlsys-seo/spexis.

# Spexis：面向 LLM 推理的推测式前瞻调度——论文总结

## 1. 核心问题与整体含义

- **研究背景**：LLM 参数量与 KV-cache 需求持续增长，单 GPU 难以承载，多 GPU 推理成为常态。主流方案是张量并行（TP）和流水线并行（PP），但二者存在结构性瓶颈：
  - **PP 的内存容量瓶颈**：微批处理要求每个 micro-batch 维护独立 KV-cache，导致单 micro-batch 批量很小，GPU 利用率与吞吐受限。
  - **TP 的通信瓶颈**：每层需多次 all-reduce 同步，GPU 在同步期间空闲；GPU 数量越多、互连越弱，开销越显著。
- **现有推测解码的局限**：传统推测解码主要用于“加速 token 生成”，并未被当作一种分布式执行/调度资源来使用。
- **论文核心含义**：Spexis 将推测解码从“算法加速技术”扩展为“系统级并行机制”，提出**推测并行（Speculative Parallelism, SP）**，让推测执行与正常执行并行，在不增加 KV-cache 内存占用的前提下引入新的并行轴，并结合前瞻调度优化准入与执行决策，缓解多 GPU 推理瓶颈。

## 2. 方法论

### 2.1 核心思想：推测并行（SP）

- 采用**自推测（self-speculation）**：模型前段层作为 draft 层生成候选 token，后段层在正常执行路径中验证这些 token。
- 关键设计：**推测执行与正常执行（即验证）并行运行**，并整体以 PP/TP 方式分布到多 GPU。
- 与 PP 微批处理不同，SP 的推测执行**共享正常执行的 KV-cache**，不额外增加 KV-cache 条目，因此可支持更大有效批量，提升吞吐。
- 当 SP 生效时，可降低所需 TP 度，从而减少 TP 通信开销。

### 2.2 面向 PP/TP/SP 的解析成本模型

- 为选择最优并行组合，论文分别建立 PP、TP、SP 的稳态解码吞吐模型。
- 对 PP：N 个流水级、N 个 micro-batch 时，每级有效批大小为 B/N。
- 对 SP：通过递推关系描述每轮推测接受、拒绝与正常执行的数量，得到稳态有效批大小：
  - 设 Θ 为推测准确率，N 为流水级数，B 为最大批量，则稳态有效批大小约为 \(B/[N-\Theta(N-1)]\)。
- 利用 profiling 获得 PP、TP、SP 的解码延迟函数 \(T_{pp}(\cdot)\)、\(T_{tp}(\cdot)\)、\(T_{sp}(\cdot)\)，结合有效批大小估算吞吐，据此选择 PP、TP、SP 的最优组合。
- 成本模型能捕捉 PP 的 micro-batch 内存开销与 TP 的同步开销；实验表明估计吞吐与实测吞吐高度接近。

### 2.3 接受引导的选择性推测

- 自推测模型的 draft token 置信度可用于估计接受概率。
- Spexis 不显式预测接受概率，而是**按置信度对批次内 draft token 排序，丢弃最低的 α 比例**，只对高置信度 token 进行推测。
- α 通过 profiling 保留 token 的接受率与推测延迟联合确定，实验中使用 0.15–0.3。
- 在成本模型中引入 α 与 Θα，修正稳态批量与有效批量估计，得到选择性推测下的吞吐模型。

### 2.4 剩余长度感知的前瞻调度

- 目标：预测运行中请求的剩余输出长度，估计未来 KV-cache 压力，决定新请求的准入时机，减少 KV-cache 驱逐与重计算。
- **剩余长度预测**：
  - 不预测精确长度，而是做**序数阈值预测**：判断剩余长度是否低于 4、8、16、32、64 token，或超过 64。
  - 使用三层 MLP，以 draft 层隐藏状态为输入，输出 5 个阈值对应的置信度。
  - 为每个阈值选择置信度 cutoff，使“低于阈值”预测具有高精度（约 83%）。
- **前瞻内存估计**（Algorithm 1）：
  - 基于当前长度、剩余长度预测、流水深度、推测准确率，估计未来 1–64 个解码迭代中每个请求的期望生成 token 数、完成概率与释放内存。
  - 计算未来各迭代的 KV-cache 内存使用估计。
- **准入决策**：
  - 若准入新请求会导致运行中请求被驱逐，则延迟其 prefill。
  - 建立解析模型比较两种策略：
    - **aggr**：立即执行新请求，可能引发驱逐与重计算；
    - **delay（本文）**：延迟到最早不触发驱逐的迭代。
  - 定义吞吐增益 \(G\)，权衡“提前准入的吞吐收益”与“驱逐重计算开销”。通常重计算开销是主要因素，但若驱逐很少且延迟过久，延迟也可能不划算，因此需显式建模两者。

### 2.5 实现要点

- 基于 **vLLM v0.8.4** 与 **Ray v2.53.0** 实现，扩展 `GPURunner` 以支持推测并行执行。
- 兼容 Ray 的 compiled DAG 优化，但因 DAG 仅在完整模型执行后暴露阶段输出，使用独立 IPC 获取第一阶段输出用于 drafting。
- 在流水线首尾阶段放置 LM head；为缓解阶段不均衡，将 input embedding 卸载到主机内存并由 CPU 查表，仅增加数百微秒开销。
- Drafting adapter：线性层 + 注意力层 + 预训练 LM head，在 ShareGPT 上以 AdamW 训练 5 epoch。
