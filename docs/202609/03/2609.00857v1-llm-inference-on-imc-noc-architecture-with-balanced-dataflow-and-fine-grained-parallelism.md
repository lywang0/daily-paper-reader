## 摘要
LLM推理已成为一项必不可少的服务，但它对内存带宽、计算密度和通信效率提出了前所未有的需求。虽然IMC是解决内存墙问题的有前景的方案，但LLM的异构数据动态性需要互补资源来处理运行期间生成的中间数据。此外，LLM中大量的参数需要扩展架构，其中片上数据移动通常是主要的性能瓶颈。本文提出了一个硬件-软件协同设计框架，将分布式计算、内存和通信统一为无缝的处理-通信结构。在硬件方面，我们提出了一种名为LEAP的可扩展架构，它集成了IMC PE、NMC PE和INC。这使得每个硬件层能够执行专门的任务：IMC用于静态权重，NMC用于动态数据，INC用于部分结果归约。在软件方面，我们介绍了一种针对LLM服务中关键指标（包括吞吐量和延迟）优化的分区、映射和调度框架。为了解决prefill和decode阶段不同的计算强度，我们提出了一种prefill-decode分离方法，该方法动态重新配置PE组织以最大化资源利用率。与商用GPU平台相比，所提出的架构分别提供了$\geq{}1.52\times$的吞吐量提升和$24.91\times$的能效提升。

## Abstract
LLM inference has become an essential service, yet it imposes unprecedented demands on memory bandwidth, computational density, and communication efficiency. While IMC is a promising solution to the memory wall issue, the heterogeneous data dynamicity of LLM requires complementary resources to handle intermediate data generated during run-time. Furthermore, the massive number of parameters in LLM necessitates scale-up architectures where on-chip data movement is often the primary performance bottleneck. This article presents a hardware-software co-design framework that unifies distributed compute, memory, and communication into a seamless processing-communication fabric. On the hardware side, we propose a scalable architecture, named LEAP, that integrates IMC PE, NMC PE, and INC. This allows each hardware layer to execute specialized tasks: IMC for static weights, NMC for dynamic data, and INC for partial result reduction. On the software side, we introduce a partitioning, mapping, and scheduling framework optimized for key metrics in LLM serving, including throughput and latency. To address the distinct computational intensities of the prefill and decode phases, we present a prefill-decode disaggregation approach that dynamically reconfigures PE organizations to maximize resource utilization. Compared to commercial GPU platforms, the proposed architecture provides a throughput and an energy efficiency improvement of $\geq{}1.52\times$ and $24.91\times$, respectively.

## 🔬 2. 方法论：核心思想与关键技术细节

### 2.1 总体架构——LEAP

论文提出名为**LEAP**的可扩展统一架构，核心设计思想是**让每种硬件资源专门处理一类矩阵操作**：

| 硬件资源 | 专精任务 | 处理的操作类型 |
|---------|---------|--------------|
| **IMC PEs**（存内计算） | 静态权重存储与计算 | DSMMs（动态×静态矩阵乘法） |
| **NMC PEs**（近内存计算，位于router中的scratchpads + 矩阵乘逻辑） | 动态数据存储与计算 | DDMMs（动态×动态矩阵乘法） |
| **INC**（网内计算，IRCU） | 部分结果归约 | AllReduce、ReduceScatter等归约操作 |

### 2.2 两种工作模式（硬件重构层）

| 模式 | 定义 | 核心特点 |
|------|------|---------|
| **LEAP-A（聚合模式）** | prefill和decode阶段共享全部硬件资源 | 所有macro同构：IMC PE + 路由器资源 |
| **LEAP-D（分离模式）** | prefill和decode阶段使用隔离的硬件资源分区 | prefill区域与LEAP-A相同；decode区域**不设IMC PE**，scratchpad容量翻倍以覆盖IMC容量 |

> 核心逻辑：decode阶段是带宽密集型的，不需要存储大量静态权重，因此去掉IMC PE并将资源转化为更大scratchpad，可提升KV缓存容量与并发内存访问带宽。

### 2.3 分区（Partitioning）
- 静态权重矩阵（WQ, WK, WV, WO）沿行/列维度切分，分区大小遵循IMC PE大小
- 动态矩阵（Q, K, V）分区大小由IRCU带宽和scratchpad容量决定
- 分区方案类似张量并行与上下文并行的组合，但分区粒度更细、依赖更频繁的片上通信

### 2.4 映射（Mapping）

**层内映射的启发式约束：**
1. 同一原始矩阵切分的子矩阵映射到连续区域的macros
2. 连续区域尽量为矩形，避免不规则数据流和拥塞
3. 子矩阵在该区域中主要以行主序或列主序展开

**具体映射方案：**
- 整个注意力层映射到 2⌈D/C⌉ × 2⌈D/C⌉ 宏区域（D为嵌入维度，C为crossbar尺寸）
- Q、K、V采用列主序tile间映射，O采用行主序tile间映射
- KV缓存采用**循环存储技术**：token向量循环添加到指定映射区域的scratchpad中，实现内存负载均衡
- 层间采用**蛇形拓扑**（serpentine topology）映射，支持自回归decode阶段最后一个decoder到第一个decoder的token中继

**关键术语定义：**
- RPU：单一channel中一排macros
- RG：存储WQ/WK/WV的列向分区或WO的行向分区的RPU组合

### 2.5 数据流模式（核心贡献之一）

论文将LLM推理中的所有数据移动归纳为三种确定性集体数据流模式：

| 模式 | 源 → 目的 | 计算单元 |
|------|-----------|---------|
| **Broadcast** | IO端口/scratchpads → 输入buffer | 生成树 |
| **Reduce** | 输出buffer → 输入buffer/scratchpads | 反向生成树 |
| **ReduceScatter** | 输出buffer → 输入buffer/scratchpads | 环形或分解生成树 |

另包含**AllGather、E-ReduceScatter、AllReduce**等运用于其他需要跨macro通信的场景。所有数据流在编译阶段就确定，减少运行时控制和仲裁负担。

### 2.6 Prefill与Decode数据流编排

**Prefill阶段数据流（LEAP-A）：**
- 输入tokens Broadcast到所有Q/K/V权重IMC PEs → MAC计算
- IMC输出进行ReduceScatter（每个Q/K head）
- AllGather传递K到Q区域 → IRCU内MAC-2（计算注意力分数）
- 需要时AllReduce聚合注意力分数 → AllGather + MAC-3到V区域
- AllGather + MAC-4（IMC上） + ReduceScatter到O区域
- **关键优化**：当DDMM-MAC或Reduce可与集体通信并发执行时，采用流水线重叠加法/通信

**Decode阶段（LEAP-A和LEAP-D的区别）：**
- 每轮迭代只处理一个token向量，prefill中的ReduceScatter退化为Reduce

**LEAP-D的工作流程创新：**
- KV缓存从prefill区域到decode区域的转移与prefill阶段的AllGather-1和AllGather-2重叠，**关键路径上无额外开销**
- decode区域的Q/K/V会广播到该区域的**所有宏**，实现更大的计算并行度
- 设计差异：GPU场景依赖过度配置的链路来最小化KV传输延迟，而LEAP依赖细粒度计算-通信调度在中等带宽互连上维持低延迟

### 2.7 序列批处理（Batch Size = 2）
- 考虑到本地scratchpad容量和分离架构约束，论文聚焦于**batch size为2**的场景
- 基线调度策略：当前请求的decode阶段转移到decode区域后，立即在prefill区域内启动新请求的prefill
- 并发处理的不同请求可能**竞争IMC中的静态模型权重**，需要细粒度协调：
  - 若请求A的decode需要权重访问而请求B的prefill在注意力操作中 → decode需等待或prefill需在向量环迭代间暂停

| **吞吐量提升** | ≥2.55× | ≥1.52× |
| **能效提升** | ≥71.94× | ≥24.91× |

- **核心优势来源**：全分布式计算-内存组织搭配优化的数据流策略大大减少了数据移动，这与现代GPU共享内存范式形成鲜明对比

### 其他的关键
1. **prefill和decode吞吐量差距**在LEAP-A中达到4-6×，但在LEAP-D中显著缩小——原流水线瓶颈通过向decode区域内全部PE广播当前token向量，得以增强计算并行性和有效内存带宽
2. **模型规模扩展性**：LEAP呈现亚线性吞吐退化。原因是关键路径由最长水平

传输路径（而非垂直方向的深度或总参数量）决定，因此扩展模型规模并不线性延长关键路径。

3. **LEAP-D优势显著**：相比单一模式，LEAP-D在分离的decode区域内给予计算更多的并行度——每个新token向量被广播至所有宏，从而提升了吞吐。这使得LEAP-D成为长输出任务（如生成型对话）的更优选择。

4. **模式切换低开销**：KV缓存传输与prefill的集体通信操作完全重叠，证明了LEAP-D是首屈一指的低开销"训练/推理分离"方案。
5. **Roofline分析**：在给定IRCU并行度范围内，吞吐量随包位宽的增大而上升，但显露出饱和趋势——当网络带宽不再是瓶颈后，继续增加位宽不再带来与面积/功耗开销相称的收益。这使得**在位宽受限的硬件上，通过增加IRCU并行度可以缓解部分带宽瓶颈**。

## 🌟 7. 关键创新贡献总结

### 贡献1：统一异构架构（LEAP-A/LEAP-D）
首个提出 **IMC（存内计算）+ NMC（近内存计算）+ INC（网内计算）** 三位一体协同的体系结构，将静态权重（适合IMC）与动态数据（适合NMC）分开处理；两种模式间的资源切换是基于阶段负载特征（prefill vs decode）自动配置的。

### 贡献2：确定性集体数据流范式（Collective Dataflow）
将LLM推理错综复杂的中间数据流动，抽象为**Broadcast/Reduce/ReduceScatter/AllGather/AllReduce**等一系列固定数据流原语。相比自由路由，这种设计通过编译期预规划，消除了动态仲裁带来的能耗和延迟。

### 贡献3：跨阶段与跨请求调度
在**LEAP-D模式**中实现了KV缓存传输与prefill计算的重叠调度；在**序列批处理**中提出请求间动态资源竞争和切换策略（decode请求可能等待或占用prefill的IMC权重）。这是文献中少有的在IMC架构上同时考虑阶段级和请求级影响的工作。

## ⚠️ 8. 局限性与潜在批评

| 维度 | 批评点 |
|------|--------|
| **实现成熟度** | 基于RRAM的IMC PE的非理想效应（良率、工艺偏差、有限精度、写入耐久度）未被纳入评估，而这是决定IMC方案是否能实际落地的关键因素 |
| **精度验证缺失** | 文中没有提供任何端到端模型精度（perplexity或下游任务分数）是否与FP16/FP32基线一致的评估 |
| **可扩展性边界** | 批处理仅验证batch size=2，未讨论典型数据中心场景下的较大批处理（batch≥8）对IMC权重竞争的处理 |
| **对比公平性** | 与A100/H100的对比直接使用官方TDP规格，而7nm下缩放得到的LEAP数字可能包含乐观工艺外推误差（45nm仿真结果缩放至7nm存在约一个数量级的误差空间） |
| **未覆盖真实数据分布** | 合成工作负载忽视了KV缓存实际的访问局部性、稀疏模式及真实应用中常见的系统级动态性（如请求超时、尾部效应） |
| **缺少对FFN维度更深层的映射讨论** | 文中对注意力层给了较详细的映射图解，但对FFN（两个大矩阵）的映射粒度与传输开销讨论较为概要 |

## 🔮 9. 未来研究方向

1. **混合精度与容错计算**——将RRAM非理想特性（如软错误、写入噪声）纳入数据流调度，探索训练/推理一体化的鲁棒性设计。
2. **更大规模验证**——在8B/13B以上（如70B）模型中验证LEAP的亚线性退化假设；模拟包含数百个宏的LEAP-D配置。
3. **跨请求批处理策略深化**——面向真实云负载的请求调度器设计，融合TTFT/TPOT感知的动态资源分配。
4. **引入非Transformer架构的支持**——观察当前映射方案对Mamba、RWKV等线性注意力模型的适应性。
5. **IMC crossbar内的宏流水线设计**——为避免每次操作将完整向量广播带来的能耗开销，做行缓冲级粒度的流式处理。

**总体一句话定位**：这是一篇**架构探索类的系统级设计论文**，它的主要贡献在于提出了一个可配置的计算-数据流协同框架，而非制造层面的可交付硬件方案。其对研究社区的启发主要在于：（1）将"数据流原生支持"嵌入硬件设计；（2）明确了"内存与通信之间的协同必须比计算资源更早被规划"这一方法论。

**阅读建议**：
- 如果你是**体系结构研究者**——重点关注第2节（映射与数据流），这是本文最难但最有启发的章节。
- 如果你是**系统与编译器研究者**——关注第3-4节中的集体操作抽象和调度策略。
- 如果你是**应用工程师**——结论很清晰：IMC方案在该设计中体现出的能效优势高达24-72×，说明在**静态权重主导的大模型推理**中，存储转向计算是核心趋势。

## 📚 11. 核心术语速查表

|------|------|

| TTFT/TPOT | 首token延迟/每输出token延迟 |
| Scratchpad | 片上便签式内存（可作NMC的近内存存储） |
