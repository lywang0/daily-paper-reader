## 摘要
端侧移动大语言模型（LLM）推理正受到越来越多的关注。然而，移动设备运行在高度动态的多任务环境中，用户经常在应用程序之间切换，导致内存压力，迫使操作系统驱逐LLM内存（模型权重和KV缓存）。当新的推理请求到达时，推理系统必须通过较慢的存储读取来恢复被驱逐的内存，或重新计算整个KV缓存，这严重降低了响应速度。为解决这一问题，我们提出了mzCache，一个面向多任务环境的端侧LLM推理系统，其具有专门的内存管理机制。在不可预测的内存压力下，mzCache弹性地驱逐LLM内存，并利用移动SoC的统一内存，在CPU端并发恢复的同时，实现GPU上的零等待推理。mzCache通过面向恢复的内存管理来实现这一点：LLM内存被划分为细粒度的共享缓冲区，既支持部分驱逐与恢复，又能实现跨处理器并发访问；同时，混合交换与反向驱逐策略确保从任何驱逐状态下都能进行低延迟恢复。mzCache已在llama.cpp上实现并作为Android应用部署，与基于存储的部分卸载相比，首Token时间（Time-to-First-Token）降低了2.1-5.5倍，并在真实多任务场景中展示了其有效性。

## Abstract
On-device mobile Large Language Model (LLM) inference is gaining significant attention. However, mobile devices operate in highly dynamic multitasking environments where users frequently switch between applications. This creates memory pressure, forcing LLM memory (model weights and KV cache) to be evicted by the operating system. When a new inference request arrives, the inference system must restore the evicted memory through slow storage reads or recompute the entire KV cache, severely degrading responsiveness. To address this, we present mzCache, an on-device LLM inference system with specialized memory management for multitasking environments. Under unpredictable memory pressure, mzCache elastically evicts LLM memory and leverages the unified memory of mobile SoCs to enable zero-wait inference on the GPU with concurrent CPU-side restoration. mzCache realizes this through restoration-oriented memory management: LLM memory is partitioned into fine-grained shared buffers to enable partial eviction and restoration with concurrent cross-processor access, while hybrid swap and backward-out eviction policies ensure low-latency restoration from any eviction state. Implemented on llama.cpp and deployed as an Android application, mzCache achieves 2.1-5.5$\times$ reduction in Time-to-First-Token compared to storage-backed partial offload and demonstrates its effectiveness in real multitasking scenarios.

## 1. 核心问题与研究动机

论文针对的场景是：移动端运行 LLM 服务时，用户频繁在多个 App 之间切换，由此产生的外部、不可预测的内存压力，会迫使操作系统驱逐 LLM 推理所用的内存（权重 + KV 缓存），导致后续推理请求的大量恢复延迟。核心观察在于以下两点：

- **移动端 LLM 内存占用巨大**：典型 12 GB RAM 的智能手机上，一个 3B 以下参数模型，权重加 KV 缓存可达 4.7–7.0 GB，占 RAM 近半。
- **OS 通用内存管理机制完全不适合 LLM 工作负载**：
  - 对于可换页内存（pageable），zRAM 的 lz4/zstd 等通用压缩算法对 KV 缓存几乎无效（省空间仅 0.2%–9.3%），存储读取又慢，导致 TTFT 暴涨 18–20 倍（存储换页）或 5–6 倍（zRAM），内存压力也得不到缓解，最终被 Low-Memory Killer（LMK）杀掉进程，不得不冷启动重算上下文。
  - 对于页锁定内存（page-locked），OS 无法回收，只能靠 LMK 杀进程，冷启动代价较大。
- **现有移动 LLM 推理系统没有专门应对机制**：如 MLC-LLM、mllm 等都只专注于运行时推理优化，完全依赖 OS 机制管理内存。
- 加上移动端常见的全局单一缓冲区（monolithic buffer）、缺少服务器端那个“主机内存中的快速恢复中间层”等平台限制，使得恢复路径完全依赖慢速 Flash；而移动平台的统一内存又带来了 CPU 与 GPU 共享同一物理内存、可协同处理的机会。

**论文的意义**：mlCache 是首个将 LLM 内存管理与端侧多任务场景作为一等问题来设计的系统，指出 LLM 推理系统必须自行管理内存，而不是依赖通用 OS 机制，并提出面向恢复的内存管理新思路。

## 2. 方法论：核心思想、关键技术细节与算法流程

### 2.1 总体架构与核心思想

系统采用“空闲阶段 – 推理阶段”两阶段模型：

- 空闲阶段：收到系统释放内存请求时，只驱逐被请求的量，而对任意驱逐量都保持“快速恢复”的元状态。
- 推理阶段：恢复被驱逐的 LLM 内存，并在 GPU 上尽快开始推理。

关键思想是“**面向恢复的驱逐**”：在驱逐过程中每一步，都考虑如何让未来的恢复尽可能快；系统能在任意驱逐状态（逐出多少、哪些）下启动最低延迟的恢复。

### 2.2 关键技术 1：细粒度移动端内存管理

- 将模型的**权重按 Transformer 层**分区，KV 缓存则按每层再划分为**固定大小（256 tokens）的 KV 块**，以支持任意量的部分驱逐。
- 内存以 **共享缓冲区（SVM）** 存在于 SoC 统一内存中，CPU 和 GPU 都可以直接访问；
- 恢复时 GPU 先利用还没被驱逐的浅层立即开始 prefill 计算；同时 CPU 在后台通过直接 I/O 从存储读权重、从内存解压 KV 块，直接写入共享缓冲；
- 不同内存单元的分配与数据读取在多个 CPU 核上并行，最大化恢复吞吐；
- 自研基于 OpenCL 的注意力核，通过 chunk 指针数组以在线 softmax 在非连续共享缓冲上做单遍 prefill 注意力（8-wide FP16）。

采用此方法后，消除了跨 CPU–GPU 的显式数据拷贝，使 CPU 恢复与 GPU 推理可流水线重叠，显著降低 TTFT。

### 2.3 关键技术 2：KV 缓存的混合交换（Hybrid Swap）

- **mzCache 将 KV 压缩（量化等）后置于内存作为“第二条恢复路径”**，与存储读取路径并存。同时把模型权重留在 Flash 存储上（压缩率低、体积大）。
- 为平衡两条路径的恢复耗时，先通过**离线 profiling** 得到每个单位（KV 块解压、KV 块读存储、权重层读存储）的耗时参数：单位时延为 t_KV_d、t_KV_r、t_W_r。
- KV 块大小设置为 256 tokens（512 KB），以保证单次读请求可接近 UFS 全带宽。
- 动态计算阈值 \(T = N_{W}^{total} \cdot \lfloor t_{W\_r} / t_{KV\_d} \rfloor\)（即解压路径在权重读期间能覆盖的 KV 块数量），通过四阶段驱逐维持两条路径的负载平衡：
  1. **KVonly（当 \(N_{KV} > T\)）：** 只把 KV 块按解压和存储两条路径的比例进行驱逐，权重不动。
  2. **KVandW（当 \(N_{KV} \le T\) 但两者仍有剩余）：** 每次丢一个权重层的同时压缩 \(\lfloor t_{W\_r} / t_{KV\_d} \rfloor\) 个 KV 块到内存交换区，二者同时耗尽。
  3. **Wonly：** KV 已全部处理完，还有剩余权重需要丢弃，只丢权重。
  4. **CompKV（内存压力更高时）：** 将内存压缩区里的压缩 KV 块也转移存到存储上，进一步释放内存。
- 任意时刻停止驱逐，两条路径都已被分配了与自身吞吐匹配的恢复任务。

### 2.4 关键技术 3：反向驱逐/正向恢复策略

- 采用 MRU 风格顺序：**驱逐永远从最深的层开始，一路向浅层删除**（backward-out）。
- 恢复则按正向（forward-in）进行，恰好符合推理层顺序：GPU 从 L1 开始做 prefill，同时 CPU 正在恢复后面的层，两类工作像流水线一样叠加，最大化 GPU 利用率。
- 内存中压缩 KV 共享区用**栈结构**维护，按 LIFO 排列并可按需增长/释放内存段，防止碎片化。

## 6. 主要结论与发现

- 对比 Partial Offload **TTFT 降低 2.1–5.5 倍**，且在所有剩余内存水平（0%、25%、50%、75%）上保持优势；
- 对比 OS Paging（完全驱逐点），Galaxy S25+ 上快 2.5–3.0 倍，OnePlus 12 上快 9.2–25.9 倍，原因是 OS Paging 的 KV 压缩占内存且恢复出现级联缺失问题；
- mzCache 从内存提取的 1.37 倍分配加速、2.15 倍重载加速（hybrid swap+零拷贝）、2.33 倍 prefill 加速；全部重叠再带来 1.61 倍累计收益；反向驱逐明显优于正向/随机；
- 混合交换把两条路径的恢复任务负载均衡得很好，并行恢复比顺序恢复显著更快；
- 虽然 mzCache 峰值功率高于基线（19.2W vs 14.6W），由于总时间缩短，总能量消耗仍明显更低；
- 8bit quantization 在中高内存保留率时 TTFT 更低；CacheGen 在低保留率（大量数据从存储恢复）时因压缩率更高而更好。两者 F1 精度差异不大、幂等、误差不累积；
- **真实部署是全文最有力的场景**：OS Paging 在 10 轮里每一轮都被 LMK 杀死；mzCache（25pp 增量式驱逐）10 轮全部存活且无需冷启动，证明了 OS 机制失败时专用 LLM 内存管理的价值。

## 7. 方法或实验上的亮点

- **问题定位独特且现实性强**：直接针对别的移动系统忽略的“推理间隙 / 空闲时内存被外部逐出”场景，而非只针对“模型内存放不下”的纯资源约束场景；
- **“面向恢复的驱逐”系统性设计**：把驱逐过程本身当作后续能快速恢复的服务来设计，在任意中间驱逐状态下都能保持良好恢复性能；
- **充分利用移动 SoC 统一内存**：CPU 与 GPU 并发进行恢复与推理，使用 SVM 零拷贝、OpenCL 非连续注意力核以及 512KB 对齐阈值（适配 UFS 4.0 带宽饱和点）等底层实现细节扎实；
- **轻量动态、便于落地**：只需两次离线吞吐 profiling 即可推导全部参数；模型更换时无需重复 profile 设备；算法组件可插拔替换；
- **无需修改操作系统**，同时支持 App 级（onTrimMemory）与系统级（vmpressure/PSI）压力检测，扩展性好；
- 真实环境的长时间测试和 LMK 对比保留记录具有较强的说服力。

## 8. 局限、风险与不足

- **硬件评估覆盖较少**：只在搭载高通 Adreno 的两台手机上硬件验证，没有覆盖 Mali/Apple/联发科/NPU 或非统一内存体系结构。
- **评价范围偏窄**：只评估了两 个较小（<2B）的 Dense 模型，没有包括 MoE、稀疏注意力等新架构。
- **内置假设对部分新架构不成立**：假设 TTFT 一定会访问所有层与全部 KV 缓存——对于稀疏注意力/MoE 模型，则会浪费恢复带宽。

## 9. 总结与展望

**总体评价**：mlCache 是一篇定位精准、工程实现扎实、实验设计完整的移动端系统论文。它抓住了真实移动场景中一个被长期忽视的核心矛盾——现代 OS 的通用内存管理机制无法理解 LLM 推理的内存语义（权重 + KV 缓存的恢复依赖关系），从而在外部内存压力到来时做出最坏选择（如压缩 KV 却无法有效缩小占用、驱逐后需要从慢速 Flash 全量恢复）。论文提出的“面向恢复的驱逐”范式，将内存管理的评价指标从“释放了多少内存”转变为“任意驱逐状态下恢复成本有多低”，这一视角的转换是其在方法上的关键贡献。

**领域内的主要启发**：

- LLM 推理系统必须自管内存，OS 的通用回收机制（page cache 换页、zRAM 压缩、LMK 杀进程）均不能满足其延迟敏感性与恢复成本约束；
- 移动端统一内存体系结构与 CPU–GPU 共享物理内存的特性，为“边恢复边推理”提供了独特的优化空间，此类零拷贝协同方案在服务器端不常见、但可反向迁移；
- 压缩不是目的，而是恢复路径的带宽调节手段——mlCache 把“KV 压缩”与“存储读取”看作两条可编程调度的并行通道，这一思路对任何分层存储系统中管理大状态服务的恢复问题均有借鉴意义（如边缘推理服务器、统一内存 GPU 上的大模型管理）。

**技术扩散的可能性**：mlCache 的核心组件（反向驱逐、混合交换、阈值动态计算、共享缓冲下的三级重叠）均不依赖高通专有接口，未来可以直接适配其他 SoC 平台（Apple、Mali、联发科）乃至非统一内存的桌面 GPU（需要引入 PCIe 拷贝路径）。

**对未来研究的可能延伸**：

- 扩展至 MoE、稀疏注意力模型，让“恢复哪些层/哪些 KV 块”的策略本身成为可学习的决策问题；
- 结合多进程或多租户 LLM 服务场景，把驱逐策略提升为对多个独立会话的全局内存调度；
- 考虑与 Hypervisor/固件级内存保护协作，在保证恢复能力的同时进一步压缩防 LMK 所需的内存余量；
- 探索使用 MMA 风格 API 在 GPU 上直接访问压缩数据，进一步消除解压瓶颈。

**一句话总结**：mlCache 用一套轻量、无需改 OS、可在任意驱逐粒度下工作的恢复驱动内存管理方案，系统性地证明了“端侧 LLM 推理应该主动管理自己的内存，而非被动承受 OS 的通用回收”，是移动端大模型系统研究方向上的一个重要节点。
