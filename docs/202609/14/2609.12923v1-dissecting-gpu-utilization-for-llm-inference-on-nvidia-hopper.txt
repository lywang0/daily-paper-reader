# Dissecting GPU Utilization for LLM Inference on Nvidia Hopper 

Mohammad Siavashi, Gerald Q. Maguire Jr., Dejan Kostić, and Marco Chiesa 

KTH Royal Institute of Technology, Stockholm, Sweden {siavashi, maguire, dmk, mchiesa}@kth.se 

## Abstract 

A single “SM utilization” percentage can make an LLM inference workload look compute-saturated while hiding how much useful work is being done. The problem is not that the counter is wrong, but that it collapses several different mechanisms into one number. This is most severe during decode, where each request contributes only one new token and dense projection GEMMs become small-row matrix multiplications. On Hopper, the bfloat16 GMMA path executes these operations in fixed 64-row matrix fragments, so small-batch decode can fill only a small fraction of each fragment with real token rows. In this paper, we profile vLLM with FlashAttention-3 and cuBLASLt on an H100 NVL across cold prefill, warm prefill, and decode, sweeping sequence length and batch size. We replace the usual single utilization number with eight counter-validated views derived from raw Nsight Compute reports, each pinned to an NCU counter or ex-plicit formula. Together, these views map utilization gaps to concrete mechanisms—fragment fill, occupancy limits, stall signatures, wave quantization, and kernel selection—across four production models and six per-layer kernel roles. 

Index Terms —LLM inference, GPU workload characteriza-tion, NVIDIA H100, Hopper, Tensor Cores, Nsight Compute, FlashAttention-3, mixture of experts, vLLM, performance profiling. 

## 1. Introduction 

A GPU can look busy for reasons that have little to do with useful LLM work. That distinction now matters in practice: LLM inference consumes enough hyperscale GPU time that a utilization number quickly becomes a capacity-planning, batching, and optimization decision. Yet the question “is the GPU being used?” is often answered with a single percentage: NVIDIA Nsight Compute (NCU)’s 

sm__throughput.avg.pct_of_peak_sustained_elapsed ,conventionally called SM utilization or sm_busy_pct . This counter is useful, but narrower than the name suggests. It is an elapsed-cycle pipeline-throughput proxy, not the 

sm__cycles_active “≥1 warp resident” counter, not an occupancy measurement, and not a direct measure of useful matrix-multiply throughput. The problem is not that the counter is wrong; it is that a single scalar is being asked to explain too many different denominators. This ambiguity is concrete. In Qwen3-14B dense de-code on an H100 at batch size 32, the GEMMs report ≈72% 

sm_busy_pct , reading as near compute-saturation—yet only half of each Hopper m64 matrix fragment holds real token rows, and long_scoreboard memory stalls still dominate the issue budget; the cause is architectural, an m64 frag-ment floor in Hopper’s bfloat16 (BF16) warp-group matrix multiply-accumulate (GMMA) path that no tile retuning can repair (§5.6). The same ambiguity appears the mo-ment the serving regime changes. For the same projection role at the same model, context length S, and batch size B,

sm_busy_pct can be ∼97% in cold prefill, where cuBLASLt ’s autotuner selects a large tile, yet only ∼9% in warm prefill after a cached prefix collapses the row dimension toward decode size (§5.6). Even occupancy can appear to tell two stories at once: the same kernel is only ∼14% occupied against the architectural 64-warp ceiling, but 75–95% occu-pied against its own register/shared-memory resource cap (§2.4). Each reading is internally consistent. The confusion comes from forgetting which denominator each metric uses. This paper makes those denominators explicit. We in-strument vLLM with FlashAttention-3 (FA3), cuBLASLt ,and Hopper’s GMMA path on an H100 NVL with 94 GB third-generation high-bandwidth memory (HBM3) [15]. We study four production models: Meta-Llama-3-8B, Qwen3-14B, Qwen3-32B, and Qwen3-30B-A3B, the last a sparse mixture of experts (MoE) model with top-8 routing over 128 experts. For each model, we sweep three serving regimes— cold prefill, warm prefill, and decode—along with context length S, batch size B, and per-layer kernel role: QKV pro-jection, attention output projection, FFN Gate/Up projection, FFN Down projection, attention, and the MoE expert path where applicable. For every (model, regime, S, B, role) point, we compute eight utilization views directly from raw Nsight Compute report files, pinning each view either to an NCU counter or to an explicit formula. The central result is that decode underutilization is not one bottleneck but several—resource limits, spatial wave quantization, and an instruction-set fragment floor—each with a different fix, and each invisible to the single scalar. Existing inference profiling often reports either end-to-end latency or a single utilization axis, with no methodology to say whether a low number comes from memory stalls, tile shape, CTA wave loss, an occupancy cap, attention-side synchronization, or an instruction-set fragment floor. Our goal is therefore not another aggregate benchmark, but a counter-pinned map from the symptom—a high or low utilization reading—to the mechanism that produced it. ## 2. Background and Motivation 

2.1. The H100 microarchitectural budget 

Our NVIDIA H100 NVL has 132 streaming multiproces-sors (SMs). Each SM contains four sub-partitions (warp schedulers), each with one 4th-generation tensor core (TC) — 528 TCs in total [14]. Peak dense BF16 TC through-put is 835 TFLOP/s ( 1 671 TFLOP/s with 2:4 structural sparsity, which we do not exploit) [15]. The BF16 GMMA instruction ( wgmma.mma_async ) has a fixed 64-row M-axis fragment [14], an instruction-set property we analyze as a small-batch decode ceiling in §5.6. Peak HBM3 bandwidth is 3.9 TB/s [15]. The L2 cache is 60 MB unified across SMs. The per-SM resource budget is 65 536 32-bit registers, 228 KB shared memory (opt-in max), 64 resident warps (architec-tural ceiling), 32 resident thread blocks, and 4 Tensor Cores. Under the roofline model [23], the arithmetic-intensity ridge is I∗ = 835 / 3.9 ≈ 214 FLOP/byte in BF16. Kernels below I∗

are HBM-bandwidth-bound; kernels above I∗ are compute-bound.

The dense BF16 general matrix multiplication (GEMM) kernels are dispatched by cuBLASLt , built on CUTLASS [17], and typically come from the nvjet_hsh_* family on Hopper. 2.3. Three operational regimes 

Three regimes exercise the H100 differently. ❶ Cold prefill :every prompt is processed end-to-end with no prior key– value (KV) cache reuse; dense GEMMs see row dimension 

M ≈ S·B and arithmetic intensity is high. ❷ Warm prefill :only a short suffix is re-evaluated after a cached prefix is reused, collapsing M from ≈ S·B toward ≈ B; representative of multi-turn chat. ❸ Decode : one query token per request per step against a growing KV cache ( M ≈ B); the dominant production regime; HBM-bandwidth-bound. 

How the regimes are realised. vLLM’s prefix cache [8, 26] reuses already-computed KV blocks across requests (or warmup iterations) sharing a prefix; this flag alone con-trols the two prefill regimes. A cold-prefill cell runs with 

enable_prefix_caching=false (0% hit by construction), so dense GEMMs see the full M ≈ S·B row dimension. A warm-prefill cell enables the cache after an identical-prompt warmup; with vLLM’s 16-token cache blocks, the profiled call re-evaluates at most one trailing 16-token block, a deterministic ≥99.2% hit at S=2048 rising to ≥99.9% at S=16384 (decode-sized M). The two prefill regimes there-fore bracket the cache-reuse axis at its endpoints; the near-perfect-hit warm case is the small-payload limit, distinct from a realistic intermediate-hit multi-turn workload (§6). Decode is profiled at max_tokens=2 with the leading prefill iteration discarded post hoc . In every regime, at least three warmup iterations precede the profiled one and CUDA graphs are captured ahead of time. 

2.4. Occupancy has two denominators 

Achieved occupancy can be normalized against two denom-inators that often differ by about 5×; this is one of the most common and consequential confounds in interpreting GPU utilization . ① Architectural limit : 64 warps/SM, a hardware constant independent of the kernel. ② Kernel resource cap (NCU’s “Theoretical Active Warps per SM”): the maximum warps the kernel’s resources permit, defined as the minimum over register file, shared memory (SMEM), max blocks, and named barriers; typically 8–12 for the kernels in our sweep, far below 64. FA3 main is the cleanest illustration: it reaches 7.6 warps/SM, which is 12% of the architectural limit yet 95% of its 8-warp resource cap, i.e. near saturation. Both readings are correct but answer different questions; keeping the normalization explicit resolves much practitioner confusion. 

## 3. Methodology 

3.1. Profiling pipeline 

All measurements use NVIDIA Nsight Compute 2024.3 (ncu ) [16]. We invoke ncu per kernel with the 

MemoryWorkloadAnalysis , LaunchStats , SpeedOfLight ,

WarpStateStats , and Occupancy sections enabled. Per-layer, per-role kernel instances (32, 40, 64, and 48 layers for Llama-3-8B, Qwen3-14B, Qwen3-32B, and Qwen3-30B-A3B respectively) are aggregated using NCU’s per-kernel CSV export. Three metric families (per-stall-reason counters, raw tensor-pipe counters, and the per-call FA3 main-vs.-combine split) are renamed or blended in the upstream CSV, so we re-read the underlying .ncu-rep files into three caches: h100_role_stall_cache.csv (per-(model, role, regime, S, B) stall counters), h100_role_tc_cache.csv 

(tensor-core counters from sm__pipe_tensor_* ), and 

h100_fa_split_cache.csv (FA3 main and combine separated). NCU reports metrics per kernel launch. For utilization metrics we average matched calls across a model’s layers; for time decomposition we sum across roles within a token. Both views are required: a single per-token aggregate can hide kernel-launch overhead. 

3.2. Metrics and their denominators 

Tab. 2 defines each metric via its NCU counter or explicit formula. A recurring confound is that nominally similar “utilization” quantities use different denominators : SM utiliza-tion is elapsed-cycle (not per-active-SM); the two occupancy readings normalize by the 64-warp architectural limit vs. the kernel’s own resource cap; and compute SOL is reported both per active SM and device-wide ( × SMs reached /132 ,the Model FLOPs Utilization (MFU)-like form [2]), the two coinciding only when a launch reaches all 132 SMs.

5.5. Matmul throughput against the whole array 

The per-active-SM and warp-pool metrics quantify how hard the SMs a kernel occupies are working, but not how much of the H100’s aggregate matmul capacity is exer-cised over the kernel’s wall-clock. To capture whole-device matmul throughput, we take NCU’s compute_sol_pct (the 

Compute (SM) Throughput SOL metric on the SMs the ker-nel reaches, §3) and scale it by spatial coverage to obtain 

device-wide compute SOL , a per-kernel analog of model-level MFU: device-wide compute SOL = compute_sol_pct · SMs_reached  

> 132

discount multi-wave tail loss (the wave-efficiency metric of §5.7), so for multi-wave launches it is an upper bound on true elapsed whole-device duty. We also report “effective active SM compute throughput” ( 528 × device-wide compute SOL) as a wall-clock-duty upper bound, not a literal Tensor-Core count. 

The cross-counter triangulation. The device-wide compute SOL is corroborated by two independent NCU counter families read on the same kernel call : the DRAM-throughput SOL (gpu__dram_throughput.avg. pct_of_peak_sustained_elapsed ) and the stall budget (§5.4). On the dense decode GEMM mean the device-wide compute SOL is ∼7.9% while the DRAM SOL is ∼64% (both elapsed-cycle denominator); the ∼8× asymmetry falsifies “the kernel is idle” without invoking stall classifiers. The stall-budget view (§5.4, long_scoreboard 70–84%) is the second corroborating counter family: it is sourced from the per-issue warp-stall counters, independent of 

sm__throughput and of DRAM throughput. 

5.6. The GMMA fragment-fill ceiling on decode matmul 

Independent of stalls and spatial coverage, a kernel-internal ceiling caps useful matmul on small-M shapes. Hopper’s BF16 GMMA instruction issues at a fixed

5.7. Wave-quantization waste 

The fragment floor of §5.6 wastes rows inside each instruc-tion. The launch grid can waste whole SMs in the same way, one level up. A CUDA grid with NCTA thread blocks (CTAs) executes on 132 SMs in ⌈NCTA /132 ⌉ waves of up to 132 blocks per wave. 5.8. Memory hierarchy and L2 working-set fit 

Decode is HBM-bandwidth bound (§5.4), but separating kernels that are limited by L2 capacity from those limited by HBM bandwidth is a finer question. We use the L2 fit ratio ρ = footprint /60 MB, where ρ > 1 indicates that the working set spills L2 across calls. Decode FFN projections ( gate_up , down_proj ) spill L2 by 2–4 × across all dense models, consistent with the low observed L2 hit rates. Decode QKV is dominated by its weight matrix ( ∼48 MB on Llama-3-8B), so fits L2 ( ρ≈0.80 ), whereas the larger Qwen QKV weights spill (1.2–1.7 ×). Across all (kernel, S, B) combinations, 90.0% spill in cold prefill, 92.5% in warm prefill, and 53.8% in decode. The per-call MoE moe row spills less aggressively than dense FFNs at B=1 : top-8 of 128 experts touches roughly 1/16 

the dense-FFN working set, so the per-call footprint is correspondingly smaller. At B>1, up to min( Bk , E) distinct expert weight matrices may be loaded per call, raising the effective MoE weight footprint by up to min( B, 16) ×; thus, the ρ≈1.20 figure is a lower bound at larger batches (see the working-set caveat in §6).

5.11. Kernel-selection stability 

Stable kernel selection is a precondition for hand-tuning and persistent-kernel rewrites. We measure kernel-selection diver-sity as the number of distinct kernel names that cuBLASLt 

selects for each (model, regime, role) across the sweep. In decode, this count is uniformly 1 for dense GEMMs and 2 for FA3; cold-prefill QKV peaks at 7 (Llama-3-8B). Thus, decode underperformance is not caused by unstable kernel selection: cuBLASLt selects kernels stably, and the selected kernels remain inefficient — a favorable setting for persistent-kernel rewrites.

## 6. Discussion 

Implications. The findings translate into levers at three layers. Software and serving : batch to the compute–memory crossover rather than to “more batch” — B∗∈[25, 49] (§5.9) bounds where dense decode leaves the bandwidth-bound regime, a concrete target for batching, speculative decod-ing [10], and PD-disaggregation; and schedule decode and warm prefill separately, since warm prefill is closer to de-code than to cold prefill (§5.6). Decode’s analytical launch overhead reaches ∼30% of the iteration (Tab. 7), so a dispatch-amortizing decode path (graph capture or a per-sistent kernel) helps. 

Libraries and code generation : the largest decode losses are not retiling problems — no cuBLASLt tile yields a 132-multiple grid for decode-QKV (§5.7), warp-pool headroom needs register and SMEM cuts together (§5.3), and the GMMA m64 floor caps every decode cell at ηM=B/64 re-gardless of tile choice (§5.6). It is worth separating two levers that are easily conflated. A persistent decode kernel removes launch overhead and wave-quantization loss, but it leaves ηM unchanged, because it adds no token rows. Con-tinuous batching does not raise ηM either, since it already sets the decode-GEMM row count to M=B (§2.3) and the latency target holds B below the crossover of §5.9. Rows can only come from speculative, tree, or multi-token decoding, which give M=kB and fill the fragment at k=8 , B=8 .

Architecture : decode stresses memory and host dispatch, not the tensor pipe, raising the open question of whether finer-grained power/clock gating of the tensor datapath is warranted; and decoupling the register file from shared memory would let one resource give occupancy headroom instead of both having to move. Finally, operators should report multiple denominators: a kernel can look healthy on SM-time and warp axes while delivering a small fraction of peak matmul throughput. 

Threats to validity. Six caveats qualify our claims. ❶ FA3 row blending : the standard flash_attn row blends FA3 main and combine, so reading it as main alone underes-timates decode FA3 duty (we re-read the two separately from the .ncu-rep files; §3). ❷ Linear B∗ extrapolation is validated and refined by the B=32 arm (§5.10: Qwen3-14B crosses near B∗≈31 , Llama-3-8B approaches, Qwen3-32B crosses at short S but is KV-capped at long S, Qwen3-30B-A3B shifts to a routed-FFN/FA3 co-bottleneck) — a diagnostic, not a predictor. ❸ Single-GPU, TP=1, single H100 SKU : TP alters per-GEMM shape and adds all-reduce, and HBM-bound numbers may shift on other H100 SKUs. 

❹ Launch-overhead constant : the analytical τ =5 μs is host-/driver-dependent and captures raw dispatch only, not runtime-path/replay/scheduling cost. ❺ Working-set model is first-order : no scratch/tile staging; within ∼10–20% of 

dram__bytes on cross-checked kernels. ❻ Warm-prefill cache state : synthetic warmup yields ≥99% prefix-cache hit; realistic multi-turn intermediate hits are uncharacter-ized. 

## 7. Related Work 

GPU characterization and roofline. Prior LLM inference work on A100/H100 [7] measures end-to-end performance. We instead map per-role kernels to NCU counters, validate with calibration, and tie analysis to measurement via a controlled cuBLASLt tile-space enumeration. Hopper micro-benchmarking [13] studies primitives in isolation; we show how an end-to-end serving stack (vLLM/FA3/ cuBLASLt )composes them. Roofline [23–25] is the main analytical precedent; we extend it with wave quantization, kernel-selection stability, and a cuBLASLt algorithm-space enumer-ation. Our counter-level results (the FA3 blending caveat and the register/shared-memory occupancy co-limit) refine the meaning of NCU metrics [16]. FlashDecoding++ [5] also treats the small-M decode GEMM as a first-order problem and builds a flat-GEMM kernel that pads M to 8 instead of 64. The two efforts meet from opposite directions. That work proposes a kernel; we measure what the stock library path actually does and show why the row deficit survives every tile the library can produce (§5.7). Read together, our enumeration explains why a custom kernel is the level at which the problem has to be solved. MoE, profiling, and benchmarks. MoE work is mostly training-focused, covering routing, expert parallelism, load balancing, grouped-GEMM kernels, and distributed-MoE imbalance [3, 4, 6, 9, 11, 20]. Benchmark suites such as MLPerf [21] report end-to-end latency or throughput; we instead report per-role microarchitectural metrics. 

## 8. Conclusion 

SM utilization is a useful number, but it is not a diagnosis. In LLM inference, the same kernel can look busy or idle depending on whether we count elapsed SM activity, tensor-pipe work, launch-grid coverage, occupancy headroom, or useful GMMA fragment fill, and collapsing these views into one scalar hides where performance is actually lost. Decode makes this concrete. Dense decode GEMMs often reach most of the chip, yet at small batch sizes Hopper’s BF16 GMMA 

m64 fragment floor leaves most rows of every instruction empty, so SM-busy stays high while useful matmul does not. This is an instruction-set ceiling, not a tiling choice, and no cuBLASLt retuning can lift it. FA3 decode loses time to a different cause, barrier-style waits rather than memory stalls. Different bottlenecks need different fixes: small-batch decode is improved less by retuning cuBLASLt 

tiles than by raising the effective row dimension M, through cross-request token packing or persistent decode kernels. More broadly, LLM inference studies should report counter-pinned, per-role metrics rather than a single device-wide utilization percentage.
