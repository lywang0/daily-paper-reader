## 摘要
混合专家（MoE）模型扩展了智能手机上语言模型的容量，但专家卸载仍受限于有限的DRAM容量和高昂的数据移动开销。顺序的token路由将专家执行与碎片化的闪存读取及多阶段NPU准备耦合在一起，使稀疏计算因权重传输而停滞。每次传输仅服务少量token，随后执行便继续推进。我们利用投机解码的多token验证窗口，将专家移动与单token执行解耦，从而实现权重复用、连续闪存读取以及加载-计算重叠。我们提出BigMoMo，一个移动端MoE运行时，它在整个内存层次中利用这一窗口。它基于接受率、路由影响和移动成本来剪枝投机分支和专家激活；根据运行时共同加载模式重新组织闪存上的专家；并将就绪的专家分批，以将NPU计算与待处理传输重叠。在两个移动平台的四个MoE模型和五个基准上，BigMoMo相比按需自回归卸载实现了平均4.83倍的解码加速，相比最佳投机MoE基线实现了1.82倍加速，支持高达300亿参数的MoE模型。

## Abstract
Mixture-of-Experts (MoE) models expand language model capacity on smartphones, but expert offloading remains constrained by limited DRAM capacity and costly data movement. Sequential token routing couples expert execution to fragmented flash reads and multistage NPU preparation, leaving sparse computation stalled on weight transfers. Each transfer serves few tokens before execution moves on. We exploit the multi-token verification window of speculative decoding to decouple expert movement from single-token execution, enabling weight reuse, contiguous flash reads, and load-compute overlap. We present \textsc{BigMoMo}, a mobile MoE runtime that exploits this window across the memory hierarchy. It prunes speculative branches and expert activations using acceptance rates, routing impact, and movement cost; reorganizes on-flash experts according to runtime co-loading patterns; and batches ready experts to overlap NPU computation with pending transfers. Across four MoE models and five benchmarks on two mobile platforms, \textsc{BigMoMo} achieves mean decoding speedups of $4.83\times$ over on-demand autoregressive offloading and $1.82\times$ over the best speculative MoE baseline, supporting MoE models up to 30B parameter.

## 1. 核心问题与研究动机

- **背景**：个人智能（personal intelligence）需求增长，推动在智能手机上直接运行大语言模型；MoE 通过稀疏激活在有限计算量下扩展模型容量，但其**总参数量往往超出移动端 DRAM 容量**，必须依赖专家卸载（expert offloading）。
- **现有方案的局限**：已有 MoE 卸载系统多面向 CPU–GPU 平台，主机–设备带宽高、数据通路简单（两层），专家搬运延迟小且易于与计算重叠。而移动端面临三重结构性困难：
  1. **专家搬运带宽受限**：DRAM 容量小、带宽低，更多专家只能留在外部 Flash，动态路由导致频繁且漫长的搬运。
  2. **Flash 访问开销高**：移动端从 UFS Flash 而非主机 DRAM 取权重，性能对访问粒度与连续性高度敏感；稀疏动态的专家请求退化为碎片化读，带宽利用率低（图 4b 显示即便有 co-activation 布局，与 UFS 理想带宽仍有明显差距）。
  3. **多阶段执行路径**：移动 NPU（Qualcomm Hexagon）推理需要先映射到受限的 NPU buffer，再搬入 VTCM 做布局转换/反量化，最后才进 HMX 计算，专家因驻留状态不同而"就绪时刻"不一，产生流水线气泡。
- **核心矛盾**：MoE 的"参数解耦"（每 token 只激活少数专家）并没有解决"数据搬运与单 token 执行顺序耦合"的问题——一次完整专家搬运只服务极少量 token，稀疏计算被权重传输拖住。
- **论文主张**：应从"模型级参数解耦"转向"**系统级数据移动解耦**"，把执行粒度从单 token 扩展到多 token，而**投机解码的多 token 验证窗口**天然提供了这一扩大的执行窗口。

## 2. 方法论

### 2.1 核心思想

- 利用投机解码的**多 token 验证窗口**（token tree）将专家搬运与单 token 执行解耦，带来三个机会：
  - **可复用的专家搬运**：同一验证轮内多个草稿 token 命中同一专家，可共享一次加载；
  - **对 Flash 友好的访问**：一轮内暴露更多专家请求，可将碎片读聚合为连续读；
  - **跨阶段搬运–计算重叠**：更多专家计算量可用于掩盖其他专家的剩余搬运延迟（理论上可隐藏 `min(R_j, T_HMX^m)`）。
- 系统命名为 **BigMoMo**（Big Mobile MoE），在整条内存层级（Flash → DRAM → NPU Buffer → VTCM → HMX）上协调专家搬运与执行。

### 2.2 关键技术一：面向复用的专家搬运准入（§4.2）

- **动机**（图 7）：被拒绝的草稿节点占目标验证计算时间的 82.1%、专家搬运时间的 81.8%；不同专家请求的路由重要性差异明显。
- **接受率感知的节点剪枝**：
  - 每个树深度 h 用离线标定得到的接受概率 p̂_h，结合草稿模型 token 概率 q_u，定义节点价值：
    `V_d = p̂_{h(d)} · Π_{u∈path(d)} q_u`
  - 按 V_d 降序保留累计价值占比达到 ρ 的最小节点集合（实验取 ρ = 0.9）。
- **层级感知的专家剪枝**：
  - 路由影响定义：`I_e = Σ_{d∈D_e} V_d · min_{j∈T_d\{e}} |s_{d,e} − s_{d,j}|`，即被低价值节点选中、或存在路由分数相近替代者的专家影响更低。
  - 离线按专家尺寸与层级阶段剖析搬运延迟作为搬运成本 C_e。
  - 迭代剪枝优先级 `P_e = ΔI_e / C_e`，在累计路由影响预算 τ（实验取 0.4）下剪枝；被剪专家的路由权重**重分配给路由分数最接近的保留专家**，每个节点至少保留一个专家。

### 2.3 关键技术二：运行时自适应的 Flash 上专家组织（§4.3）

- **动机**（图 8）：共加载关系在邻近验证轮次内保持稳定；近期 Flash 读时间下降更大的重定位往往持续有益。
- **超图建模**：专家为顶点，一轮内被共同加载的专家集合为超边 M^k_l；最近 K 轮（实验 K = 3）的重叠超边刻画复现的共加载模式。
- **锚区选择**：对每个超边，在 Flash 中寻找能容纳 |M^k_l| 个专家的连续区域，选与其驻留集合重叠最大的作为锚区 A^k_l，最小化需搬入的外部专家数。
- **读时间估计**：`T^k_l = T^Flash_S(A^k_l) + Σ_{e∈M^k_l \ A^k_l} T^Flash_S(e)`（锚区连续读 + 区外碎片读）。
- **重定位收益**：对候选交换 (e_i, e_j) 重算最近 K 轮所有超边的估计读时间，累计降幅 `B_l(e_i,e_j) = Σ_r (T^r_l − T̃^r_l)`；选取收益最大的可行交换增量执行。
- **工程细节**：交换在两位专家均已载入共享 DRAM 后才写入，避免为搬移额外读 Flash；当有延迟敏感的 Flash–DRAM 加载请求到达时**暂停重定位写入**，优先保证读。

### 2.4 关键技术三：跨层级搬运调度（§4.4）

- **VTCM 双缓冲**：VTCM 划分为两个交替权重缓冲 + 128 KiB 激活/输出区；就绪专家按缓冲容量组批，超限专家沿输出维 N 以 32 为倍数分块；权重打包成连续 128 B 向量跨 VTCM bank 分布，供 HMX 并行访问；DMA 搬运量化权重后由 HVX 反量化。
- **就绪时间估计**：DRAM 驻留专家 e 的估计就绪时间为剩余 NPU buffer 映射延迟 τ^map；Flash 驻留专家还需加上 Flash–DRAM 加载延迟。下一个专家就绪的估计间隔 `τ^next_t = min_{e∈E^pending_t} τ^map_{e,t}`。
- **未覆盖搬运时间**：`R_t = max(0, τ^next_t − W_t)`，W_t 为残余 HMX 计算窗口。
- **组选择策略**（式 6）：
  - 初始阶段为已在 NPU mapped buffer 中的 8 个最常激活专家预构造计算组，每组有 T^VTCM_b 与 T^HMX_b；
  - 只在 T^VTCM_b ≤ W_t（搬运可被当前窗口掩盖）的候选中选择；
  - 若存在 T^HMX_b ≥ R_t 的候选，选 HMX 执行时间**最短**者（避免过度延迟）；
  - 否则选 HMX 执行时间**最长**者以尽量覆盖估计间隔；
  - 新专家就绪后动态加入后续组构造，循环调度。

### 2.5 系统总览（图 6）

一个解码轮：构造草稿树 → 复用导向的搬运准入（节点剪枝 + 专家剪枝）→ 驻留查询确定需从 Flash 取回的专家 → 运行时自适应 Flash 组织（连续 Flash 访问 + 地址重映射）→ 跨层级调度（计算组、双缓冲、HMX 执行）→ 输出聚合与接受反馈。

- **性能**：BigMoMo 在所有模型–benchmark 组合、两个平台上均取得最低 TPOT；平均相对 OnDemand **4.83×**、相对 SD-OnDemand **3.00×**、相对最佳基线 **1.76×** 加速（分模型：Qwen3 1.73×、LFM2 1.47×、Gemma 1.80×、ERNIE 2.03×）。
- **尾延迟

- **尾延迟与端到端**：尾延迟（P90/P99）同样改善，端到端延迟随输出长度增长而持续领先，说明收益并非来自单次请求的偶然波动，而是稳定降低每 token 开销。
- **性能来源拆解**：TPOT 分解显示，BigMoMo 大幅压缩了"暴露的搬运停顿"（exposed stall）与专家计算时间，草稿生成开销相对稳定；验证窗口越大，可复用专家与可聚合的 Flash 读越多，搬运停顿被重叠得越充分。
- **三机制各自有效且互补**：增量消融（表 3）显示，仅加入"复用导向搬运准入"即带来明显 TPOT 下降，叠加"Flash 上专家组织"后进一步降低 Flash 读开销，再加入"跨层级搬运调度"后 HTP 利用率跃升、搬运停顿基本被掩盖；三者组合的效果优于任意单独机制之和的简单叠加，说明它们作用于不同瓶颈（请求数、访问连续性、流水线气泡）。
- **搬运准入的取舍**：节点剪枝 + 专家剪枝显著减少验证节点数与专家请求数（表 4），同时 TPOT 改善；生成质量在 GSM8K/HumanEval/MMLU-Pro 上仅下降 0.05–0.18 个百分点（表 5），即在可接受的质量损失下换取效率，且质量损失随剪枝强度增大而单调上升，符合预期。
- **Flash 组织的收益**：有效 Flash 读带宽（图 15）明显高于默认布局与离线共激活布局，接近 Oracle 上界；每输出 token 的 Flash 读次数（表 6）下降，验证了"连续锚区读 + 碎片读减少"的机制；且运行时自适应优于静态离线共激活，说明共加载模式虽在邻近轮次稳定，但仍有可利用的时序变化。
- **调度的收益**：跨层级搬运调度将 HTP 利用率从 18.96–45.03% 提升至 83.78–98.30%（表 7），说明移动 NPU 在朴素卸载下大量时间处于等待权重搬运的空转状态，而就绪时间估计 + 组选择策略能有效填补这些空档。
- **敏感性与稳健性**：不同投机配置（表 8）下，收益随验证窗口增大而提升但存在边际递减，说明过大的树会引入更多无效节点与搬运；不同专家驻留数（图 16）下 BigMoMo 均优于基线，且驻留数越少（DRAM 越紧张）相对优势越大，符合"减少 Flash 搬运"的设计意图；跨平台（表 9）结果一致，说明方法不依赖某一代骁龙的特定参数。

## 7. 局限性、适用条件与未来方向

- **依赖投机解码**：BigMoMo 的收益根基是"多 token 验证窗口"，因此要求目标模型配有可用的草稿模型（同族或独立小模型），并需要接受投机解码带来的额外草稿生成开销；在不适合投机的场景（如极短输出、严格逐 token 流式要求）收益会受限。
- **依赖离线标定**：逐深度接受概率 p̂_h、专家搬运延迟 C_e、Flash 读时间模型等均需离线剖析，且针对具体硬件与模型组合；换模型或换平台需要重新标定，增加了部署成本。
- **剪枝带来的质量–效率权衡**：虽然报告的质量损失较小，但剪枝本质上是启发式近似，在分布外任务或对准确性极敏感的负载上，0.05–0.18 个百分点的下降可能不可忽略；ρ 与 τ 等超参需要按场景调整。
- **基线的复现公平性**：如前所述，对比方法为作者自行复现并运行在自研后端上，可能与原实现存在差距；主实验未在基线各自最优投机配置下比较，加速比可能被高估或低估。
- **硬件与软件绑定**：实现基于 llama.cpp + Hexagon 后端，VTCM 双缓冲、128 B 权重打包、HVX/HMX 分工等均针对骁龙 NPU 特性；迁移到其他移动 NPU（如苹果 ANE、联发科 APU）需要重新设计数据通路与调度。
- **未覆盖的方向**：论文未涉及训练/微调、未讨论多请求并发与批处理场景、未评估长期运行下的 Flash 磨损与热/功耗影响；这些是移动端部署的实际关切，可作为后续工作。

## 8. 总体评价

- **问题定位准确**：论文抓住了移动端 MoE 推理的本质矛盾——不是"参数太多"，而是"搬运与单 token 执行耦合"，并将解决思路从模型级参数解耦提升到系统级数据移动解耦，视角清晰且有解释力。
- **方法设计成体系**：三个机制分别针对"请求数量"（搬运准入）、"访问形态"（Flash 组织）、"流水线气泡"（跨层级调度），彼此互补而非堆砌，且都紧扣移动端 Flash 与 NPU 的物理特性。
- **工程落地性强**：在真实手机、真实 UFS、真实 Hexagon NPU 上实现并评测，报告了尾延迟、端到端延迟、HTP 利用率等系统级指标，而非仅停留在模拟或理想带宽假设。
- **实验较充分但公平性有隐忧**：模型、任务、平台覆盖广，消融完整，并披露了质量损失；但基线为自行复现、统一运行在自研后端，比较结论需谨慎解读。
- **可复现性**：论文描述了关键超参（ρ=0.9、τ=0.4、K=3、D=2、B=2、常驻专家数等）与实现规模（约 5,000 行），但未提供代码/权重/标定脚本，完整复现仍有难度。
- **整体结论**：BigMoMo 表明，在移动端 MoE 推理中，"让搬运服务更多 token"比"让每个 token 更快"更关键；投机解码的验证窗口不仅是加速解码的手段，也可被重新诠释为**扩大专家复用与聚合 I/O 的系统级执行窗口**，这一思路对移动端大模型部署具有参考价值。
