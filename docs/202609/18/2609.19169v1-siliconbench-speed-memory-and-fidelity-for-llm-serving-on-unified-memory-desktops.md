## 摘要
并发本地 LLM 服务在统一内存桌面上必须保留内存余量和输出保真度，而仅看速度的排名会忽略这一点。我们提出 SiliconBench，它从三个视角评估九种 Apple Silicon 服务引擎：速度、内存与保真度。我们在 Qwen3、Qwen3.5 和 Gemma 4 上评估聊天与智能体服务。我们使用一个分类任务来检查相对于 NVIDIA 参考实现的质量退化。DGX Spark 提供了一个补充性的服务性能参考。三项期望指导解读：服务架构就绪度、内存纪律和多节点扩展。在 Qwen3-0.6B 上，仅 vllm-metal 就在两种工作负载下，从并发度 1 到 16 将吞吐量提升了一倍以上。CUDA vLLM 和 SGLang 在相同提示词上展现出更强的并发扩展能力。显式内存预算并不保证内存余量：两个技术栈完成了所有请求，但内存使用接近物理容量，且吞吐量下降。较新的模型架构获得的引擎支持更窄。它们被评估的实现与保真度参考相匹配。只有三个技术栈满足完成度、保真度和模型覆盖率的门槛。在更大的稠密模型和 MoE 模型上的比较，强化了将提示词处理与持续生成一起调度的重要性：vllm-metal 的打包式预填充-解码路径在并发负载下保持比 omlx 更低的首 token 延迟。在测试的双机配置中，基于 Thunderbolt RDMA 的张量并行能够扩展，而基于 TCP 的流水线并行则出现性能退化。我们发布基准测试代码、每次运行的结果和维护日志，并辅以一种将有界智能体修复与人工审查相结合的工作流。

## Abstract
Concurrent local LLM serving on unified-memory desktops must preserve memory headroom and output fidelity, which speed-only rankings overlook. We introduce SiliconBench, which evaluates nine Apple Silicon serving engines through three lenses: speed, memory, and fidelity. We evaluate chat and agent serving on Qwen3, Qwen3.5, and Gemma 4. We use a classification task to check for quality regressions against an NVIDIA reference. DGX Spark provides a complementary serving-performance reference. Three desiderata guide interpretation: serving architecture readiness, memory discipline, and multi-node scaling. On Qwen3-0.6B, vllm-metal alone more than doubles throughput on both workloads from concurrency 1 to 16. CUDA vLLM and SGLang show stronger concurrency scaling on the same prompts. Explicit memory budgets do not guarantee memory headroom: two stacks complete every request while memory use approaches physical capacity and throughput declines. The newer model architectures have narrower engine support. Their evaluated implementations match the fidelity reference. Only three stacks satisfy the completion, fidelity, and model-coverage gates. Comparisons on larger dense and MoE models reinforce the importance of scheduling prompt processing alongside ongoing generation: vllm-metal's packed prefill-decode path maintains lower first-token latency than omlx under concurrent load. In the tested two-machine configurations, tensor parallelism over Thunderbolt RDMA scales while pipeline parallelism over TCP regresses. We release benchmark code, per-run results, and maintenance journals, supported by a workflow combining bounded agent fixes with human review.

# SiliconBench 论文中文结构化总结

## 1. 核心问题与整体含义

- **研究背景**：统一内存桌面（Apple Silicon、NVIDIA DGX Spark）正成为本地 LLM 服务的平台，其 LPDDR 内存由 CPU 与 GPU 共享，与数据中心 HBM 加速器不同。Apple Silicon 生态规模庞大（Ollama/llama.cpp/LM Studio 年装机数十万、mlx_lm 月下载 145 万次、mlx-community 社区模型 4,710 个）。
- **核心问题**：现有评测主要按吞吐量排序，忽略了两个关键维度——
  - **内存余量**：模型权重与推理缓存与浏览器、IDE、OS 共享 RAM，吞吐高但占用接近物理上限时，会拖慢前台应用甚至导致请求失败。
  - **输出保真度**：即使请求完成，引擎产出的任务级得分也可能低于参考实现。
- **并发维度**：单个编码 Agent 可同时发出 4–16 个请求，单请求速度无法反映并发负载下的表现；缺乏连续批处理或内存纪律的栈会变慢或崩溃。
- **整体含义**：论文提出 SiliconBench，首次在**速度、内存、保真度**三个维度上联合评测九种 Apple Silicon 服务引擎，并给出三项指导性期望（Desiderata）：
  - **D1 服务架构就绪度**：支持新模型架构并高效处理并发请求。
  - **D2 内存纪律**：高效使用共享内存，同时为 macOS 与前台应用保留余量。
  - **D3 多节点扩展**：跨机器分布式推理，服务超出单机内存容量的模型。

## 2. 方法论

### 2.1 核心思想
- 以"速度 + 内存 + 保真度"三视角联合审计，而非单一吞吐排名。
- 用三项 Desiderata 解释各引擎的优势与剩余差距。
- 采用**维护智能体 + 人工审查**的工作流保持基准时效性（每两周一次验证快照）。

### 2.2 关键技术细节

- **服务引擎分类维度（Table 1）**：对九种栈按四项实现选择刻画：
  - **Prompt batching**：packed tokens（打包、无 padding）vs. padded batch vs. 单提示词。
  - **KV-cache layout**：paged（分页）/ contiguous per batch / preallocated KV cells。
  - **Prefill / decode**：same pass（混合步）vs. separate passes。
  - **Memory policy**：explicit cap（显式上限）/ advisory hint（建议性提示）/ unbounded（无界）。
- **批处理分析**：
  - 打包查询处理 $\sum_b q_b$ 个真实 token 行；填充批处理处理 $B \cdot T_{\max}$ 行，其中 $T_{\max} = \max_b q_b$，造成 padding 浪费。
  - 分页 KV 允许缓存增长而无需重塑连续存储；调度步组成决定 prefill 与 decode 是否共享前向传播。
- **内存浪费量化**：以 mlx_lm 为例，三提示词（30K/5K/10K）并发时查询张量形状为 [3, 30000]、KV 为 [3, heads, 30000, head_dim]，实际 token 35,010 却跨越 90,000 位置，浪费 61% 查询计算与 KV 内存 I/O。
- **部署悬崖（deployment cliff）**：32 GB M1 Pro 上浪费内存触发 macOS 页压缩，每步 decode 需解压/再压缩，wall time 增长 2.5×；64 GB M1 Max 上无惩罚。同一代码在较小机器上静默退化，无错误信号。
- **多节点并行策略**：张量并行（TP）分片权重；流水线并行（PP）按设备分配层范围。连接带宽远低于 NVLink，传输选择至关重要。
- **维护工作流**：Claude Code 智能体更新框架、运行基准、提出修复；写白名单仅覆盖框架适配器与模型配置，工作负载、评分与聚合由人工控制；官方结果重跑前须经人工审查。

## 6. 主要结论与发现

### 6.1 速度与并发扩展

- **Qwen3-0.6B**：vllm-metal 是唯一在 chat 与 agent 两种负载上从 c=1 到 c=16 吞吐均翻倍以上的栈（chat 3.65×，agent 2.71×）。相同批处理能力的 hf_transformers 仅 1.23×，说明实现质量而非声明特性决定扩展性。
- **TTFT**：仅 vllm-metal 在 c=16 同时满足亚四分之一秒中位 TTFT（219 ms）与 agent 吞吐增长；sglang 虽快速接纳请求（655 ms）但 agent 吞吐从 80.6 降至 45.3 tok/s。
- **完成率**：九栈中六个在两个切分的每个 level 均完成 ≥90/100；mistral.rs 在 c=8 退化、c=16 崩溃；mlx_lm agent c=16 崩溃至 2/100；hf_transformers agent 超过 1 h 上限。

### 6.2 内存纪律

- **显式预算不等于内存余量**：mistral.rs、vllm-mlx、sglang 声明显式预算，却接近物理 RAM 且吞吐下降。mistral.rs 在 agent c=8 达 59.3 GB 仅完成 13/100；sglang 与 vllm-mlx 虽完成全部 600 请求但内存占用高。
- **平坦内存不足以保证余量**：ollama 从 c=1 起就占用 Metal 建议提示的 94–97%。
- **无界增长**：mlx_lm chat 内存接近三倍，仅换来 7% 吞吐提升。
- **vllm-metal 与 llama.cpp** 内存几乎平坦，vllm-metal agent 峰值 34.7–34.9 GB，且吞吐随负载增长。

### 6.3 保真度

- Qwen3-0.6B 上 8 栈中 6 栈在 0-shot 与 5-shot 均落在参考 ±1.5pp 带内；两个新模型上 5 栈均在 ±1.4pp 内。
- **ollama** 0-shot 在带内，但 5-shot 几乎无增益，落后约 30pp（聊天模板对多示例处理疑似为原因）；工具调用提示下流式输出约 254 个空内容 token。
- **vllm-mlx** 在 Qwen3-0.6B 上比零样本参考低 5.0pp（尽管零请求/解析错误），疑似实现 bug；在两个新模型上落在参考带内。

### 6.4 多节点

- **TP over RDMA 可扩展**：mlx_lm 与 EXO 双节点 decode 提速 1.28–1.37×，prefill 短上下文约 2×、4K 上下文 1.7–1.8×。EXO 另有 35% 单机领先。
- **PP over TCP 回退**：llama.cpp 顺序流水线在双节点下降 16–20%。

### 6.5 审计门槛与最终结论

- **仅三个栈通过全部门槛**（完成度、保真度、三模型覆盖）：**llama.cpp、vllm-metal、omlx**（Table 5）。
- 速度被报告但不作为门槛（慢栈仍可用，缺失栈不可用）。
- 核心结论：**声明特性不保证并发扩展，成功请求不保证内存余量或参考保真度；多节点扩展取决于并行策略与传输的组合。**

## 7. 优点

- **三视角联合评测**：首次在统一内存桌面上同时量化速度、内存、保真度，揭示"仅速度排名"掩盖的部署风险（如部署悬崖、显式预算失效）。
- **Desiderata 框架**：D1/D2/D3 提供了清晰的解释性结构，将测量结果与工程判断连接。
- **受控对比设计**：同一 M5 Pro、固定提示集/种子/数据集版本，跨快照可比；桥接对（DGX Spark）隔离 CUDA 与 Metal 后端的差异。
- **具体机制洞察**：padding 浪费 61% 计算与 KV I/O、页压缩导致 2.5× 减速、TTFT 与吞吐的联合分析，均具工程指导价值。
- **维护工作流创新**：有界智能体修复 + 人工审查 + 允许清单，配合每两周快照，回应基准老化问题；两起真实事故（共享依赖破坏、ChatML 模板导入错误）展示了流程价值。
- **开放与可复现**：发布代码、逐次运行结果、维护日志、文件哈希与快照 commit。
- **诚实的局限声明**：明确列出无方差估计、单一保真度任务、部分栈覆盖等。

## 8. 不足与局限

- **硬件覆盖窄**：主审计仅一台 Apple M5 Pro；DGX Spark 仅覆盖三引擎且仅测吞吐与延迟，无维护周期；未覆盖 AMD 统一内存 APU。代际特定 kernel 支持可能改变排名。
- **模型覆盖不完整**：0.6B 为九栈通用模型；新

- **模型覆盖不完整**：0.6B 为九栈通用模型；新架构模型（Qwen3.5-0.8B、Gemma-4-E4B-it）仅覆盖 5 个栈，更大模型（Qwen3.8-27B、Qwen3.6-35B-A3B）仅覆盖 3–4 个引擎，多节点仅 3 个系统。因此"某栈在 0.6B 上表现良好"不能直接外推到 27B/35B 或 MoE 场景，反之亦然。
- **保真度任务单一**：仅用 GMRID 供应链事件分类（8 类、0-shot/5-shot）衡量输出保真度。该任务偏短输出、结构化标签，无法覆盖长文生成、代码、多轮对话、工具调用参数正确性等对 Agent 服务更关键的保真度维度；±1.5pp 带内的结论可能对任务类型敏感。
- **无正式方差估计**：论文明确承认没有设计重复实验（no designed repeat pass），近似并列按并列处理。虽然三次附带 telemetry 重复中 9 个 level 有 8 个变化 ≤5.6%，但 omlx agent c=16 出现 20% 波动，说明高并发下 run-to-run 方差可能不可忽略，排名在噪声范围内的差异不应被过度解读。
- **多节点规模有限**：仅验证 2 节点，未测试 3 节点及以上；未测试必须跨机才能容纳（即单机物理内存不足）的模型，因此"多节点解决内存容量瓶颈"这一动机尚未被端到端验证。Thunderbolt 5 + RDMA 的拓扑也非典型集群互联，PP over TCP 的结论可能随传输层实现变化。
- **并发上限与负载形态**：并发扫描止于 c=16，未探索 32/64 或真实 Agent 突发式、非均匀请求到达；闭环固定并发（closed-loop）与真实生产中的开放到达过程存在差异，排队延迟与内存峰值的结论可能偏乐观。
- **内存测量方法**：依赖逐秒 metalstat 采样，可能错过亚秒级峰值；Metal 提示值（51.84 GB）是系统建议而非硬上限，不同 macOS 版本与后台负载会影响余量判定，跨机器可比性受限。
- **维护流程证据有限**：维护工作流仅在 M2 Max 上记录 5 次运行、2 起事故，样本量小；智能体自动修复 + 人工审查的长期稳定性、修复正确率与回归风险尚未被充分评估。
- **未覆盖维度**：未评测能耗/热约束、电池续航、多用户隔离与安全、模型加载时间、冷启动、量化精度对保真度的交互影响，也未涉及 AMD APU 等竞争性统一内存平台。

## 9. 可复现性与开放材料

- **开放内容**：发布评测代码、逐次运行结果、维护日志、文件哈希与快照 commit，支持外部复核与跨快照比对。
- **固定要素**：提示集、采样种子、数据集版本在快照间固定，使性能与保真度变化可归因于框架本身而非数据漂移。
- **受控条件**：同一 M5 Pro 硬件、temperature=0、非思考生成、统一 HTTP 超时与 wall-clock 上限，减少配置差异带来的混淆。
- **桥接设计**：DGX Spark 上的 llama.cpp/vLLM/SGLang 与 Apple 侧同族引擎构成"桥接对"，有助于把后端差异（CUDA vs. Metal）与实现差异分离。
- **维护透明**：每两周验证快照、白名单仅覆盖框架适配器与模型配置、官方结果重跑前人工审查，兼顾时效性与评分完整性。

## 10. 对领域的影响与未来方向

- **评测范式**：把"速度 + 内存 + 保真度"三视角联合审计引入本地 LLM 服务评测，挑战了以 tok/s 单指标排序的惯例；D1/D2/D3 可作为后续基准设计的模板。
- **工程启示**：
  - 批处理声明不等于并发扩展，实现质量（打包、分页 KV、调度）决定实际表现。
  - 显式内存预算不等于安全余量，需要测量实际占用与前台应用体验。
  - 多节点收益取决于并行策略与传输组合，TP over RDMA 优于 PP over TCP。
- **潜在后续工作**：扩展到更多 Apple 代际与 AMD 统一内存平台；加入 3 节点以上与真正跨机模型；增加长文/代码/工具调用保真度任务；引入设计重复实验与置信区间；将能耗、冷启动、多用户隔离纳入维度；持续用维护智能体跟踪框架演进。

## 11. 总体评价

- **贡献定位**：SiliconBench 是首个面向统一内存桌面（Apple Silicon）在速度、内存、保真度三维度联合评测九种服务引擎的系统性工作，问题选择紧扣本地 LLM 服务真实痛点（共享 RAM、并发 Agent、前台体验）。
- **方法强度**：受控对比、固定提示集/种子、桥接对、维护工作流与开放材料构成较完整的方法论闭环；padding 浪费量化、部署悬崖、TTFT-吞吐联合分析等机制洞察具有直接工程价值。
- **结论稳健性**：核心定性结论（声明特性不保证扩展、成功请求不保证余量与保真度、多节点取决于并行+传输）由多组实验交叉支撑，较为可信；但具体排名受单机、单保真度任务、无方差估计等限制，应视为方向性而非终局性。
- **实践建议**：在 Apple Silicon 上部署本地 LLM 服务时，优先考虑通过全部门槛的 llama.cpp、vllm-metal、omlx；对高并发 Agent 负载重点关注内存纪律与完成率，而非仅看单请求吞吐；多节点扩展优先选择 TP over RDMA 方案。
- **总体判断**：论文在评测维度创新与工程洞察上贡献突出，局限主要来自硬件/模型/任务的覆盖广度与统计严谨性；其"三视角 + Desiderata + 维护流程"的框架有望成为统一内存 LLM 服务评测的参考基线。
