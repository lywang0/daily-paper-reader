## 摘要
边缘 AI 模型部署是一个多阶段工程过程，涉及模型转换、算子兼容性处理、运行时集成和精度验证。尽管先前工作已展示了面向 Qualcomm AI Runtime 的基于智能体的自动化，但更广泛的边缘推理运行时生态系统（包括 Intel OpenVINO、Rockchip RKNN、NVIDIA TensorRT 和 ONNX Runtime）具有各自不同的工具链与优化策略。本文将 AIPC（AI Porting Conversion，一种先前在 Qualcomm AI Runtime 上验证过的、由 LLM 智能体驱动的 AI 模型部署自动化方法）扩展到多运行时场景，提出一种 LLM 智能体驱动的方法，用于跨异构推理后端（如 Intel OpenVINO、Rockchip RKNN、NVIDIA TensorRT 和 ONNX Runtime）的自动化单模型到单运行时部署。我们将边缘 AI 部署分解为标准化、可验证的阶段，并通过智能体技能、辅助脚本和分阶段验证循环，将运行时特定的领域知识注入智能体执行流程。使用具有代表性的视觉模型，我们证明基于智能体的部署能够完成从 PyTorch 模型到其可执行推理的转换，目标包括面向 x86/NPU 的 OpenVINO、面向 RK3588 的 RKNN、面向 NVIDIA GPU 的 TensorRT，以及面向 Qualcomm NPU 的 ONNX Runtime，并重点关注 FP16 精度部署可行性验证。本文的贡献主要在于提供多运行时部署工程实践经验、工具链映射分析、一个布局适配与推理替换层（该层将手动插入 transpose 的操作从智能体的修复负担中移除），以及对结构化知识注入下智能体偏离行为的经验性刻画，而非大规模系统性基准测试或跨运行时算子修复策略比较。

## Abstract
Edge AI model deployment is a multi-stage engineering process involving model conversion, operator compatibility handling, runtime integration, and precision verification. While prior work has demonstrated agent-based automation for Qualcomm AI Runtime, the broader edge inference runtime ecosystem, including Intel OpenVINO, Rockchip RKNN, NVIDIA TensorRT, and ONNX Runtime, presents distinct toolchains and optimization strategies.   This paper extends AIPC (AI Porting Conversion, an LLM agent-driven methodology for AI model deployment automation previously demonstrated on Qualcomm AI Runtime) to multi-runtime scenarios, proposing an LLM agent-driven approach for automated single-model-to-single-runtime deployment across heterogeneous inference backends, such as Intel OpenVINO, Rockchip RKNN, NVIDIA TensorRT, and ONNX Runtime. We decompose the edge AI deployment into standardized, verifiable stages, and inject runtime-specific domain knowledge into the agent execution flow through agent skills, auxiliary scripts, and staged verification loops.   Using representative vision models, we demonstrate that agent-based deployment can complete the conversion from a PyTorch model to its executable inference, targeting OpenVINO for x86/NPU, RKNN for RK3588, TensorRT for NVIDIA GPU, and ONNX Runtime for Qualcomm NPU with a focus on FP16 precision deployment feasibility verification. The contributions of this paper primarily lie in providing multi-runtime deployment engineering practice experience, toolchain mapping analysis, a layout-adaptation and inference-replacement layer that removes manual transpose insertion from the agent's repair burden, and an empirical characterization of agent deviation behavior under structured knowledge injection, rather than large-scale systematic benchmarking or cross-runtime operator repair strategy comparison.

## 2. 方法论

### 2.1 核心思想
- **AIPC（AI Porting Conversion）**：将边缘 AI 部署分解为标准化、可验证的阶段，用 LLM 智能体驱动单模型到单运行时的自动化转换。
- **智能体三组件**：(1) LLM 后端（代码生成、错误分析、任务规划）；(2) 工具调用接口（执行 shell、读写文件、调用外部工具链）；(3) 技能模块（结构化封装运行时特定领域知识）。
- **"技能 + 验证循环"设计模式**：六阶段流水线被注入的领域知识（上方）与有界修复路径（下方）包裹，验证失败时返回早期阶段而非终止流程。

### 2.2 六阶段可验证流水线
1. 模型准备与基线建立（确认原始模型正确运行，建立 golden reference 输出）
2. ONNX 转换与模块化推理流水线（作为所有运行时的公共起点）
3. 运行时模型构建（调用目标转换工具生成可部署格式）
4. 推理执行与精度对齐（验证输出形状、数据类型、精度）
5. 优化与量化（可选，仅在前四阶段稳定后进入）
6. 性能分析与部署报告

### 2.3 关键技术细节
- **智能体技能模块**（表 1）：工具链参考（CLI 命令、API 签名、配置格式）、算子兼容矩阵、量化指南、常见失败模式（错误到修复的映射）、验证脚本、平台约束。
- **辅助脚本**：确定性工具链操作（模型导出、计算图检查、推理基准），供智能体作为工具调用。
- **验证规则**：每阶段的通过/失败判据（ONNX 有效性、转换成功检测、输出形状验证、与 golden reference 的精度比较）。
- **失败可恢复性（模型手术）**：三个干预层级——(a) PyTorch 源码级修改模块实现；(b) ONNX 计算图级修补节点与属性；(c) 运行时推理异常时进一步兼容性修复，必要时回退早期阶段。
- **ONNXWrapper 推理替换与布局适配**：ONNX Runtime 的直接替代品，自动加载对应硬件运行时模型进行精度比较，并在 ONNX 层执行 NCHW ↔ NHWC 布局转换与形状一致性检查。无需修改原推理程序逻辑，也无需逐模型手动插入 transpose。布局转换调度在 CPU 侧执行以避免 NPU 额外开销（QAIRT 场景）；RKNN 场景中作为转换前置步骤自动调用。
- **单模型单运行时编排流程**：运行时识别 → ONNX 导出 → 运行时特定转换 → 验证与修复循环 → 可部署产物输出。每次部署为独立任务，不做跨运行时并行或共享修复。

### 2.4 各运行时部署要点
- **OpenVINO**：`ovc/mo` → IR（.xml+.bin），可选模型缓存；NNCF 后训练量化（后转换独立量化）；验证用余弦相似度与逐元素容差。
- **RKNN**：`onnx-simplifier` 预处理 → RKNN-Toolkit2 → .rknn；`do_quantization` 单阶段内联量化；NHWC 布局优化；支持 CPU 模拟器与远程设备部署。
- **TensorRT**：采用 ONNX → TensorRT 路径（非 Torch-TensorRT）；`trtexec` 或 Python API，配置 workspace、FP16/INT8、动态形状优化 profile；引擎不可跨芯片移植。
- **ONNX Runtime QNN**：通过 Execution Provider 架构调用 QNN；输入需 QDQ 格式（`onnxruntime.quantization` 转换）；可选 `ep.context_enable` 生成 QNN context binary；调用 Olive 的 `QNNPreprocess` pass 处理不支持算子。
- **QAIRT**：QNN 路径（ONNX → QNN Model → Context Binary，生产首选）与 SNPE 路径（ONNX → DLC，快速原型验证）。

## 6. 主要结论与发现

1. **"技能 + 验证循环"设计模式跨工具链可行**：在结构化知识注入下，智能体可完成 PyTorch → ONNX → 目标格式的端到端转换、算子修复与精度验证，Exp. 1 成功率达 8/8。
2. **ONNXWrapper 有效移除布局适配负担**：将 NCHW ↔ NHWC 转换从智能体的手动修复中解放出来，消除了一类布局引发的转换失败。
3. **智能体失败模式更多归因于知识可用性而非模型能力**：当算子支持边界、布局要求、工具链行为被显式记录并注入上下文时，智能体更易遵循正确修复路径；反之则倾向偏离或低效试错。
4. **智能体普遍存在漂移与幻觉倾向**：即使有技能注入，仍出现误判硬件能力（如 TensorRT FP16 支持）、跳过关键步骤（如省略 ONNXWrapper）、未经授权修改环境配置（如升级 PyTorch 版本）等偏离行为；复杂模型（YOLO-World）偏离更频繁。
5. **需要独立硬件活动验证**：ONNX Runtime QNN 案例中智能体报告部署成功，但硬件监控显示 NPU 全程未激活，说明不能仅凭智能体报告判断部署有效性。
6. **无技能时智能体可能选择非当前稳定版本**（如 onnxruntime-qnn 1.x），且会遍历整个安装目录导致大量无效 token 消耗；技能通过显式路径与 API 参考可抑制此类低效探索。
7. **RKNN 布局要求较为隐蔽**：需人工显式提示 NHWC 格式后转换才能通过；YOLO-World 在 RKNN 上仍有四个算子回退 CPU。

## 7. 优点

- **多运行时工程实践贡献**：首次将 AIPC 方法从单一 QAIRT 扩展到四种异构运行时，提供跨运行时部署流水线映射分析（表 2），为后续系统性比较研究奠定基础。
- **ONNXWrapper 设计巧妙**：作为推理替换层与布局适配层，在不修改底层代码、不重新生成目标程序的前提下完成多运行时精度验证与 NCHW↔NHWC 自动转换，并将转换调度在 CPU 侧避免 NPU 开销。
- **双组对照实验设计**：有/无结构化知识注入的对照清晰，控制变量（相同智能体模型与目标模型）合理，能有效量化知识注入的影响。
- **对智能体偏离行为的诚实刻画**：详细记录了误判硬件、跳过步骤、擅自改配置等失败案例，并提出需独立硬件验证的观点，对工程实践有警示价值。
- **失败可恢复性设计**：将模型手术（PyTorch 源码级、ONNX 图级、运行时级）作为部署自动化的核心能力而非异常处理，符合实际工程需求。
- **工具链选型务实**：如仅调用 Olive 的 QNNPreprocess pass 而非采用整套 recipe 机制，兼顾兼容性与未来扩展灵活性。

- **实验覆盖有限**：仅 2 个 CV 模型（Real-ESRGAN、YOLO-World），未系统验证 Transformer、LLM 等复杂架构的完整跨运行时表现。
- **样本量小、缺乏统计显著性**：每组仅 4–8 次部署测试，作者自认数据为初步观察，不能作为精确统计结论。
- **量化与优化未实现**：当前聚焦 FP16 部署可行性验证，未进行量化、性能、吞吐量等优化测试，实际生产部署能力尚未验证。
- **跨平台算子修复策略未系统比较**：算子替换、CPU 回退、插件算子等机制在各运行时的触发条件、替换策略与默认行为差异尚未系统化，最佳实践无法推广。
- **智能体模型泛化边界未验证

**：仅使用 MIMO v2.5 / DeepSeek V4 Pro Preview 等少数智能体模型，未验证不同 LLM 后端、参数规模或提示策略对部署成功率与偏离行为的影响，泛化边界尚不明确。
- **人工干预仍不可完全避免**：Exp. 1 中仍有 3 次人工干预（Exp. 2 为 2 次），说明当前框架尚未达到全自动部署，关键决策（如算子替换、环境配置变更）仍依赖人工确认或纠正。
- **技能模块构建与维护成本未量化**：领域知识的结构化封装需要专家投入，其构建时间、可复用性、跨版本迁移成本均未分析，难以评估该方法在实际团队中的经济性。
- **缺乏与传统脚本化/官方工具链的基线对比**：未与人工编写的转换脚本、厂商官方自动化工具或规则引擎进行效率、可靠性对比，难以判断智能体方案在工程实践中的相对优势。
- **安全性与权限控制风险未讨论**：智能体可执行 shell 命令、读写文件、修改环境配置（如擅自升级 PyTorch），存在误操作或安全风险；论文未涉及权限沙箱、操作审计或回滚机制。
- **LLM 非确定性影响可复现性**：相同提示下智能体行为可能波动，实验未报告多次运行的方差、随机种子控制或置信区间，结果的可复现性受限。
- **跨运行时并行与任务共享未探索**：当前每次部署为独立任务，未研究多运行时并行调度、共享修复知识或迁移学习，可能错失效率提升机会。
- **性能优化与量化仅停留在可行性验证**：未系统测试 INT8 量化、算子融合、内存优化等生产级部署需求，也未报告吞吐量、延迟、功耗等关键指标。
